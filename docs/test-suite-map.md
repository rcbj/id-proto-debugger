# What each test covers

Notes on the individual test files in `/tests/`. The hazards that apply to writing *any* of them — Web Crypto's secure context, `--headless=new`, waiting on content, the `@noble` pin — are in `tests/CLAUDE.md`, which is loaded whenever you open this directory; this file is the lookup.

**This is 76 of the 126 test files, not the suite.** The entries below are the ones with something non-obvious to record; the rest are named at the foot of this file with no note, and their absence means nothing about their importance. To recheck the split:

```bash
ls tests/*.js | xargs -n1 basename | sort > /tmp/actual
grep -oE '^- .[a-z0-9_]+\.js.' docs/test-suite-map.md | sed 's/^- .//; s/.$//' | sort > /tmp/listed
comm -23 /tmp/actual /tmp/listed   # test files with no entry, plus the five helpers
```

**Several tests are named for what they check rather than for the module they check**, and that is not stylistic: `tests/Dockerfile` copies test scripts and the modules they exercise FLAT into one directory, so a test sharing a basename with a module silently overwrites it or is overwritten by it. `jwk_pem.js` is checked by `jwk_pem_encoding.js`, `krb5_crypto.js` by `krb5_crypto_vectors.js`, `krb5_pac.js` by `krb5_pac_layout.js`, `dpop.js` by `dpop_vectors.js`, `jose_jwe.js` by `jose_jwe_encryption.js`, `url_safety.js` by `url_safety_schemes.js`. The module keeps its own name because other code imports it. `testsImageHasNoCollidingFilenames()` in `jwk_pem_encoding.js` now fails the suite if a new pair ever collides — three tests had been reporting green in ~30ms while executing a module.

- `token_http_exchange.js` (**the HTTP tab on the token exchange pane** — `oauth2_oidc_2.html`'s second tab, showing the Token Request and its response as they actually went: method, URL, headers and body each way, and how long the far end took. It exists because the interesting half of that exchange **cannot be observed by the page at all**: this workflow's default is to have the api make the call, so the request that matters is made by another process and the browser only sees it because the api hands back what it saw under `http_exchange` (`buildHttpTrace()` in `api/server.js`, switched on per call by `http_trace: true`). Every link in that chain fails SILENTLY — the pane keeps rendering and simply shows the browser's own call to the api instead, a plausible-looking HTTP exchange with the wrong URL in it — so the URL shown is asserted to be the TOKEN ENDPOINT, compared against the page's own `#token_endpoint` field rather than a literal, and the note is asserted to name the end that made the call. Which end that is comes off the page, not from an assumption: a static deployment has no api, `backendAvailable: false` disables the back-end radio and the call is made from the browser, where the trace is the jqXHR and the pane says which response headers CORS withheld. It runs the **Client Credentials** grant because the pane, the handler and the trace are the same for every grant this page sends and that one needs no login — the code grant's own path to this pane is covered by `oauth2_authorization_code.js` and `oidc_authorization_code.js`. Three further things it pins. The tab is asserted BEFORE the call as well as after (an empty panel behind a tab is indistinguishable from a tab that does not work, and a test that only ever looks after a successful exchange cannot tell the difference either). The tab is never selected by code and its LABEL carries the status — a successful call collapses this whole pane, so the test re-opens it the way a reader does, by clicking the title. And LAYOUT is measured with the exchange in it: nothing the panel draws may cross the pane's border and neither the panel nor the page may scroll sideways, which an empty pane would satisfy trivially. Mutation-tested: making the api never attach the trace fails it by name, at the note, with the api's own URL in the message. It covers FOUR panes that carry this exchange. The request form has the tab it was composed on; a successful call COLLAPSES that form, so the pane left on screen is **Token Endpoint Results**, which carries the same view under a **Tokens** / **HTTP** strip of its own — and that pane is not in the page at all, it is built as a string in four branches of `oauth2_oidc_2.js` and given its tab afterwards by `attachHttpTabToTokenResults()`. Four things are pinned there that the first pane cannot pin: that the strip is attached at all (dropping the call fails it by name), that there is exactly ONE strip after a rebuild, that the access token survived being re-parented into a tab panel — the tokens are filled in by value after the pane is built, so a wrap that moved them out of `#token_endpoint_result` would cost the reader the thing the pane is for — and that the two panels' text is character-for-character identical, which is what stops a second implementation of this view from growing beside the first. It then walks the journey that reaches the other branch: `token_detail.html` and back via `?redirectFromTokenDetail=true`, where `recreateTokenDisplay()` rebuilds the pane out of localStorage — the tokens, but not an exchange, since the exchange is kept per GENERATION and that pane cannot know which of the stored ones the current-token slots belong to. The tab has to say so and point at Token History, rather than being empty (a broken-looking tab) or claiming nothing has been sent yet (a lie about a page covered in tokens). Both wordings are mutation-tested. **The third pane is Currently Viewing**, and it is the one this file grew for: activating a generation in Token History draws that generation's kept exchange through the same renderer, off a `viewing` channel read back out of `token_history` — the one path here that can break without either live pane noticing, since it is fed by a JSON document rather than by the ajax handler that just ran. It is asserted on CONTENT (method, URL, status, response body, the "kept with it at" line) rather than on the tab existing, because a pane drawing its empty sentence looks exactly like one that was never given anything. **The fourth is the refresh pane's**, in the only state Client Credentials can produce — no refresh token, so no Refresh Request, so the empty state, which is the one that must say so rather than be a blank panel behind a tab; `oidc_authorization_code.js` makes a real one. **And what this file REVERSED is worth knowing before editing it**: it used to assert that nothing about the exchange reached localStorage. The exchange is now kept, so that became an assertion about REDACTION — the stored copy carries the whole exchange with the credential-bearing header and parameter values replaced, the live panes are checked to be UNredacted (the two copies are deliberately different, and a redaction leaking into the live view would take away the bytes the tab exists to show), and the client secret is looked for in the RAW stored document rather than field by field, because a secret copied into a field nobody thought to check is exactly the failure that is for. Needs the client, the api and an identity provider)

- `rfc9700_client.js` (**RFC 9700, the client half, with no browser and no services — so it never skips.** Four kinds of check. The CATALOGUE in `client/src/rfc9700.js` — fifteen sections all represented, ids unique and matching the section they are filed under, every row carrying a level, a title and a note. The MODE-OFF CONTRACT, which is the reason this file is not merely a unit test: with the compliance checkbox clear the workflow must behave exactly as it did before any of it existed, and that is invisible from inside every other RFC 9700 test because they all turn the mode ON. It is asserted lexically — an `rfc9700.enabled()` must appear inside the enclosing function of every call into a check, over both page modules — and the boundary is the enclosing `function` rather than a line count, because a line window silently changes meaning as a function grows. It is also why `rfc9700GateAuthorizationRequest()` carries a guard although both of its callers already ask: a guard living only at the caller satisfies the contract and not the check, and the two disagreeing is how the contract stops being asserted at all. THE RULES, each of the four check functions driven directly with inputs this file chooses and the exact requirement id asserted — a finding that fires under the wrong id sends the reader to the wrong section of the specification. That is where the negatives live, and they are most of the value: almost every rule in RFC 9700 fires only against a misbehaving server, and this is the only place one can be produced on demand. And the ALWAYS-ON posture — `/callback` not being an open redirector, 303 rather than 307, the three headers, no iframe anywhere, no `postMessage` in this workflow, no `'*'` target origin, the one message listener in the tree matching `event.origin`, no token in a query parameter, no third-party resource on either page — asserted over the source that holds it, because those are the properties a well-meaning edit removes silently. Note the open-redirector check reads a STATEMENT rather than a line and requires the `Location` to BEGIN with `debuggerLandingUrl()`: `/callback` deliberately copies the response's parameters through, so "nothing off the request appears in the header" would be both wrong and unimplementable — what must never happen is request-derived text deciding the origin or the path)
