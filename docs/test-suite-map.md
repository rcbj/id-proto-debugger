# What each test covers

Notes on the individual test files in `/tests/`. The hazards that apply to writing *any* of them — Web Crypto's secure context, `--headless=new`, waiting on content, the `@noble` pin — are in `tests/CLAUDE.md`, which is loaded whenever you open this directory; this file is the lookup.

**This is 24 of the 60 test files, not the suite.** The entries below are the ones with something non-obvious to record; the rest are named at the foot of this file with no note, and their absence means nothing about their importance. To recheck the split:

```bash
ls tests/*.js | xargs -n1 basename | sort > /tmp/actual
grep -oE '^- .[a-z0-9_]+\.js.' docs/test-suite-map.md | sed 's/^- .//; s/.$//' | sort > /tmp/listed
comm -23 /tmp/actual /tmp/listed   # test files with no entry, plus the five helpers
```

- `oidc_authorization_code.js`
- `oidc_dpop_optional.js` (**DPoP is optional on the OAuth2 / OIDC workflow**: off by default, on when the pane asks, off again discards the key — and, the phase it exists for, the SD-JWT VC workflow's own DPoP switch does not decide for this one. The thumbprint is recomputed in node from the public JWK in storage (RFC 7638 section 3.1) rather than read from the pane, so "the token is bound to this key" is checked against the arithmetic and not against the page agreeing with itself. Needs the STS mock and the client — no identity provider, no api. Mutation-tested twice: reverting the whole fix fails it at the *on* phase, and reintroducing only the cross-over — this workflow's state consulted first, the VC workflow's used as a fallback — fails it at the phase written for that, which is what stops the last phase being decoration)
- `oidc_userinfo.js` (**the UserInfo endpoint through all three of `debugger2.html`'s *UserInfo Data* links** — the token set the Authorization Code flow produced, the one the refresh call produced, and the one Activated from Token History. Click the link, press *Retrieve UserInfo* without touching the configuration, check the answer, come back with *Return to debugger*, next link. **Three links, because they differ only in which access token they carry** (`?type=token_access_token`, `?type=refresh_access_token`, `?type=history_access&generation=N`) and every token in the run belongs to the same user — so a link carrying the wrong one still returns a correct-looking answer. The test therefore reads the access token the UserInfo page loaded and requires it to be the one from the pane the link was in, and activates **generation 1** for the history case so that the token asked for is demonstrably not the live one. It also requires `sub` to match the ID token in the same pane (OIDC Core 5.3.2). Mutation-tested: pointing the refresh link at the original token fails it. Runs against both OPs, and unlike the flow matrix it exercises the page's DEFAULT initiation, which on a build that HAS the api is the **api** — so these two jobs need the api service too. Note that default is worth knowing: the markup gives the front-end radio `checked="true"` and the back-end one `checked="false"`, but `checked="false"` is still the attribute being PRESENT, so both are checked in the source and the last of two radios sharing a name wins — the front-end intent is dead, and the effective default matches every other initiation pane. **On the deployed static sites there is no api** (`backendAvailable: false`), where `userinfo.js` disables the back-end radio and forces the front-end one; the test reads which build it is off the page rather than assuming, and still fails a backed build that stopped defaulting to the api or a backend-less one that left the disabled option selected. Pinning the api default unconditionally is what failed the two live-site jobs on 2026-08-07, for a reason that had nothing to do with UserInfo)
- `oidc_flows.js` (**every OIDC authentication flow, with DPoP and without** — six flows times two, twelve jobs from one script, through `debugger.html` / `debugger2.html` against the mock STS. The OP is the mock rather than Keycloak because it advertises and implements all seven response types and is in this project's control, which also means the jobs need no identity provider. **The check that has to come first is what the page is about to SEND**: everything downstream still looks plausible when `response_type` is wrong, which is exactly the state five of the six were in — see `docs/oidc-flows.md`. Then: the response arrives in the fragment and no token appears in the query; exactly the artifacts the `response_type` named are present and the others absent; the ID token verifies against `jwks_uri` and carries the nonce the page sent; `at_hash` / `c_hash` match the access token and code that shipped with it (computed here from OIDC section 3.3.2.11, not read back from the server); and for the four code-bearing flows the code redeems at the token endpoint. **The DPoP axis is not symmetric, which is why it is a matrix rather than a flag**: with `OIDC_DPOP=on` a code-bearing flow must carry `dpop_jkt` on the authorization request and come back with `cnf.jkt` equal to the RFC 7638 thumbprint recomputed here from the stored public JWK, while an Implicit flow must bind **nothing** and the pane must say why — those two never reach a token endpoint, so they are exactly where a DPoP implementation can look busy and achieve nothing. An access token minted by the *authorization* endpoint is asserted to carry no `cnf` in every case. It exchanges the code **browser-direct**, which keeps the jobs free of the api service and its CORS allow-list. Mutation-tested: reintroducing the `response_type` selector bug fails all of them; blanking the results pane or re-inverting the `id_token` check each fails the job it belongs to; removing the Implicit-flow DPoP notice fails the two Implicit `on` jobs; and dropping the proof from the Token Request fails the code-bearing `on` jobs with a **400 from the token endpoint**, because the mock enforces the `dpop_jkt` code binding — a code bound to a key cannot be redeemed without it)
- `sd_jwt_vc_issuance.js` (the OID4VCI / SD-JWT VC workflow; needs the STS mock and Keycloak. Its `presentationHandoff()` section covers the *Present It* offer on steps 3 and 4 — that the click copies nothing, that the five readiness states stay distinct, and that step 4 names the generation in hand and disowns an unkept refresh. Mutation-tested: collapsing the two missing-key states, dropping the handler's own guard so a re-enabled button navigates anyway, dropping the unkept-refresh or generation clause, copying the credential into a new key, and rendering the offer only on the populated-history path are each caught. Note its "the offer is in the last pane" check now means the last pane the WORKFLOW puts on the page: every page also ends with the shared VC Tools pane, which is excluded — and asserted to be there, so the exclusion cannot hide a regression instead of accommodating one)
- `sd_jwt_vc_presentation.js` (the OID4VP / SD-JWT VC presentation workflow: the four pages against the mock Verifier, plus five negatives — a replayed presentation, a KB-JWT signed by the wrong key, an invented Disclosure, one removed after signing, and a claim the verifier asked for withheld. Needs only the STS mock)
- `sd_jwt_vc_presentation_waltid.js` (the presentation workflow against walt.id's `verifier-api2`: walt.id issues the credential, walt.id verifies the presentation, and our pages are the wallet in between. Positive by value and by reference, plus two negatives — a withheld claim, which **walt.id accepts** because it runs no DCQL-fulfilment policy, so what is asserted is that the claim never reached it and that our step 3 reports the shortfall; and a **replay** of accepted bytes into a second session, which walt.id does refuse (`nonce-check`, `NONCE_MISMATCH`) and which is what makes its `SUCCESSFUL` on the positives mean anything. Skipped when `WALTID_VERIFIER_URL` is unset)
- `sd_jwt_vc_waltid.js` (the same workflow against walt.id's `issuer-api2` — the interoperability check; needs the `waltid-issuer` container and Keycloak, and is skipped when `WALTID_ISSUER_URL` is unset)
- `wsfed_sso.js` (driven against `wsfed_request.html` — the page called `wsfed_tools.html` before 2026-08-09 — the WS-Federation Passive Requestor round trip **and sign-out**: `wa=wsignin1.0` to the Keycloak 8.0.1 side-car, login, the `wresult` POSTed to the api's `/wsfed` landing, the SAML token inspected on `wsfed_response.html` — then `wa=wsignout1.0` from the same page, in the same browser, because sign-out needs the session sign-in established. Sign-out returns no token, so what is checked is that the browser came back to `wreply` as a sign-out and that **the session is really gone**: signing in again must show Keycloak's login form rather than silently minting a second token off a surviving SSO cookie. The `signout=` flag on that last hop is **not** asserted to be `wsignout1.0` — the extension's `finishLogout` sends no `wa` at all, so the api's fallback makes it `signout=1`; `wsignoutcleanup1.0` is the value when `frontchannelLogout` is involved instead. Needs the `keycloak-wsfed` container **and** the api; skipped when `WSFED_METADATA_URL` is unset. `./local-run-tests.sh --wsfed-only` runs just this one. It also asserts the shared **Operations History** closed the sign-out out as `Success`, matching the label exported by `client/src/wsfed_history.js` rather than a string of its own — the point being that a dispatched call is only proved complete when the entry stops saying `Sent`) It drives **either landing** without knowing which — the assertions are on what the user sees, and both landings put the same thing on the same page — so it runs against the deployed static sites too. It is skipped only when there is nothing to receive the POST: `remote-run-tests.sh` probes the target with a real POST and sets `WSFED_LANDING_AVAILABLE`, and the skip message says to apply the infrastructure. `edgeLandingContract()` in that test additionally compares the Lambda's hand-off key names against `wsfed_msg.js`'s, since nothing else can catch that drift before a deployment. Related: the IdP metadata cannot be fetched cross-origin either — the cloudtrust extension's `@GET @Path("descriptor")` returns a bare String and the extension contains no `Cors.add()` anywhere, so **no client `webOrigins` setting can make that endpoint send `Access-Control-Allow-Origin`**; the page's metadata load is best-effort for that reason and the test derives the sign-in endpoint instead.
- `saml_encrypted_sso.js` (SSO against Keycloak's `saml.encrypt=true` client, then **decrypt the EncryptedAssertion in the browser**. The decryption never needed a backend — `decryptAssertion()` is node-forge in the page — but the response must arrive: that client is provisioned `saml.force.post.binding: "true"`, so it POSTs regardless of the AuthnRequest, and the Redirect fallback the other SAML jobs use statically is not available to it. Gated on `SAML_LANDING_AVAILABLE`, which `remote-run-tests.sh` probes; it asserts the ACS default is a landing and that the request asked for `ProtocolBinding=HTTP-POST`, rather than discovering either through a timeout)
- `keypair_storage_optout.js` (the key-pair localStorage opt-out on all three protocols — the "Save this key pair in browser localStorage" checkbox on `saml_request.html` and `wstrust_tools.html`, in **both** states. It earns a browser test because the failure mode is silent in the reassuring direction: if the guard in `saveState()` broke, the box would still untick and the warning note would still appear while the private key went on being written — only reading `localStorage` shows it. It asserts that checked still saves, that clearing **purges** what was already written rather than merely skipping future writes, that the purge **survives later saves** (the assertion that fails if the guard sits only in the change handler instead of in `saveState()`), that unrelated configuration and the STS's own `wst_enc_cert` are untouched, that the preference survives a reload, and that the response page then reports the missing prefill instead of claiming one. Needs only the client — no IdP, no STS — so it is never skipped. Note the two pages differ in a way that bit the first draft: the SAML page ships with *Digitally sign* ON, the WS-Trust page ships with it OFF, so on WS-Trust the key-pair pane and this checkbox are hidden until signing is enabled. Mutation-tested: ignoring the checkbox, dropping the purge, purging the wrong field set, losing the preference across a reload, and leaving the response page's prefill promise in place are each caught. It also covers the **SD-JWT VC holder key pair**, which is a bigger surface: that key is written on issuance step 2, read on step 4 to refresh, read by the *presentation* workflow to sign the Key Binding JWT, and kept per generation inside Credential History — so the opt-out purges all four copies, the gate lives in `sd_jwt_vc.js`'s `set()` rather than at the call sites (three bundles write it), and the paste-in fields on step 4 and presentation step 2 are what keep the workflow usable at all. Mutation-tested there too: leaving the history copies, removing the gate, stripping the credential along with its key, never re-enabling *Reuse the bound key*, matching any pasted key instead of the bound one, and ignoring the pasted key entirely are each caught)
- `jwk_pem_encoding.js` (the JWK → SPKI PEM encoder, `client/src/jwk_pem.js`. The DER is checked by round-tripping it through node's own SPKI parser — a stronger oracle than matching a second encoder's bytes, and one that needs no extra package installed — plus the encoding rules whose failures are silent: the DER INTEGER sign byte, minimal encoding, both length forms, and an EC coordinate a publisher trimmed a leading zero from. It also fails if any file in `client/src` takes a require that would put `elliptic` back into a bundle. No browser and no services, so it never skips. Mutation-tested: dropping the sign byte, the coordinate padding, the zero-stripping, the BIT STRING's unused-bits byte, the long-form length, the curve OID, or appending a stray byte each makes it fail. **Named `_encoding` rather than `jwk_pem` on purpose**, and for a reason that had already bitten: the tests image copies both this test and `client/src/jwk_pem.js` flat into one directory, the module's COPY runs second, and it therefore REPLACED the test — `node jwk_pem.js` loaded a module, printed nothing, exited 0, and the runner recorded a pass. The elliptic scan, the only check that catches a *new* page requiring `jwk-to-pem`, had not run in a containerized build until the rename on 2026-08-08)

- `webauthn_decode.js` (the WebAuthn decoder — `client/src/cbor.js`, `cose.js` and `webauthn.js` — against **real ceremonies**: ES256 and RS256, registration and assertion, produced by Chrome 121's WebDriver virtual authenticator and committed as `tests/webauthn_vectors.json`, so the test needs no browser, no network and no hardware, and never skips. Two oracles, neither of them ours: the browser's own `getPublicKey()`, which the COSE_Key → JWK → SPKI chain must reproduce **byte for byte**, and node's `crypto.verify`, which checks the same signatures from the JWK our COSE decoder produced. CBOR is checked against RFC 8949's appendix A, and refuses indefinite lengths (CTAP2 canonical CBOR forbids them), duplicate map keys, a declared length longer than the input, trailing data and runaway nesting. The negatives each fail exactly ONE named check — tampered authenticator data, tampered client data, challenge, origin, RP ID hash, sign-count regression — and the interesting one is user verification: a **UV-clear assertion must be rejected on the flag while its signature stays valid**, paired with the same assertion passing when UV is not required, because reporting it as a bad signature would send the user after the wrong thing entirely. Mutation-tested: removing the DER→raw ECDSA conversion breaks every ES256 check while RS256 stays green, which is the exact signature of that bug)
- `did_tools.js` (`did-tools.html` through a browser, against DIDs **generated by the mock STS**: `GET /did/generate?method=jwk|web` hands back a DID *together with a credential signed by the key that DID publishes*, so the page's verdict is checked against a known-good answer rather than against "the document parsed". `did:jwk` exercises the local-decode path with an ES256 credential — a pass cannot come from accidentally verifying against the service's RSA key — and `did:web` exercises a real retrieval plus the domain linkage. Also asserts the page writes no `did_*` key belonging to the issuance workflow. Its tampered-signature negative flips a **decoded byte**, not a base64url character: the first version edited the last character, which is a silent no-op whenever the signature's length leaves padding bits there — several characters decode to identical bytes. It passed locally and failed in the suite, in 2 of 20 credentials when measured. Needs the STS and the client. **Mutation-tested, and the first round found a hole**: making Verify Signing Key always answer VERIFIED ESCAPED, because the mismatch negative stops at "this document describes a different subject" and never reaches the signature check. It now also plants a credential whose issuer matches the document but whose signature is tampered, which is the case that reaches it)
- `sts_metadata.js` (the mock STS's own index, `GET /sts-metadata`: that it lists exactly the routes the Express router registers — failing on a route described nowhere *and* on a description with no route — that every method it shows actually reaches a handler, that no specification claim is idle and no non-spec endpoint claims one, and that every endpoint the service's RFC 8414 and OID4VCI metadata advertises appears in it. Needs only the STS mock. Mutation-tested: a new undescribed route, a renamed description, a pure stale entry, a coverage note with no detail, and a non-spec endpoint claiming a spec are each caught by the assertion meant for it)
- `did_document.js` (the wallet's DID module, `client/src/did.js`: the three methods, reading a document, `resolveVerificationMethod`'s two forms, and the DIF domain linkage check with nine negatives — each asserted to fail **the one check it should**, since a verifier that rejected everything would pass a test that only looked at the verdict. No browser and no services, so it never skips. It found the truncated P-384/P-521 curve constants on its first run; mutation-tested: overwriting a key's own `kid` in `assertionJwks`, and treating "this origin links some DID" as "it links the DID asked about", are each caught)
- `vc_did.js` (the issuer named by DID, end to end against the STS mock: the advertisement, the DID document, the domain linkage, and then — for both `dc+sd-jwt` and `ldp_vc` — that the credential names the DID and that the key **resolved from its document** verifies the signature or the BBS proof. A DID that resolves to the wrong key looks like success until exactly that last step, which is why the chain is walked rather than spot-checked. It also asserts the plain siblings still name the issuer by https URL, because a suite where every credential had switched to DIDs would have stopped testing the mechanism SD-JWT VC actually defines. Mutation-tested: a DID configuration that does not use a DID, an `issuer_identifier` hard-wired to the https base, a linkage credential naming another origin, and an `ldp_vc` `verificationMethod` left as an https URL are each caught by the assertion meant for it)
- `api_ssrf_guard.js` (the api's outbound address policy, `api/ssrf_guard.js`: which addresses the default list refuses, the range notations the configuration accepts, both enforcement layers — the URL pre-flight and the agent — and the off switch. No browser and no services, so it never skips. Mutation-tested: removing the agent's literal-address check, the IPv4-mapped reduction, or the refusal of bare single addresses each makes it fail)
- `dpop.js` (DPoP's arithmetic, `client/src/dpop.js`: the RFC 7638 JWK Thumbprint that becomes `cnf.jkt`, `htu` normalization, the `ath` hash and the proof's shape. Checked against the RFCs' **own published vectors** — RFC 9449's worked example prints an EC key and the `jkt` of the token bound to it, RFC 7638 section 3.1 does the same for RSA — plus the three silent ways a thumbprint goes wrong: an extra member, the wrong member order, whitespace. Signatures are verified with node's crypto, which shares no code with the Web Crypto path that made them. No browser and no services, so it never skips; it found a real API hazard on its first run, `proof()` throwing synchronously instead of rejecting)
- `sts_dpop.js` (the SERVER half of DPoP against the STS mock, over HTTP: all twelve RFC 9449 section 4.3 checks, `cnf.jkt` on access **and** refresh tokens, the `dpop_jkt` code binding, `jti` replay, and the nonce handshake in both shapes. Almost entirely negatives — each named for the check it is about — because a server that issues bound tokens and accepts good proofs looks finished and can be worth nothing. Its happy paths are interleaved so a server that simply stopped answering could not pass, and it writes its own DPoP client rather than importing the wallet's, so a shared misunderstanding cannot make both sides agree and interoperate with nobody. Needs only the STS)
- `dpop_workflow.js` (DPoP through the VC Issuance **pages**, which is what the other two cannot reach: that the wallet really sends the proofs, that the token really came back bound — asserted against the access token's own `cnf.jkt`, recomputed in the browser from the displayed JWK rather than read off the pane — that Holder of Key really binds the credential to the DPoP key, and that the two checkboxes are honest about each other. Driven with the pre-authorized code grant, so it needs the STS and the client and no identity provider)
- `oauth2_sts_endpoints.js` (the STS mock's authorization server endpoints; no browser)

- `webauthn_analyzer_page.js` (the **Analyzer page**, `webauthn_analyzer.html`, driven against the same real ceremonies. It covers what the node test cannot: that the decoded values reach the screen — a pane left empty by a renamed element id decodes perfectly and shows nothing. Also asserts the layout bound with an **RSA modulus** loaded, that being the longest unbreakable string the page will ever hold, and that nonsense input is refused by name rather than in silence. Needs the client and nothing else: the page performs no ceremony, so no authenticator, no IdP, no network, and not even a secure context)

- `webauthn_lab_page.js` (the **Lab page**, `webauthn.html`, running REAL ceremonies against the WebDriver **virtual authenticator** — a CTAP2 authenticator inside the browser, so no hardware, no touch, no flake. Registration decoded end to end, an assertion verified against the key kept from it, the sign counter advancing across two assertions, and a removed credential reported as `NotAllowedError` with its deliberate ambiguity explained rather than guessed at. Note what is deliberately absent: a UV-required ceremony against an authenticator that cannot verify is refused by the **browser**, so the relying party never receives a UV-clear assertion and that check cannot be exercised here — it lives in `webauthn_decode.js`, where the material can be manufactured. Two hazards recorded in the file: the JS bindings' `VirtualAuthenticatorOptions` setters return `undefined` so they cannot be chained, and the resulting failure reads `WebAuthn is not supported on sites with TLS certificate errors`, which sends you hunting through origins instead of at the line above)
