# What each test covers

Notes on the individual test files in `/tests/`. The hazards that apply to writing *any* of them — Web Crypto's secure context, `--headless=new`, waiting on content, the `@noble` pin — are in `tests/CLAUDE.md`, which is loaded whenever you open this directory; this file is the lookup.

**This is 50 of the 100 test files, not the suite.** The entries below are the ones with something non-obvious to record; the rest are named at the foot of this file with no note, and their absence means nothing about their importance. To recheck the split:

```bash
ls tests/*.js | xargs -n1 basename | sort > /tmp/actual
grep -oE '^- .[a-z0-9_]+\.js.' docs/test-suite-map.md | sed 's/^- .//; s/.$//' | sort > /tmp/listed
comm -23 /tmp/actual /tmp/listed   # test files with no entry, plus the five helpers
```

**Several tests are named for what they check rather than for the module they check**, and that is not stylistic: `tests/Dockerfile` copies test scripts and the modules they exercise FLAT into one directory, so a test sharing a basename with a module silently overwrites it or is overwritten by it. `jwk_pem.js` is checked by `jwk_pem_encoding.js`, `krb5_crypto.js` by `krb5_crypto_vectors.js`, `krb5_pac.js` by `krb5_pac_layout.js`, `dpop.js` by `dpop_vectors.js`, `jose_jwe.js` by `jose_jwe_encryption.js`, `url_safety.js` by `url_safety_schemes.js`. The module keeps its own name because other code imports it. `testsImageHasNoCollidingFilenames()` in `jwk_pem_encoding.js` now fails the suite if a new pair ever collides — three tests had been reporting green in ~30ms while executing a module.

- `api_ldap.js` (**the LDAP protocol through the api's eight `POST /ldap/*` endpoints, against the mock STS's embedded directory over a real TCP socket.** No browser: RFC 4511 is BER on a socket, so the whole protocol lives in the api and nothing about the exchange is visible from a page — `ldap_page.js` covers the page, and keeping them apart means a failure names which of the two broke. The ten operations the workflow exists for are the easy half; what earns this test its keep is the three things a happy-path version would pass without. **An LDAP result code is not an HTTP error** — `noSuchObject` on a DN that is not there is a completed round trip whose answer was "no", so every negative asserts the STATUS (200, with `ok: false`) as well as the code; answering 500 would put the most useful half of this workflow behind an error page. **The scope has to be the scope asked for** — a wrong scope returns a SUPERSET, so every assertion about the contents still holds and only the count differs, which is invisible in exactly the direction that makes it hardest to find; `one` and `sub` are therefore compared against each other rather than each being checked for "some entries", and it had already happened once in the mock, where ldapjs spells the scopes `single` and `subtree`. **Membership is a modify on the GROUP**, asserted from both ends — the members of a group are read from the group, the groups of a user are found by searching the groups for a `member` value naming the user — because an implementation that got one direction right and the other backwards looks correct until somebody asks the other question. Plus a presence filter (`(objectClass=*)` matched NOTHING here once, because @ldapjs/filter compares the attribute name case-sensitively by default, and the symptom was a successful search returning zero entries — which reads as an empty directory); `compare` answering 6 or 5, **neither of which is success**; the mock's two teaching properties, that any password binds except the literal `invalid` and that deleting a user leaves it dangling in its groups; and the auto-created user, which is one hook on `admin_stats.recordAuthentication()` and so cheap to break. Since 2026-08-18 it also builds a **populated directory** — 20 users, 10 groups, two unique users in each, and one of the twenty in all ten — because everything above it is one user and one group, which is the right shape for asserting what an operation MEANS and the wrong shape for asserting anything about a set. Three defects survive the one-of-each workflow untouched. **A search that silently returns fewer entries than matched**: three caps sit between the test and the store (the api's `ldapMaxEntries` and `maxContentLength`, the mock's `LDAP_SIZE_LIMIT`) and the honest answer to reaching one is `sizeLimitExceeded` (4), while the dishonest one is a truncated list with result 0 that is indistinguishable from a directory holding exactly that many — invisible with one entry, one `strictEqual` with twenty. **Membership that is not per-group**: ten groups of two will pass "the group contains the user" for every group even if the modify landed on the wrong one, or on all of them, so each group's member list is compared for EXACT equality against the pair that belongs in it and a superset is a failure. **The reverse lookup at fan-out**: the pivot is in ten groups and every other user in exactly one, so a `(member=...)` filter matching too much and one matching too little give different wrong answers — with one user in one group they give the same right one. The pivot is deliberately one of the twenty rather than a twenty-first, which makes one of its ten joins a re-add of a value already present: RFC 4511 section 4.6 makes that `attributeOrValueExists` (20) and **this mock answers success**, filtering the value instead, so the divergence is asserted rather than avoided — a client that learns "re-adding a member is harmless" here meets 20 the first time it points at a real directory.
