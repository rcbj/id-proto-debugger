# tests/ — the Selenium suite

Scope: everything under `tests/`, plus the launchers (`docker-run-tests.sh`, `local-run-tests.sh`, `remote-run-tests.sh`, `run-coverage.sh`) and the provisioning in `common/common.sh`. The commands themselves are in the repo-root `CLAUDE.md`; the services on the other side of each protocol are described in `api/CLAUDE.md`, `client/CLAUDE.md`, `waltid/CLAUDE.md`, `keycloak-wsfed/CLAUDE.md` and `docs/mock-sts.md`.

Tests use Selenium WebDriver with Chrome. A Keycloak test IdP is spun up automatically.

Most of them, anyway. **A handful drive the mock STS DIRECTLY over HTTP with no browser at all** — `sts_dpop.js`, `vc_did.js`, `sts_saml11.js` and, since 2026-08-31, `ssf_protocol.js` — and they are a family rather than three exceptions: each takes `WSTRUST_STS_URL` / `OID4VCI_ISSUER_URL`, each skips with a reason when there is no STS to talk to, and each is almost entirely NEGATIVES, because a mock that answers a well-formed request correctly looks finished and can be worth nothing. **A new test of the mock's protocol surface belongs in this directory and not in the `sts/` submodule**, and that is a decision somebody has already reversed once: `sts_saml11.js` was written over there on 2026-08-25, in a `tests/` directory of its own with its own `npm test`, and moved here the same day — a second suite means a second runner, a second report, a second thing CI has to know about and a second place to forget. **What went the OTHER way on 2026-08-28 is the mock's own ADMIN surface**: `sts_metadata.js`, `admin_api.js`, `sts_admin_api_operations.js` and `sts_admin_console.js` drove that service's `/admin` console and its `/admin-api`, which is a claim about the mock rather than about this debugger, and they are the submodule's tests now. The rule above is unchanged and this is the other half of it: a test of the mock's PROTOCOL surface — what it puts on the wire, which is what this project consumes — belongs here; a test of its own console belongs over there, in the tree where a control is added to that console. **The submodule now keeps NO protocol test at all.** It kept exactly one, `federation-e2e/`, on the grounds that it built a three-container topology out of several copies of the mock rather than driving one — and that ground closed on 2026-08-26, when the mock's TRUST REALMS made several copies of it out of ONE process. That test is `federation_sso.js` here, driving two realms of the mock the suite already starts, with the debugger's OAuth2/OIDC workflow supplying the application tier the old stack had to build a container for. What the move gave up is the front-channel / back-channel distinction, which needs two origins and two DNS names; what it bought is a four-second job in the ordinary pool. The submodule's own `tests/` is untouched and is a different kind: in-process assertions about its module contracts, needing no port and reachable by nothing here.

**That file was called `saml11_sso.js` until the debugger grew a SAML 1.1 service provider of its own**, and the name now belongs to the Selenium job that drives it (`saml11_sso.js`, `saml_sso.js`'s sibling, once per binding) with `saml11_options.js` beside it. The two kinds are complementary rather than redundant and both run: the browser job proves the DEBUGGER builds a request that identity provider accepts and renders the answer, and the direct one proves the identity provider is right about things a browser cannot easily reach — an artifact resolved twice, an `InResponseTo` on a profile with no request message. **They share a JOB_LOCK** (`sts-saml11`), because the direct test turns `saml11.signAssertion` off and flips `saml11.defaultProfile`, and a browser round trip inside that window fails naming the signature or the profile with nothing to say which other job did it. See `docs/saml11.md`.

**SHARED SIGNALS ADDED FOUR JOBS AT ONCE AND THEY ARE SPLIT BY WHAT EACH ONE NEEDS**, which is the division the SCIM three and the SPIFFE four make and for the same reason: a failure in `ssf_engine.js` names a RULE, in `ssf_protocol.js` a TRANSMITTER, in `api_ssf.js` the api's own contract, and in `ssf_page.js` a PAGE. Collapsing them would make every SSF defect present as the same thing. Three of the four are worth knowing about individually.

`ssf_engine.js` needs nothing at all and never skips, and it is FIRST deliberately: **the defects this protocol actually produces are never crashes.** A subject identifier with an extra member — which every conforming receiver MUST reject and which looks perfectly fine in a log; an `exp` on a Security Event Token, which RFC 8417 section 4.1.4 forbids because a SET records that something HAPPENED; `events_requested` read back as `events_delivered`, so a receiver waits for event types nothing will ever send; a delivery method spelt `push` rather than `urn:ietf:rfc:8935`. Every one of those produces a workflow that works perfectly against itself, and a broken engine makes the other three fail in ways that look like a broken transmitter.

`ssf_protocol.js` is the one in this family whose value is that **the two implementations are deliberately separate.** The mock has its own RFC 9493 subject grammar and this workflow has its own, written independently — the argument `common/pq_jose.js` makes in that submodule, applied to a grammar — so this job drives ONE reading of that specification against ANOTHER over the wire. If both ends shared an implementation, a misunderstanding they shared would be one neither could see. It also **hosts an RFC 8935 listener of its own**, in four lines of node, which is what makes push delivery testable end to end at all; `SSF_RECEIVER_HOST` is the name the TRANSMITTER has to reach the test by, which on the containerized stack is the tests container's compose name (`docker-compose-run-tests.yml` sets it, because the test's own idea of itself is `localhost` and on that bridge `localhost` is the sts container — the push would be delivered to the transmitter itself and the test would wait for an event that had already arrived somewhere else) and on the local launcher is nothing at all, since `local-tests.yml` puts every service on HOST networking and the default is then already right. It is the fourth answer to a question this suite has got wrong before.

`api_ssf.js` exists for four things no module test can see, and the first is the one that would be silent: **the body parser for `application/secevent+jwt`.** Neither `bodyParser.json()` nor `bodyParser.urlencoded()` touches that media type, so without the text parser `api/server.js` installs for it every push arrives as an empty body — a failure that reads as a transmitter sending nothing.

**What each individual test covers is in `docs/test-suite-map.md`** — 24 files' worth of notes, including which services each needs and what gates or skips it. Read it before changing a test you did not write, or before adding one that overlaps. What follows here is the part that applies to **every** test in the suite, and each item below has already cost a run.

## The suite runs in a POOL, so a test may not assume it is alone

`run-report.js` ran its jobs one at a time until 2026-08-23, and the cost was the whole suite's wall clock: 196 jobs, 20.6 minutes, of which the **median job is 3.2 seconds** and the ten longest are 54% of the total. The jobs were already independent processes — each spawns its own browser, writes its own log, returns its own result, and nothing in `buildJobs()` declares an order — so they now run **`TEST_CONCURRENCY` at a time**, defaulting to one less than the machine's cores and held between 2 and 4. The cap is not politeness: the longest jobs here are CPU-bound in-browser crypto (SLH-DSA and RSA on the Digital Signature page, 96s and 108s of one 261s job), a GitHub Actions runner has 2 to 4 cores, and on the containerized stack Keycloak, Postgres, both mock STS instances, both walt.id containers and the WS-Fed side-car are on that same machine.

**On the two CONTAINERIZED launchers that setting had to cross `sudo` first, and until 2026-08-27 it did not.** `docker_compose()` in `common/common.sh` runs compose under `sudo`, whose `env_reset` keeps only the assignments written on its command line — built from `COMPOSE_FORWARDED_VARS`, which named neither `TEST_CONCURRENCY` nor `STS_LOG_LEVEL`. So the `${TEST_CONCURRENCY:-}` passthrough in `docker-compose-run-tests.yml` substituted to the empty string, `run-report.js` read `parseInt("")`, and the pool sized itself from the **container's** view of the cores exactly as though nothing had been asked for. Nothing warned: a `${NAME:-}` with a default is not a missing variable to compose, and the only evidence was the wall clock — which is the thing the person setting it was trying to change. `./local-run-tests.sh` never had the problem, because it runs `run-report.js` on the host and the variable is simply inherited. All three tuning variables are forwarded now (`TEST_JOB_TIMEOUT_MS` joined them and gained a passthrough of its own), and **`tests/compose_env_forwarding.js`** holds the arrangement to it: it parses every compose file in the tree for both forms a variable can be read in — a `${NAME}` substitution and a bare `- NAME` under `environment:` — and fails if one of them is not on the forwarded list. Node only, so it runs everywhere; the compose files are COPYed into the tests image for it, and a missing one FAILS the check rather than skipping it.

**`TEST_CONCURRENCY=1` restores the old behaviour exactly, live streamed output included, and it is the first thing to try when a job fails here and passes on its own.** Above 1, a child's output is buffered and written as one block when it finishes, because interleaving the lines of four browsers makes all four unreadable — the per-job **log file is still written as the bytes arrive**, so `tail -f report/latest/logs/NN-*.log` follows a running job either way. The report is written in job order regardless of the order things finished, and the runner now prints its wall clock against the sum of the job times.

**A job's process TREE is reaped when the job ends, and this is not a tidiness measure — it is why the suite no longer takes the machine down.** A browser job is `node` → `chromedriver` → `chrome`, and one headless Chrome is about **fifteen OS processes** (browser, two crashpad handlers, two zygotes, a gpu process, the network and storage services, a renderer per frame); only the first of the three is the runner's child. Until 2026-08-26 a test that died without reaching `driver.quit()` left the whole browser resident: selenium's own exit hook (`io/exec.js`) sends SIGTERM to **chromedriver** and nothing at all to the browser it launched, so chromedriver died and Chrome was orphaned. Measured that day: **one failing job left 11 Chrome processes behind, and a run of this suite left 559**, which exhausted the laptop's memory and cost a reboot. Every job is therefore spawned **`detached`**, giving it a process group of its own that chromedriver and chrome both inherit, and `runJob()` sends one `process.kill(-pgid, "SIGKILL")` after **every** job — passing ones too, because a job that passed can still have leaked a browser. A **per-job watchdog** (`TEST_JOB_TIMEOUT_MS`, default 900000ms = 15 minutes, `0` disables it) kills the tree of a job that never exits and records it as a timeout; the default is deliberately far above the slowest real job, which was 389s on 2026-08-26. **`detached` has a price that is paid in the same place:** a child in its own process group no longer receives the terminal's Ctrl-C, so `run-report.js` installs SIGINT/SIGTERM/SIGHUP handlers that reap every live group before exiting — without them, interrupting the runner would leave the whole pool running with nothing left to kill it.

**The other half of that fix is in the test files, and it is the reason the leak existed at all: `process.exit()` inside a `catch` SKIPS the `finally` that quits the driver.** `process.exit()` is synchronous termination and the `finally` of an `async` function needs a microtask turn that never comes, so `} catch (e) { log.error(e); process.exit(1); } finally { await driver.quit(); }` — which is how 39 of these files were written — never quit anything. The shape now is a `let testFailed = false;` above the `try`, `testFailed = true;` in the `catch`, and the `process.exit(1)` **after** the `try` statement has finished. Two variants matter as much: an exit **inside the `try` body** (the `PKCE_ENABLED` validation in five files) skips the `finally` just as thoroughly and is now a `throw`, and an exit inside a **helper called from** that `try` (`tokenDetailPage()` in `oidc_authorization_code.js`) skips its caller's `finally` and now rethrows. Write new browser tests this way from the start: the runner's group-kill is a backstop for a suite run, and it does not protect somebody running `node tests/foo.js` by hand.

**What must not overlap is declared in `JOB_LOCKS` at the top of `run-report.js`, in one table, because it is a property of the SERVICE a script drives rather than of the script.** The mock STS keeps its `/admin` configuration in memory and **it survives between jobs** — the hazard `docs/mock-sts.md` already warns about, which sequential execution hid. A lock name means "no two of these run at the same time": `sts-vc` is the mock's credential and verifier configuration (`/admin/vc` and `/admin/vc-verifier-config` — the claims a credential carries and the ones the Verifier asks for, which `sd_jwt_vc_presentation.js` pins and the rest of that family reads off the wire), `waltid` is the same argument for walt.id's own issuer and verifier containers, `sts-rfc9700` is the mock's RFC 9700 **trust realm** that `rfc9700_flows.js` reconfigures through `/realm/rfc9700/admin-api/config/set` (the name is kept from when it was a second instance; the state it protects is a realm override now, so it serialises those jobs against each other and no longer against anything driving the permissive server), `sts-tls` is the mock's client truststore, which `pki_mutual_tls.js` fills and empties on a live process, and **`sts-spiffe`** is that service's SPIFFE configuration and registry — `spiffe_protocol.js` names an administrator in `spiffe.adminIds` (the only route from "I can fetch an identity" to "I can drive the registry" that does not already require one), shortens `spiffe.svidTtl` to watch a rotation, and turns `spiffe.autoCreateEntries` off — DELETING the invented entry — to run a client's "I have no identity" path. Each is restored per setting, but not instantly, so a job fetching an SVID inside that window gets an EMPTY LIST, which reads as a Workload API that stopped issuing. **`EXCLUSIVE` — the job runs alone, before the pool starts — is in that table and nothing claims it at present**: the three jobs that did drove the mock's admin surface and left this suite on 2026-08-28. Keep the mechanism in mind rather than the vacancy, because the shape of job that needs it recurs: one that reads a TOTAL off the mock, or that changes something the process has only one of and a trust realm therefore cannot contain.

A script that is not in that table runs unlocked, and that is the right default: nearly every test here mints an identity of its own (`random_username.js`, and the `stamp` prefixes in `scim_page.js` and `ldap_page.js`) and asserts on **what it created** rather than on a total. Three rules follow for anything written from now on.

* **Assert on your own litter, never on a total.** `GET /admin-api/scim` reporting *n* operations, `/admin/tokens` holding *n* artifacts, a KDC principal table of size *n* — every one of those is now somebody else's job's business too. `scim_protocol.js` gets this right (it looks for its own prefix in the list); a count comparison is what `EXCLUSIVE` in `JOB_LOCKS` exists for, and is the reason the mock's own `admin_api.js` held it while that job still ran from here.
* **A test that CONFIGURES a shared service belongs in `JOB_LOCKS`,** and the symptom of forgetting is a failure in a job that has nothing to do with it — a wrong claim set, a `dcql_query` naming claims the workflow never mentions, an empty truststore. That is the failure `sd_jwt_vc_presentation.js` already documents from 2026-08-18, arriving from a *concurrent* job instead of from a hand-driven stack.
* **The mock STS USED TO BLOCK ITS EVENT LOOP for tens of seconds, and a `fetch` to it during that window did not fail like a busy service — it failed like a dead one.** The cause was fixed on 2026-08-30 (rcbj/mock-sts#6: the post-quantum signing runs in a pool of stateless child processes and the front process's loop stays free — `workers.count`, default 2, nothing here sets it), and the retry described below STAYS, because what it is really defending against is a shared service that is busy, which is a standing condition of a pool of six jobs and not a property of one algorithm. One SLH-DSA-SHAKE-128s signature is about twelve seconds of straight-line CPU in a single-threaded node process, and `sts_userinfo_protected.js` asks for one per advertised algorithm, twice over. While that runs the kernel still ACCEPTS the connection, so a TLS handshake to that port starts and never finishes; undici gives it ten seconds and throws `TypeError: fetch failed`, whose whole stack is internals and which names no URL, no service and no algorithm. That is what took `sts_jws_verification.js` out on 2026-08-29 — it opened its first connection twenty-two seconds into its own in-process work, straight into the other job's ID Token pass. Those two jobs were marked `EXCLUSIVE` for a day as the interim fix and are not any more. **A test that talks to the mock over HTTPS should retry a CONNECTION failure rather than report it**; `stsFetch()` in `sts_jws_verification.js` is the pattern, and it says in its message how long it waited so that a mock which really is down still reads as one. A `JOB_LOCK` is the wrong tool here: the two jobs share no state, and serialising them would cost the pool a minute to fix a client-side timeout.
* **Anything named after the clock needs the pid too.** `Date.now()` is not unique when four jobs start in the same millisecond: the seven Chrome profile directories under `/tmp` (`digital_signature.js`, `jwt_tools.js`, `saml_tools.js`, `encoding_tools.js`, `oauth2_metadata_rfc8414.js`, and the two operation-history tests) carry `+ "-" + process.pid` for exactly that reason. `browser_flags.js` and the download directories were already safe — they use `fs.mkdtempSync`, which is the better habit.

The ceiling is now the **longest single job**, not the pool: `digital_signature.js`, measured at 261s before the JWS and XML Signature panes were added on 2026-08-24 and about 30s longer with them (a host run of the whole file took 292s). Splitting it by pane (it has NINE independent sections now and already reports them separately) is the next thing worth doing, and the same question applies to `sd_jwt_vc_issuance.js` at 116s — which also carries 43 `driver.sleep()` calls, the largest concentration in the suite, so there it may be cheaper to wait on content than to split.

## The federation GRID is forty-nine jobs of one script, and it is unlocked on purpose

`federation_matrix_sso.js` is one parameterised script that `run-report.js` schedules **forty-nine times**: every combination of five application protocols (`oidc`, `oauth2`, `saml2`, `saml11`, `wsfed`), five federation protocols (the same five), and two ways the far realm authenticates (`password`, `webauthn`), less the one point `federation_sso.js` already drives. `FEDERATION_APP_PROTOCOL`, `FEDERATION_FED_PROTOCOL` and `FEDERATION_MECHANISM` select the point; the job NAME in `report.xml` is the combination, which is the whole reason it is forty-nine jobs and not five of fifteen. A grid job that walks its combinations inside one browser is faster and reports a group: the first failure ends the group, and reproducing one point means running fourteen others first.

**It is unlocked, and the argument is the "assert on your own litter" rule taken to its limit.** All forty-nine share `federation-matrix-1` and `federation-matrix-2` — one pair of realms, created by whichever job gets there first, with the create RACE-TOLERANT rather than asserted, because forty-nine `must()` calls on the same create is a coin toss. Every object a point asserts on is named after its own combination: its application, its two relationships, its partner entry, its username. So **nothing here may assert anything REALM-WIDE** — not the number of relationships, not the size of the directory, not the contents of the register — which is exactly what `federation_sso.js` DOES assert about `federation-realm-2` and why the grid was given realms of its own rather than reusing 1 and 2.

**The one shared setting it changes is not put back, and that is deliberate.** The twenty points whose federation protocol is `oidc` or `oauth2` have a BACK CHANNEL — realm 1 redeems a code at realm 2's token endpoint through `federation_http.js`, which is https-only and refuses a certificate nothing trusts unless `federation.outboundAllowInsecure` says otherwise, and every stack here runs the mock on a certificate it regenerates at each start. So the job sets it, asserts from the reply that the write landed **in realm 1** rather than process-wide, and leaves it. Forty-nine jobs setting and resetting one realm setting around each other is a flake that appears only in the pool; a setting left on in a realm nothing else reads is not.

**Two mechanisms and not three.** SPNEGO was asked for and is deferred rather than faked — and the 2026-08-27 `sts/` bump retired HALF of the reason, so read the surviving half rather than the shape of the sentence. The mock has a real SPNEGO acceptor — RFC 4559 carrying RFC 4178 carrying an AP-REQ, verified through `krb5_service.accept()` at `/spnego/protected` — and it **is** an authentication mechanism there now: `/authn/spnego` (`kerberos/spnego_authn.js`) calls `startSession()`, `authn.js` resolves `spnego` as a mechanism that draws no screen, an application can carry `appAuthnMechanism: spnego` and an identity-provider-side relationship `fedAuthnMechanism: spnego` — which is precisely the third column this grid would need. **What is still missing for THE GRID is the browser end**, and it is the half that was always the open question: where a headless Chrome gets a ticket, and the allow-listed host it will answer a `Negotiate` challenge for — the mock's own `/spnego` page says so. Until a job can produce both, twenty-five points stay deferred; the mock side of them no longer is. **`kerberos_spnego_signin.js` is not that job and does not unblock it**: it drives the sign-in door with the DEBUGGER as the Kerberos client rather than the browser, which is enough to prove the door works and is not enough to authenticate a browser mid-flow the way a federation point would need. What DID change on 2026-08-27 is that the real-GSSAPI path became possible at all — this KDC advertised no PA-ENC-TIMESTAMP until then, so no MIT-derived client could get a ticket from it and `kinit` failed with `Generic preauthentication failure`. A grid column would now need `krb5-user` in the image and a per-run `krb5.conf`, which is a cost to weigh rather than an impossibility.

**The WS-Federation row exists because this grid changed the mock.** `wsfed.js` used to draw a sign-in screen of its own and call `startSession()` directly, rather than going through `authn.js`'s `beginAuthentication()` like the other three browser SSO profiles. The screen was better; owning the FUNNEL was the cost, and three features that live in the funnel did nothing for that profile alone — federation, `fedAuthnMechanism`, and the WebAuthn step in either role. It goes through the shared funnel now, `POST /wsfed/login` is gone with it, and `wsfed_sso.js` was unaffected because it already tried `#kc-login` before `#wsfed-login`. The grid detects an older submodule up front, by asking the endpoint what it does with a `wsignin1.0`, and SKIPS naming the submodule — because on an older mock the flow does not fail: it signs the person in at realm 1 and federates nothing, which looks exactly like a pass.

**It found three bugs in the mock on its first full run, and they are the argument for the grid rather than a footnote to it.** Each is invisible from any single point of it:

* **WebAuthn did not work inside a trust realm, at all, since realms existed.** `authn.js` compared `clientDataJSON.origin` against `baseUrlOf(req)` — which is `https://sts:8081` in the default realm and `https://sts:8081/realm/acme` in `acme`. An origin never has a path, so the check passed in the default realm by coincidence and failed in every other one, refusing the ceremony with `origin matches / got https://sts:8081, expected https://sts:8081/realm/acme`. The only existing test of that step, `webauthn_oidc_mfa.js`, runs in the default realm. Fixed with an `originOf()` beside `rpIdOf()` — the same mistake waiting to be made twice: one is the origin, one is its host, and neither is the base URL.
* **A SAML 1.1 federation lost its flow handle to a registered partner.** `federation_sp.js` sent only `TARGET` (its ACS URL plus a `fedctx` query) and no `shire`, so the partner chose the destination itself — and one that has this service REGISTERED posts to the registered address, which is the same path with the query stripped, because a registration holds a URL and not a per-flow handle. The assertion then verifies, the sign-in completes, and the person lands on the mock's own "signed in" page instead of going back to the application: a federation that works perfectly and never returns. Fixed by sending both, which is what a real SAML 1.1 service provider does.
* **WS-Federation federated nothing, and honoured no `fedAuthnMechanism`** — the funnel change described above, which is why the grid's WS-Federation rows are gated on a submodule probe rather than left to fail.

`federation_admin.js` beside it is the management-API client — `adminGet`, `adminPost`, `must`, `tidy` — which `federation_sso.js` and `federation_chain_sso.js` each still carry a private copy of. That is two copies and a shared module rather than three copies; folding the two older tests in is mechanical and was deliberately not done in the same change as forty-nine new jobs. **`federation_choice_sso.js` uses the shared module**, which is what it is for: a fourth private copy would have made the count worse than the reason it exists.

`federation_choice_sso.js` is the fourth federation job and the only one that drives an application with **more than one partner**. `webapp-sso-1` in `federation-choice-1` names BOTH a SAML 2.0 relationship and an OpenID Connect one to `federation-choice-2`, so the mock draws its chooser at `/authn/select-idp` rather than redirecting — which is possible because `appFederationRelationship` holds a LIST as of 2026-08-26, and it is why the two older tests read that attribute with `[].concat(...)` and clear it with `/applications/remove` rather than a `set` the mock now refuses by name. **It signs in twice, and that is the test.** Both relationships work — `federation_sso.js` and the grid prove that — so what is new is that a choice was offered and HONOURED, and the only assertion that separates that from a service which took the first usable partner is arithmetic: one relationship at one sign-in and the other at zero, then one each. It clears cookies between the two runs, because a session left by the first satisfies the second authorization request with no chooser drawn at all. Its own realms, for the reason the grid has its own: it asserts exact counts.

## Every job that presents an identifier to the mock STS REGISTERS IT FIRST

Since 2026-08-27, a test that is about to send a client_id, an entityID, a wtrealm, an AppliesTo, a service principal name, a bind DN, a SCIM client id or a SPIFFE workload id to the mock STS puts that application in its registry FIRST, with the configuration it is about to use. `tests/sts_applications.js` is the one implementation — `provision(base, spec)`, create-or-reconcile, read back, assert — and its header carries the whole argument. Do not write a second copy of it.

**The mock requires none of it, and that is the point rather than an objection.** That service accepts an identifier it has never heard of and creates the entry from the SIGHTING, so what the entry then knows is the identifier and nothing else: no redirect URI, no ACS, no reply URL, no declared family, no name. Every job here was written against that, and every job here was therefore proving less than it looked like it was. `rfc9700_flows.js` is the case that showed it: the mock judges an authorization request against the client's OWN registered URIs when it has any and against the `oauth2.redirectUris` SETTING when it has none, so the compliant pass was being judged against a global list that no client in it had registered — and it passed. It would have passed against a client whose registration named somebody else's callback.

Four things about using it, each of which is a way of getting it wrong:

* **`stsBaseFor(url)` for a job that runs against BOTH identity providers; `baseOf(url)` for a job that only ever drives the mock.** Half the SAML, WS-Federation and OIDC jobs are pushed once per IdP, and `run-report.js` passes `WSTRUST_STS_URL` to both halves on purpose — `process.env` reaches every child anyway, so the wiring is documentation and the ORIGIN CHECK is the protection. `stsBaseFor()` compares the document this job was actually given against the mock's origin (and its realm prefix, where it has one) and answers `""` for anything else, which is what keeps Keycloak's provisioned client out of the mock's registry. `baseOf()` skips that check, so it belongs only where there is no other server the job could mean.
* **Register what will be SENT, not something plausible.** The redirect URI is read from the variable the flow will type in; the assertion consumer service is read off the page, because that is the deployment's own statement about where a response is posted; the derived SPN is registered and never the one the mock advertises instead. A registration naming a URL the run will not use is exactly the plausible-and-wrong entry this change exists to replace — and in `kerberos_spnego_page.js` substituting the advertised name for the derived one is the specific mistake that once kept that job green while the workflow led a person into `KDC_ERR_S_PRINCIPAL_UNKNOWN`.
* **It reconciles rather than failing when the entry is already there**, which it will be: on a second run against a live stack, after some earlier job presented the identifier, and when two jobs of the same run provision concurrently. Every write reports "nothing changed" for a value already present, so it is safe to repeat and safe to race. `fresh: true` forgets the entry first and is almost never right — only for a job that asserts on its OWN counters, and only for an identifier no other job shares.
* **A missing STS is a skip; an STS that refuses is a failure.** Called with no base it returns `null` and the caller carries on. Called with one, a refusal fails the job there, naming the attribute — because a provisioning step that skips itself quietly is a provisioning step that has stopped happening while the report stays green. The one exception is a mock with no registry at all, which is logged at WARN and named as a submodule bump.

**`tests/sts_applications.js` needs its own `COPY` line in `tests/Dockerfile`**, the way `random_username.js` does, and for the same reason: nothing schedules it, so no cross-check notices it missing and a job that requires it dies with `MODULE_NOT_FOUND` in a tenth of a second while passing on every host run.

**Three files keep hand-written copies of this and are not being migrated**: `oauth2_delegation_chain.js`, `wstrust_delegation_chain.js` and the four `federation_*` jobs, which all provisioned through `/admin-api` before the shared module existed. Each asserts more about its entries than `provision()` does — an audience that must be ABSENT, a relationship list that must be exactly one — and rewriting them to call the shared one would lose that. They are the reason it exists; they are not what it replaces.

## One job drives the mock with a client NOBODY HERE WROTE, and it is the only one that can

`krb5_mit_client.js` runs `kinit`, `klist`, `kvno`, `kdestroy` and `curl --negotiate` against the mock KDC. Every other Kerberos job in this directory — the four node-only ones and the four browser ones — drives it with `common/krb5/`, which this project wrote, and that is the blind spot the job exists to cover.

**It found a defect that had been there for the whole life of the feature.** The mock's `KDC_ERR_PREAUTH_REQUIRED` carried `PA-ETYPE-INFO2` and `PA-PW-SALT` and not `PA-ENC-TIMESTAMP` — the salt without the METHOD. MIT reads that list to decide what to send next (RFC 4120 section 5.9.1), found nothing it could run, and gave up with `Generic preauthentication failure`; Chrome and Firefox answer `Negotiate` through the same GSSAPI, so no browser could ever have signed in at `/spnego/protected` or `/authn/spnego`. **Every test in both repositories passed throughout**, because the debugger's client and all of them send the timestamp whether it was offered or not. Both ends shared the assumption, so both ends agreed.

That is the general lesson and it is not about Kerberos: **a mock tested only by the client it was written alongside cannot be shown to interoperate with anything.** Where a real implementation of a protocol exists and can be installed, one job driving it is worth more than another dozen driving ours. `sts_dpop.js` writes its own DPoP client for a weaker version of the same reason — a shared misunderstanding between two halves of one implementation passes and interoperates with nobody — and this is that argument taken all the way.

Three things about running it:

* **`KRB5_TRACE` must name a FILE, never `/dev/stderr`.** Under captured stdio that path is a pipe, MIT's trace writes go nowhere, and the variable appears to do nothing — silently. A shell shows thirty lines and `spawnSync` shows none, so a test written against the shell's behaviour reads every exchange as "the KDC returned no errors" and every refusal assertion passes for the wrong reason. It cost an afternoon.
* **MIT logs the two exchanges differently.** An AS refusal is `Received error from KDC: -N/message`; a TGS refusal is `TGS request result: -N/message`, and the SUCCESSFUL TGS logs that same line with code 0. A parser reading only the first form reports "the KDC said nothing" for a KDC that refused perfectly clearly.
* **The client's last word is not always the KDC's answer.** For an expired password the mock correctly answers `KDC_ERR_KEY_EXPIRED`, MIT then asks for a `kadmin/changepw` ticket the mock does not serve, and what `kinit` finally prints is `Server not found in Kerberos database`. Asserting on that would assert the mock got it wrong when it got it right, so that case reads the FIRST error.

It writes its own `krb5.conf` and credential cache under the system temp directory, stamped with the pid — no root, no `/etc/krb5.conf`, and two of them cannot share a cache. `tests/Dockerfile` installs `krb5-user` (with `DEBIAN_FRONTEND=noninteractive`, because that package asks for a default realm), so the containerized suite always runs it; on a machine without MIT Kerberos it skips with a reason naming the package.

## A test of a mode that ships OFF has to assert the OFF state too

`rfc9700_client.js` and `rfc9700_flows.js` cover the RFC 9700 compliance mode on the OAuth2/OIDC workflow, and they carry a hazard worth generalising before the next optional mode is written.

**Every test of a feature behind a switch naturally turns the switch on.** So nothing in a suite full of such tests can see the day the feature starts acting with the switch off — and for this one that failure means the debugger refusing to talk to identity providers it exists to be pointed at, reported by users as the tool being broken rather than as a rule being enforced. The mode-off state is therefore asserted deliberately and in two places: lexically over the source (`rfc9700_client.js` requires an `rfc9700.enabled()` inside the enclosing function of every call into a check) and behaviourally in the browser (`RFC9700_FLOW=refused` loads the page with the mode off and requires that nothing is disabled and no report was drawn). It also asserts that turning the mode off gives back every control it took away, which is the other half nothing else can see.

Two environment notes specific to those jobs. They need a compliant STS, and since 2026-08-25 that is a **trust realm on the same mock the permissive pass uses** — `.../realm/rfc9700` — rather than a second container. It used to be a second one, and the reason is worth keeping: `oauth2.rfc9700` derives `global.https` over there, so it binds the main port as TLS, and a bound socket is settled once when the process starts. mock-sts closed that by marking the flag `realmRuntime` — restart-only for the PROCESS, settable on a realm, because **a realm binds no socket**. `configureStsRfc9700Realm()` in `common/common.sh` creates the realm (the realm is in memory and gone on restart, so there is nowhere to declare it) and is also the capability probe that leaves `RFC9700_STS_URL` unset when the submodule is too old. The jobs are gated on `RFC9700_STS_URL` rather than `WSTRUST_STS_URL` so that a permissive server cannot be handed to them by accident — which matters MORE now that the two are one process told apart by a path prefix, since a URL that lost its prefix would reach a running, healthy, permissive server rather than nothing at all. `rfc9700_flows.js` additionally refuses BY NAME to run against a permissive STS.

**What a realm cannot bring with it is a scheme, so the scheme moved to the process and the whole suite followed.** This pass is only honest over TLS — requirement 8.1 is that every configured endpoint is https — so the mock is started with `STS_HTTPS=true` on all three stacks and every STS URL in this suite is https. The certificate is self-signed and regenerated every start, so nothing holds an anchor for it: `trustStsCertificate()` fetches it once the service answers and installs it for node (`NODE_EXTRA_CA_CERTS`, inherited by every job `run-report.js` spawns) and for Chrome (`STS_SPKI_PIN`, turned into `--ignore-certificate-errors-spki-list` by `browser_flags.js`), and the `api` container does its own in `api/sts_truststore.sh`. **All three ADD an anchor rather than turning verification off**, and that is deliberate: `NODE_TLS_REJECT_UNAUTHORIZED=0` or the blunt `--ignore-certificate-errors` would each have disarmed `api_ssrf_guard.js`, `api_tls_probe.js` and `url_safety_schemes.js`, which exist to assert that a bad certificate is refused. See `docs/rfc9700.md`.

**And the containerized stack cannot use its own callback, which is the mode being right rather than a test being wrong.** Requirement 1.3 is RFC 8252's rule — a `redirect_uri` is https, or http on `127.0.0.1` / `[::1]` / `localhost` — and in mode the client refuses to send anything else, *before* the browser leaves the page. A host run is at `http://localhost:3000` and satisfies it; the containerized stack serves the debugger at `http://client:3000`, which is neither, so on the first containerized run of these jobs all three authorization-request flows failed at a sign-in screen that never appeared, with the browser still on `oauth2_oidc_1.html`. Nothing in that failure names a redirect URI. The fix moves the CALLBACK and nothing else: `run-tests-in-container.sh` sets `RFC9700_REDIRECT_URI=http://localhost:3000/callback` and `rfc9700_flows.js` gives Chrome `--host-resolver-rules=MAP localhost:3000 client:3000` so the browser can reach it — resolution only, so the ORIGIN the browser sends is still the loopback one the requirement is about. It works because `/callback` is stateless: it reads nothing and 303s to `appconfig.uiUrl`, so the pages and the transaction's `localStorage` stay on `http://client:3000` throughout. Note this is also what a user does — the debugger's own callback IS `http://localhost:3000/callback`, the case that exception exists to permit. Moving it also found a **product** bug that a host run cannot reach, because there the two origins coincide: step 2 healed the stored `redirect_uri` onto `appconfig.uiUrl` when it loaded, so the exchange carried `http://client:3000/callback` for a code issued to the loopback one and the mock refused it with `invalid_grant`. The whole symptom was a 400 from the token endpoint and a token-response report that never drew. See `docs/rfc9700.md`.

**`rfc9700_client.js` needs the client SOURCE TREE in the image, not a module beside it.** It is the one test here whose subject is a directory: two thirds of its checks are lexical sweeps over `client/src` and `client/public` (no iframe anywhere, no `postMessage` with a `'*'` target origin, no token in a query string) plus `client/server.js`'s headers and callback. So `tests/Dockerfile` mirrors those into `/usr/src/client/`, which is where the script's `../client/{src,public}` resolve from `/usr/src/app` — **not** `client/public/js`, which is 90 MB of gitignored bundles a fresh clone does not have either. Without that copy the job failed in 0.0s with `Cannot find module '/usr/src/client/src/rfc9700.js'`: the script was in the image and its subject was not. The mirror it lands in is the same one the Kerberos pane tests use, and the hazard that mirror carries is two sections down.

## Nothing outside compose may hold a port the stack binds

The local stack (`local-tests.yml`) is **host networking** throughout, so its containers bind this machine's ports directly and whoever got there first wins. On 2026-08-20 a mock STS started by hand from a sibling checkout — in RFC 9700 mode, so it was serving **HTTPS on 8081** — was still running hours later when `./local-run-tests.sh` started. The compose `sts` container hit `EADDRINUSE` on a `listen` with no error handler and exited seconds after `up -d` had already reported success, and **71 of 184 tests failed without one of them naming the cause**: WS-Trust and WS-Federation timed out waiting for a response page, Kerberos reported `ECONNREFUSED` on 88, the OIDC matrix got `fetch failed` in 0.3s, and — the part that matters most here — the jobs that probe their dependency before using it (LDAP, PKI mutual-TLS, the DPoP server checks) reported **PASS** while quietly skipping, which is the failure mode `docs/test-suite-map.md` warns about, arriving from outside the test.

Two guards now stand in front of it, and both are in the launcher rather than in a test, because a test cannot fail usefully about a service that is not there. `requireComposeServiceRunning()` requires each STS container to still be running a moment after `up -d`; `requireStsReachable()` then requires the port to answer **in the scheme expected**, and when it does not, probes the other scheme before reporting — because in this service the scheme follows the mode, an instance in the wrong one closes the connection rather than refusing it, and "other side closed" names a socket and never names the mode.

Stop a stray instance **by PID**, from `ss -ltnp`, never by pattern.

## What the launchers must get right

**Tests must not assume the client's baked defaults exist.** `client/src/env/local.js` and `docker-tests.js` set `rfc8414MetadataUrlDefault` / `oid4vciIssuerUrlDefault` to this suite's STS, so the workflow pages open ready to use; `prod.js` and `test-idptools-com.js` set them to **`""`**, because a public site has no business defaulting to somebody's localhost. A test that asserts such a default therefore fails against the deployed sites for a reason that has nothing to do with the protocol. Assert the *shape* of a default when one is present, note its absence otherwise, and supply the URL from the test's own environment — which is what these tests do anyway a few lines later.

The same rule covers **what the deployed sites do not have**, not only what they do not default to: `prod.js` and `test-idptools-com.js` set `backendAvailable: false`, and the pages read it — `userinfo.js`, `introspection.js`, `wstrust_tools.js`, `saml_request.js`, `wsfed_request.js` and `oauth2_oidc_2.js` all change their initiation controls when there is no api behind them. `tests/oidc_userinfo.js` asserted "the page defaults to calling from the api" unconditionally and so failed both its live-site jobs on 2026-08-07, naming a UserInfo default for what was really a static build. Read the state off the page (there, whether the back-end radio is even *enabled*) and assert the branch that build should be in; that keeps the guard sharp on both.

`./remote-run-tests.sh [base-url]` runs the same suite against a site that is **already deployed** — `https://test.idptools.com`, `https://idptools.com`, or a local dev server — while starting everything on the *other* side of each protocol locally, in an isolated compose project (`idptools-kctest`, `keycloak-tests.yml`): Keycloak 26.x on 8080, the mock STS on 8081 (WS-Trust plus the OID4VCI issuer and OID4VP verifier), **Keycloak 8.0.1 + wsfed on 8082**, and **walt.id's issuer on 7005 and verifier on 7003** behind their CORS proxies. Selenium drives a LOCAL browser, which is what makes that work against an https site: Chrome treats `http://localhost` as potentially trustworthy, so the page may talk to those without a mixed-content block.

Two things that launcher must get right, and both were missing until 2026-07-30 (the SD-JWT VC and WS-Federation jobs were silently skipping or failing): the walt.id **keys and rendered configuration** have to exist before compose starts, since both services mount a directory that is generated per run; and **`OID4VCI_WALLET_URL` must be the target base URL**, because the mock issuer's Credential Offer pages and the mock verifier's request pages hand the End-User back to the *wallet*, which here is the deployed site — its default of `localhost:3000` sends them nowhere. It reaches the container through `docker_compose()`, which forwards a fixed list of variables explicitly **because `sudo` resets the environment**: for a long time only `CONFIG_FILE` was passed, so every other `${...}` in a compose file (including `GIT_COMMIT` and `BUILD_NUMBER`) silently substituted to empty.

**A protocol may have two IdPs, and the launcher decides how many of them a run has.** Every WS-Federation case runs twice — once against the Keycloak 8.0.1 side-car (`WSFED_METADATA_URL`, exported by `configureKeycloakWsfed` only once the side-car has served its descriptor) and once against the mock STS (`WSFED_STS_METADATA_URL`), which grew the passive profile in 2026-08. Each half skips on its own variable, so a run with one IdP and not the other does 21 of the 42 and says which is absent. Two things about that second variable are deliberate: it is **browser-facing**, so it follows the same DNS rule as `WSTRUST_STS_URL` (compose name only on the containerized stack, loopback everywhere else — Chrome treats `http://localhost` as potentially trustworthy from an https page and a bridge name as mixed content); and it is a **separate variable** rather than derived from `WSTRUST_STS_URL`, because that one may legitimately point at a real Apache CXF STS with no WS-Federation endpoint at all, and deriving would turn "not this protocol" into 21 failing jobs. `docs/wsfed.md` records what the two IdPs each cover that the other cannot.

**A deployed target may not have the PAGE at all, which is a different thing from not having a backend.** Every gate above asks what a page can *reach*; `KERBEROS_PAGES_AVAILABLE` asks whether it was deployed. Kerberos is DER over port 88, so all six of its pages need the api's relay and `client/static_site.js` leaves them out of a static build entirely — both landing cards there are greyed out. SPNEGO is in that list although its own exchange is HTTP: the ticket it carries still comes from a KDC, and the pages that obtain one are not deployed. `remote-run-tests.sh` sets the variable `false` for a deployed target and `run-report.js` skips the page jobs naming it; without that they run against a 404 and report a missing element on a page nobody deployed. Three of the four would otherwise skip anyway, for the wrong reason (an unreachable KDC), and `kerberos_decoder_page.js` has nothing else to skip on — it needs no service, which is exactly why it used to run there. Set it `true` for a remote target that *is* api-backed.

**LDAP has a gate of its own, `LDAP_AVAILABLE`, and it is a SEPARATE variable rather than a reuse of the Kerberos one.** The two protocols are missing from a static deployment for the same underlying reason — both are binary over a raw TCP socket, so both need the api and a static site has none — but they are missing *independently*: a remote target could perfectly well be api-backed with a directory reachable and no KDC, or the reverse, and deriving one from the other would turn "not this protocol" into a set of skipped jobs about a protocol that is there. It reaches **both** LDAP jobs. `api_ldap.js` was once left out of it — it speaks only HTTP, so it never acquires the `CONFIG_FILE`-resolved-against-`sts/` failure that made two Kerberos jobs go red on a remote target, and it skips with a more specific reason of its own ("the api answered 404 for GET /ldap/limits"). That sentence is true and the report it produced was not: on a static target the 404 is not a discovery but the known state of a deployment with no api, and a line naming a missing endpoint invites somebody to go looking for it. Both now skip for the reason that is actually true.

**A job's own `API_URL` / `STS_URL` are NOT `API_BASE_URL`, and getting them wrong is silent.** `run-report.js` passes `API_URL` to six jobs and `STS_URL` to seven — the two LDAP jobs, the two SCIM jobs and the AS / TGS-AP / SPNEGO / delegation page jobs — and defaults both to a **host's** view, `http://localhost:4000` and `http://localhost:8081`. That is right for `./local-run-tests.sh`, where the stack is host-networked, and wrong inside the tests container, where those two addresses are the tests container. `API_BASE_URL` is a different variable and does not cover it: that one is the SAML / WS-Federation address an identity provider is told to POST to, which `common.sh` registers on the Keycloak client. `tests/run-tests-in-container.sh` therefore defaults `API_URL=http://api:4000` and `STS_URL=http://sts:8081` for the containerized stack, under the same `http://client:*` case as `WSTRUST_STS_URL` — and both names have to resolve in the **api's** container as well, because `SCIM_BASE_URL` and `LDAP_URL` are the api's view of the mock rather than the test's. Until 2026-08-22 nothing set them, and the failure was invisible: all seven of those jobs treat an unreachable api or mock as "not this deployment" and **skip with a reason**, so each reported PASS in about a tenth of a second on every containerized run. `scim_protocol.js` has no such fallback and is what finally said so. **A browser job that passes in 0.1s has not started Chrome** — that is the tell, and it is worth a glance down the report's times whenever a workflow is "already covered".

**`KRB5_KDC_HOST` is `sts` on BOTH stacks, and the default that looks right is the one that fails.** The four Kerberos page jobs pass that value to `run-report.js`'s job env and each test types it into the page; the address is then resolved by the api's relay, not by the browser, so `localhost` there means the api container — where nothing listens on 88 and the page reports `Could not talk to ::1:88`. The compose name is correct on the containerized stack because Docker's DNS answers it, and correct under `./local-run-tests.sh` because `local-tests.yml` gives the api an `extra_hosts` entry mapping `sts` to `127.0.0.1` (every service there is host-networked, so there is no Docker DNS at all). That second half is why `kerberos_delegation_page.js` shipped with an EMPTY job env and nobody saw it until 2026-08-23: under host networking the api's own loopback *is* the host the mock KDC listens on, so the test's `localhost` default passed every local run, and on the containerized stack the job was skipping for the unrelated `API_URL` reason above. Fixing that one exposed this one. All four jobs now carry the same three variables.

**And there is now one Kerberos job for which `sts` is the WRONG answer, which is why it has a variable of its own.** `krb5_mit_client.js` drives the mock KDC with MIT Kerberos itself, so nothing resolves a name on its behalf: `kinit` opens the socket in the test's own process, out on the launcher. It therefore reads **`KRB5_TEST_KDC_HOST` / `KRB5_TEST_KDC_PORT`**, `run-report.js` defaults those to `localhost`, and `run-tests-in-container.sh` overrides them to `sts` for the containerized stack alone — exactly the split `SPIFFE_TEST_*` draws against `SPIFFE_*`, and for the identical reason. It shipped on 2026-08-27 carrying `KRB5_KDC_HOST: "sts"` copied from the page jobs above, and the first `./local-run-tests.sh` after it went red with `kinit: Cannot contact any KDC for realm 'EXAMPLE.COM'` — a message naming neither the variable nor the stack, against a KDC that was up and reachable from the same shell. The file deliberately does **not** fall back to `KRB5_KDC_HOST`: that would be one variable standing for two views again, one layer down, and a shell exporting it for the page jobs would silently re-break this one.

**The PKI page has a third gate, `PKI_TLS_AVAILABLE`, and it is the interesting one because that page is NOT missing from a static deployment.** The CA, all twenty X.509v3 extensions and the keystore matrix are Web Crypto and pkijs in the browser and work on `idptools.com`; one pane cannot, the TLS / mutual-TLS test connection, which needs `POST /tls/connect` because a browser cannot choose a client certificate, cannot be given a truststore, and cannot read the handshake it made. So the landing card stays live, `pki.js` greys that one pane and disables every control in it, and the gate switches off the two jobs that are about the connection itself: `api_tls_probe.js` and `pki_mutual_tls.js`. `api_tls_probe.js` is the one that needs it — node-only, its own listeners, no api and no site, so nothing would stop it running against a deployed target and passing, and a green *TLS probe* line in a report about a site whose TLS pane is greyed out is the most misleading thing in it. **`pki_page.js` is deliberately not gated**: the greying is a property of exactly that build, so the job runs and asserts it in place of the section it cannot run there. See `docs/pki.md`.

**And the gate has to cover the whole protocol, not the pages it was named after.** As `KERBEROS_PAGES_AVAILABLE` it skipped four jobs and left ten — the codec, the crypto vectors, the PAC layout, the decoder output, the codec sync, the relay, both mock-KDC exchanges and both Windows ones. Those are node-only, so nothing stopped them running against `https://test.idptools.com`, where Kerberos does not exist. They exercise LOCAL code and say nothing about the deployed site, so at best they are noise; at worst they are what happened on 2026-08-15 and 2026-08-16, when both mock-KDC jobs failed there with `Cannot find module './env/test-idptools-com.js'` — because `remote-run-tests.sh` sets that `CONFIG_FILE` and `sts/common/helpers.js` resolves a relative path against `sts/`, which ships only `local.js`, `docker-tests.js` and `test.js`. (Since the mock's 2026-08-23 reorganisation that resolution is `sts/common/config_file.js`'s job rather than a side effect of every module living in the package root — it makes `CONFIG_FILE` absolute once, against the mock's root and then the working directory, so the behaviour above is unchanged and is now deliberate.) Two red tests, twice, for a protocol switched off on that target. The variable is now **`KERBEROS_AVAILABLE`** (the old name is still read), and `run-report.js` applies it as a **sweep over every job whose script starts `krb5_`, `kerberos_` or `api_krb5_`** rather than at each push site — so a Kerberos test added later inherits the gate instead of being forgotten, which is precisely how the original ten were missed.

**That `CONFIG_FILE` failure is fixed at the source now, and the gate is no longer what stands between the suite and it.** A gate switches off a protocol; it does not help the jobs of a protocol that IS on. `webauthn_cross_impl.js` hit the identical thing on the remote run of 2026-08-28 — `Cannot find module './env/test-idptools-com.js'`, a require stack naming `sts/common/config.js`, and nothing anywhere naming CONFIG_FILE, the mock or the tests directory. The mock resolves that variable against its own package root and then the process's CWD, and neither is `tests/`: `run-report.js` spawns every job from the REPOSITORY ROOT, so the CWD candidate misses, and the mock ships no `test-idptools-com.js` of its own, so the first one does too. It goes unnoticed locally only because `sts/env/local.js` exists and wins. **`mockStsModule()` now closes it on this side**, in `alignConfigFileForMockSts()`: before handing back a module from the mock, it makes `CONFIG_FILE` absolute against `tests/` — but ONLY when the mock's own two candidates would both miss, so a local run still gets the mock's own configuration rather than this suite's, which is what it has always had. It warns when it rewrites. Any test that loads a mock module through `mockStsModule()` inherits the fix; a test that reaches into `sts/` some other way does not, which is one more reason not to.

## Coverage, provisioning and the environment hazards

`./run-coverage.sh` runs that same containerized stack with Istanbul/c8 instrumentation (`docker-compose-run-tests.yml` + `docker-compose-coverage.yml`, the override touching only `api` and `client`). It therefore needs **everything the plain launcher does before compose starts**, and for a while had none of it: the walt.id key generation and `renderWaltidConfig` (both walt.id services mount `waltid/generated-*-config`, which is not in the repository — without the render compose creates those paths as empty directories, the services exit, and `--abort-on-container-exit` takes the whole run down), the pre-run teardown of stale containers from either stack, the WS-Federation side-car started and checked on its own, and a `waitForWaltid` through the proxies' published ports so a service that dies during startup prints its own log instead of stalling the healthcheck the `tests` service depends on. It tears the stack down on any exit, including the early ones those checks can take.

**But the launcher is not the only way this run diverges, and the second way is worse, because it is not in the launcher at all.** The coverage build is the only build that appends `client/src/coverage_beacon.js` to each bundle — raw, after browserify, so `require` and `process` do not exist where it runs. On 2026-08-14 the repo-wide style sweep gave that file the standard `require("bunyan")` logger; it threw at top level before `setInterval()`, which meant **no frontend coverage was collected at all** (`coverage/frontend/.nyc_output` empty, `report/lcov.info` 0 bytes, while the c8 half of the report was perfectly normal at 40KB) *and* 12 tests failed on `Uncaught ReferenceError: require is not defined`. Note the shape of that failure list, because it is what makes it expensive: the 12 were exactly the tests that assert the browser console is clean — `oauth2_metadata_rfc8414`, `saml_tools`, both WebAuthn page tests, and eight of the VC issuance/presentation ones — so it reads as twelve unrelated protocol regressions, each naming a page and a line number inside a 130,000-line bundle, and none naming coverage. **Neither `./docker-run-tests.sh` nor `./local-run-tests.sh` can reproduce it**, since neither appends the beacon; `appendedBeaconNeedsNoModuleSystem()` in `tests/jwk_pem_encoding.js` therefore reads that one file for `require`/`process`/`module.exports` on every ordinary run, so the coverage-only breakage is visible without a coverage build. When a run of this script fails a spread of protocol tests that the plain suite passes, check the browser console lines in the logs before the protocols.

**The coverage report now has a THIRD domain, and the first two were pointing at the wrong work.** Until 2026-08-23 only the browser bundles (Istanbul) and the api process (c8) were instrumented — and roughly a third of the jobs here never open a browser, taking the real `client/src` and `api` modules in-process through `module_paths.requireSharedModule()` instead. Every branch those jobs covered was reported UNCOVERED: `api/krb5_frame.js` read 29.7% while `api_krb5_relay.js` asserts each of its malformed-frame rejections by name, and `client/src/scim_client.js` read 40.3% while `scim_engine.js` calls `chooseDigestChallenge`, `verifyAuthenticationInfo` and `hobaToBeSigned` directly. On that report **336 of the api's 474 own-code missing branches, and about 2,935 of the frontend's 10,092, sat in modules that already had a node test** — so the obvious next move, writing tests for the worst numbers, would have been writing the ones that already existed. `run-report.js` now sets `NODE_V8_COVERAGE` on every job it spawns when `COVERAGE=true` and renders `./coverage/node` with c8 at the end of the run; the report also labels each job **unit** or **browser** (derived from whether its script requires `selenium-webdriver`, so it cannot go stale) and the JUnit `classname` says which. See COVERAGE.md.

**Before writing a test to raise a number, check which domain measured it.** The keytab reader is the worked example: `client/src/krb5_keytab.js` read 1.9% branch coverage in the frontend report, which reads like a module with no tests. It has one — `tests/krb5_describe_output.js` builds keytabs in both byte orders, reads them back, and asserts the refusals — and under node it was already at 78.9%. The genuinely uncovered part was **twelve branches**, all of them the reader's own bounds checks, and covering them properly took one new section rather than a new file. A new file would have been a near-duplicate of a test that already passed.

**The SAML SP key pair is never committed.** `generateSpKeyPair()` in `common/common.sh` generates a fresh self-signed RSA pair per run and exports `SAML_SP_PRIVATE_KEY` / `SAML_SP_CERT` (read by the tests through `common/sp_keypair.js`) and `SAML_SP_SIGNING_CERT` (registered on the Keycloak SAML client). It lives only in the run's environment — the containerized suite generates its own inside the tests container. Do not reintroduce a key pair under `tests/fixtures/` (gitignored, along with `sp-key.pem` / `sp-cert.pem`).

**A PUBLIC client's `CLIENT_SECRET` is a placeholder, and it used to be the word `null`.** Keycloak answers `"secret": null` for a client that has none, `jq -r` renders that as the four characters `null`, and `common.sh` exported it verbatim — so every job driving a public client typed `null` into the debugger's Client Secret field, where it is ignored and harmless. It stopped being harmless the moment a test went LOOKING for the value: `oidc_authorization_code.js` asserts the secret never reaches `token_history`, every stored generation carries `"failure":null`, and both public jobs failed on 2026-08-24 over a credential that does not exist while the confidential ones, whose secret is real, passed. `common.sh` now substitutes `public-client-has-no-secret-<flow>` for that case. It cannot be EMPTY — every one of these tests asserts `CLIENT_SECRET` is set, and the provisioning's own blank check would exit first — and the point of a marked string over a bare one is that the redaction check stays meaningful on a public client: the field still holds something, the page still sends it, and it still must not reach storage. If you write a test that searches a document for a credential, search for something that cannot occur in JSON structure, and assert that what you were looking for was actually SENT — `oidc_authorization_code.js` now counts the redacted `client_secret` parameters it found, because an absence in a document that never contained one is not a pass.

**Web Crypto needs a secure context, and the containerized suite is not one.** `window.crypto.subtle` exists only on HTTPS or a localhost origin. Locally the debugger is at `http://localhost:3000` (trustworthy, so Web Crypto works); in the containerized stack it is at `http://client:3000` — plain HTTP on a DNS name — where `crypto.subtle` is **undefined**. Most of the app depends on it (`jwt_tools.js`, `jose_jwe.js`, `vci_wallet.js`, `sd_jwt_vc.js`, `sd_jwt_vp.js`, `metadata_client.js`'s signature verification, `token_detail.js`, `digital_signature.js`, `encoding_tools.js`), so in that stack those pages silently have no crypto. The failure never says so: it appears as a `signed_metadata` signature that "does not verify with any key" (each `importKey` throws and is skipped) and as timeouts waiting for holder key pairs, proofs of possession and Key Binding JWTs that are never produced — which is how it cost a full debugging round. `tests/browser_flags.js` handles this and one other environment hazard, and the four SD-JWT VC tests call it; **any new browser test that signs, verifies, encrypts or hashes — or whose page must fetch one of this suite's local services — must call it too**:

- `--unsafely-treat-insecure-origin-as-secure` (plus the `--user-data-dir` Chrome requires alongside it), applied only to an origin that is not already a secure context, i.e. the containerized `http://client:3000`.
- `--allow-running-insecure-content` and `--disable-features=BlockInsecurePrivateNetworkRequests,PrivateNetworkAccessSendPreflights,LocalNetworkAccessChecks`, applied always. These matter against a **deployed https target**: this suite's services all live on loopback, and a fetch from a public origin to a private address is a Private Network Access request that Chrome blocks or preflights. The symptom is a status pane that never fills and a timeout naming metadata, a verdict or a credential — nothing about the network. Every other browser test in the suite had carried these flags for years; the four SD-JWT VC ones did not, which is why all four failed against `https://test.idptools.com` while passing locally.

**Clicks and reads taken just after a navigation — or just after any action that writes to Operations History — must tolerate a stale element.** `oauth2_oidc_2.html` rebuilds its panes on load, after every token call, and after each `saveOperationToHistory()`, so a `WebElement` found a moment earlier can be detached before it is used — and the window is easy to miss on a *read*, because `findElements()` and `getAttribute()` are two round trips with a re-render able to land between them. `tests/oidc_userinfo.js` flaked two runs in three on exactly that, immediately after *Return to debugger*, and `tests/oauth2_token_revocation.js` died on the live-site run of 2026-08-07 with `stale element reference` on its **second** revocation, where the re-render the first one triggered landed between `findElement()` and the click. **`clickStable()` and a stale-tolerant `valueOf()` therefore live in `common/tests.js`** (already staged into the tests image) rather than in one test — use those, do not write a third copy. Both re-find inside a retry loop; only staleness is retried, so a genuinely missing element still returns null or fails and the tolerance cannot hide a real regression.

**A results box that persists between two identical actions must be emptied before the second one.** Same test, next line: `#revocation_result_textarea` still holds the first revocation's `HTTP Status: 200` while the second revocation is being submitted, so waiting for that string is satisfied before the second call is even sent and the test reports a revocation it never watched. Waiting for the text to *differ* is not the fix either — RFC 7009 lets both calls answer 200 with an empty body, and that wait would then time out on a call that worked. Clear the field first (and assert it cleared), then wait for it to fill. A test that passes on a leftover value is a test that quietly does nothing, so mutation-test it: skip the second click and confirm the test now fails.

**And the same is true of a STATUS line, which is the field almost every tool page reports through.** `tests/encryption_tools.js` waits for a pane's status to *settle* — non-empty and not ending in an ellipsis — and the previous action's message satisfies that instantly, so the wait returns before the new operation has run, the assertion after it grades the wrong thing, and the output field is read before it is written. It produced two false passes before it produced a failure (an "As PBES2 JWE" step reading a one-segment value out of a box the previous case had filled). The fix is worth copying as much as the rule: the blanking happens inside `clickButton()` and `selectOption()`, which find the enclosing pane's `.ds-status` from the element itself, rather than at the thirty call sites — the version a caller has to remember is the version that gets forgotten, and this one fails by passing. It also means a page must keep its half of the bargain: **every in-progress message ends with an ellipsis and nothing else does**, which is the only way "still working" is told from "finished" on a page whose operations are deferred. Two messages on that page were written as `"Generating a key pair… (pure JS)"` and the test waited out its whole budget on the first of them. See `docs/encryption.md`.

**`--headless=new`, never bare `--headless`, in any browser test that uses crypto.** The tests image pins **Chrome 121**, where plain `--headless` selects the OLD headless implementation — and in that one `--unsafely-treat-insecure-origin-as-secure` has no effect. So on the containerized suite's `http://client:3000` origin `window.crypto.subtle` stays undefined however carefully `browser_flags.js` was called, and the symptom is a timeout waiting for a key pair that names neither crypto nor headless mode. It cost a containerized run of 13 jobs on 2026-08-05: the three new OIDC tests used bare `--headless` while the eighteen older crypto tests already used `=new`, and the give-away was that `dpop_workflow.js` — which generates a DPoP key on the same origin in the same run — passed. **It cannot be caught locally**: from Chrome 132 the old mode is gone and `--headless` IS the new one, so a modern browser passes either way.

**Ed25519 in Web Crypto is off in the image's browser, and the failure names `importKey`.** Chrome enabled Ed25519 in the Web Cryptography API by default only in **Chrome 137**; the tests image pins **Chrome 121**, where the implementation is there but gated, so every `crypto.subtle` call naming `{ name: 'Ed25519' }` rejects with *Algorithm: Unrecognized name*. `browserFlags.addWebCryptoEd25519Flags(options)` turns on that one Blink feature (`--enable-blink-features=WebCryptoCurve25519`, rather than `--enable-experimental-web-platform-features`, which also works but turns on everything else Chrome 121 has not shipped); it is a no-op on any browser that already has it, which is why a **host** run passes without it and only the containerized suite sees this. Just one page here needs it — the PKI page, whose `ed25519` key algorithm is a real Web Crypto key; `digital_signature.js` reaches Ed25519 through `@noble` and is unaffected. It cost the containerized run of 2026-08-19, the only failure of 182 jobs, and it did not arrive as a `generateKey` error: `pki.js`'s *Generate Key Pair & Issue Certificate* is one button, so generation failed, the next status line replaced its message, and what the report carried was `Could not issue the certificate: Failed to execute 'importKey' ... Unrecognized name` — a call made on the key pair still in the fields, which belonged to the previous case's algorithm. `generateAndIssue()` now stops when the private key field did not change, so the status line names the generation that failed; the flag is what makes the case run at all.

**A browser that reconfigures itself mid-request logs a failed load that is nobody's page.** Chrome abandons a request whose certificate-verifier or network configuration is REPLACED while it is in flight and reports it as `net::ERR_CERT_VERIFIER_CHANGED` or `net::ERR_NETWORK_CHANGED` — the server was never asked and no certificate was rejected on its merits, so neither is a verdict on anything, and Chrome's own `net_error_list.h` describes both as errors the caller should retry. Two things can cause it here and this suite controls neither: Chrome's component updater landing a new CRLSet or root store while the browser is up, and the verifier configuration carrying `addStsTrustFlags()`'s own `--ignore-certificate-errors-spki-list` being applied after the first navigations have started. What reaches the console is one ordinary `Failed to load resource` line naming whatever URL was in flight, so the twenty-odd tests here that assert a clean console read it as a page error: on the `./remote-run-tests.sh` run of 2026-08-28 it was the SINGLE failure of 270 jobs — `https://test.idptools.com/css/bootstrap.css`, on a job whose every functional assertion had already passed. `browserFlags.isTransientLoadError(message)` (and `withoutTransientLoadErrors(messages)` for a caller that has already mapped its entries down to strings) drops **exactly those two codes**, logging every drop at info so a run that met one says so. It is deliberately not widened to `Failed to load resource`: `net::ERR_CERT_AUTHORITY_INVALID` is a certificate that WAS verified and found wanting, `net::ERR_CONNECTION_REFUSED` is a service that is not there, and a filter that swallowed those would make every console assertion in this directory decorative. `transientLoadErrorsAreFilteredNotSwallowed()` in `tests/jwk_pem_encoding.js` holds both halves: the codes that must be dropped, the five real failures that must not be, and that every test judging SEVERE console entries applies the filter — a file that only LOGS them on its way to failing is listed there instead.

**And headless at all is not optional, in any browser test, for any reason.** That is a separate rule from the one above and it is the one that gets missed, because `browserFlags.addBrowserAccessFlags(options, baseUrl)` reads like it configures the browser: it does not, it deals with the secure-context and private-network hazards only and never touches headless mode. A test copied from a neighbour can therefore carry the flags and not the flag — `kerberos_delegation_page.js` did, and popped a real window on every run of the suite from the day it was written. That is a stolen desktop locally and a dead run everywhere else: a CI runner and the tests container have no display, so the session fails at `session not created` naming the page the test was about to visit. Keeping a `headless` variable so a human can watch a run is fine and customary here; initializing it `false` is not, because then every unattended run opens windows. **`tests/browser_tests_headless.js` asserts both** over this directory's own sources — a file with `new Builder()` and `.forBrowser()` must pass `--headless` through `addArguments()`, and any `headless` variable it declares must start out `true`.

**A section that clears `localStorage` must restore it.** `tests/sd_jwt_vc_issuance.js` runs one browser session through the whole workflow and then over a dozen further sections, several of which need an EMPTY page to measure or to check a pane's initial state — and the sections after them run on the state the workflow left behind. `preservingLocalStorage()` returns a restore function for exactly this; `metadataSignatureValidation()` and `presentationHandoff()` do the same by hand. Clearing without restoring does not fail where the mistake is: it fails hundreds of lines later in `presentationHandoff()` with "no credential in storage", which reads as a broken issuance. That assertion now names the likely cause and lists the keys it did find.

**What the mock STS does is now runtime configuration, so a test that assumes its defaults must pin them.** The admin pages change what that service *is* for the life of the process — `/admin/vc` what an issued credential carries, `/admin/vc-verifier-config` which claims the mock Verifier asks a wallet for and which credential format an unqualified request asks for, and nothing resets any of it between tests. So a suite run against a stack somebody has been driving by hand meets a `dcql_query` naming five claims while the test still selects two, and **every** presentation in that file is refused on `Requested claims` — including the control case, whose whole job is to prove the refusals above it are about the defects rather than about the verifier. That is how `sd_jwt_vc_presentation.js` failed on 2026-08-18, in 0.13s, naming `email, birthdate, nationality` — three claims the test never mentions. It now POSTs the claims it wants, names `format=dc+sd-jwt` on every `/oid4vp/start`, and then **reads the next request back off the wire** to prove the pin landed, because the POST's answer is only the service's account of itself and a setup step that quietly does nothing is worse than none. The neighbouring presentation tests (`ldp_vc_presentation.js`, `jwt_vc_json_presentation.js`) survived that drift because they read the requested claims out of the request rather than hold a constant — do one or the other, and never assume the mock is as it shipped.

**A host run needs the STS's OWN `node_modules`, and `tests/module_paths.js` cannot supply them.** Four tests load `sts/common/vendored/bbs2023.js` from the submodule in place — `bbs2023_cryptosuite.js`, `ldp_vc_issuance.js`, `ldp_vc_refresh.js`, `vc_did.js`, each comparing the issuer's cryptosuite with the wallet's — and that module reaches `@digitalbazaar/bbs-signatures` through a dynamic **`import()`**. ESM resolution walks the directory tree upward from the importing *file* and **does not consult `NODE_PATH`**, which is the whole mechanism `module_paths.js` uses to make a borrowed module's CommonJS `require`s resolve against `tests/node_modules`. So those four fail at load with `ERR_MODULE_NOT_FOUND` unless `sts/node_modules` exists; `prepTestEnv()` in both host launchers therefore runs **`npm ci --prefix sts`** — `ci` rather than `install` because mock-sts commits its lock and `npm install` rewrites it (its lock still carries the pre-rename package name), which would leave the submodule showing a modified file after every run. The containerized suite never sees this: there `bbs2023.js` is copied flat beside the tests, next to `tests/node_modules`.

**`tests/package.json` pins `@noble/curves` and `@noble/hashes` at `1.4.0`, and the pin is load-bearing.** `client/src/bbs.js` is written against the 1.x layout (`require("@noble/curves/bls12-381")`, `@noble/hashes/sha256`), matching `client/package.json`'s own `1.4.0` pin — but 2.x renamed every subpath (`./bls12-381.js`, `./sha2.js`) and removed the old ones from `exports`, so the failure is `Package subpath './bls12-381' is not defined by "exports"` at require time, which reads as a broken module rather than a version mismatch. `@digitalbazaar/bbs-signatures@3.1.0` — the independent implementation `bbs_crypto.js` and `bbs2023_cryptosuite.js` check ours against — depends on `^2.2.0`, so before the pin it took the top-level slot and both tests died at load. Declaring 1.4.0 directly gives the client's module the hoisted copy and leaves bbs-signatures a **nested** 2.2.0, so each gets the major it was written for; that arrangement is what `tests/package-lock.json` now records, and it is why the pin cannot simply be relaxed to match the newer dependency.

**No test may `require("chromedriver")`.** It is not a declared dependency of `tests/package.json` — Selenium finds the driver itself — so a `require` for it makes that one test the only file in the suite that cannot *start*, with `MODULE_NOT_FOUND` in 0.1s, on any checkout installed from the manifests. It is an easy line to leave behind after developing a browser test as a standalone script, which is exactly how `dpop_workflow.js` acquired one.

**`populateMetadata()` now waits for the endpoints to arrive AND is willing to click Populate again, and every test in the suite was racing it before.** Two separate things are being waited on and conflating them is what made it flaky. *Retrieve* fetches the discovery document asynchronously and the Populate button is rendered only when it arrives, so waiting for that button does gate on the fetch — but the click itself can still land without effect: the button is re-rendered as the table is built, so a click can reach the copy being replaced, and the handler leaves every field untouched when it runs against an empty document (jQuery's `.val(undefined)` is a no-op, so the seeded placeholders simply remain). One click plus a bare wait therefore fails about once per cold run — it took out the **OAuth2 Client Credentials** job on 2026-08-05, a test that touches no authorization endpoint at all. The helper now re-finds the button and clicks again until the endpoints fill or the deadline passes, and mutation-testing it is easy: inject a capturing listener that swallows the first click on `.btn_oidc_populate_meta_data` and the single-click version fails while this one recovers. The helper in `common/tests.js` clicked *Populate* and returned; the discovery document is fetched asynchronously, so the caller could read `#authorization_endpoint` while it still held the placeholder `initValuesToLocalStorage()` seeds — `https://localhost/oauth2/authorization`. The authorization request then went to a host nothing is listening on, and the failure named the OP ("the OP did not show its login screen", at `https://localhost`) rather than the race. It surfaced about one run in a dozen. The wait is for the field to be filled **and no longer the placeholder**, rather than for an expected URL, so the one condition covers Keycloak's realms, the mock STS and a deployed OP alike; ten consecutive runs of the case that failed now pass.

**The address bar is no longer the authorization request, and one of the assertions that read it was a negative.** The mock STS hands an unauthenticated `GET /oauth2/authorize` to its own authentication service — a 302 to `/authn/login?authn=<id>`, with the request held server-side — so by the time the login screen is up, `driver.getCurrentUrl()` is an opaque id and nothing else. Keycloak renders its login screen AT the authorization URL, which is why reading the request off the bar worked for years and why this only bites the sections pointed at the mock. It failed `sd_jwt_vc_issuance.js`'s H.1 section on 2026-08-19 in a message that at least named itself ("the authorization request MUST carry the offer's issuer_state ... Got: http://localhost:8081/authn/login?authn=…"), but the same file has two NEGATIVE assertions on that URL (`indexOf("authorization_details=") === -1`) which would have gone on passing while reading a URL that could not have carried one either way — a test that has quietly stopped asserting. `startAuthorizationRequest()` there now takes the request from the browser's own record of it: chromedriver's PERFORMANCE log carries a `Network.requestWillBeSent` for every navigation, redirected-away ones included, and the helper drains the log before the click, filters to `Document` requests to the page's own `authorization_endpoint`, and **asserts it found one** rather than falling back to the address bar. Turning that log on is two lines at the driver (`prefs.setLevel(logging.Type.PERFORMANCE, logging.Level.ALL)` and `options.setPerfLoggingPrefs({ enableNetwork: true, enablePage: false })`); it is a separate buffer from the BROWSER log, so `severeErrors()` and every console-error check see exactly what they saw before.

**Three WebAuthn hazards, all measured, all of which fail by naming something else.** **Branded Google Chrome will not side-load an unpacked extension** — it refuses the flags and says so only on stderr, after which the extension is absent and every assertion times out naming nothing; the image's Chrome for Testing allows it, and `tests/webauthn_extension.js` asserts the extension is *loaded* before asserting anything about captures. **`run-report.js` probes the browser and, since 2026-08-18, FETCHES one when none of them can side-load** — Selenium Manager (the binary that already ships inside `selenium-webdriver`) downloads a Chrome for Testing and the chromedriver that matches it, into `~/.cache/selenium`, which is the same thing the tests image gets by pinning it. It probes EVERY candidate first and a capable one wins outright, so a host carrying both Chromium and branded Chrome uses the Chromium rather than reporting on whichever name came first. Before that it answered with the first browser it found and skipped, which made `./local-run-tests.sh` — the launcher most people run, and the one that drives your own Chrome — report a permanent skip on every host whose `google-chrome` is the real thing; a suite that is always amber is one whose skips nobody reads. It still skips when there is no capable browser AND no network to fetch one, which is the one case the runner cannot arrange, and it names both attempts. Note the fetched **driver** is passed as well as the browser (`CHROMEDRIVER_BIN` beside `CHROME_BIN`): a Chrome for Testing 152 driven by the host's chromedriver for 151 fails on a version mismatch, which reads as a broken extension rather than as two halves of different releases. It also pins the job to the binary it probed, because a host with both Chromium and branded Chrome would otherwise probe one and launch the other. Independently, **chromedriver passes `--disable-extensions` among its default switches**, cancelling `--load-extension` on its own. And **Selenium's `VirtualAuthenticatorOptions` setters return `undefined`** in the JS bindings (unlike Java's), so chaining them yields no authenticator — and the failure reads `NotAllowedError: WebAuthn is not supported on sites with TLS certificate errors`, which sends you hunting through origins and certificates instead of at the line above.

**A test that CHANGES a shared service's configuration must change it back, and in a `finally`.** The rule above is about `localStorage`; this is the same hazard one process further out, and it is worse because the state outlives the browser session. `tests/pki_mutual_tls.js` POSTs a CA to the mock STS's `/tls/trust` half way through, precisely so that "the server would not verify this certificate" and "the server verified it" are told apart by one configuration change and nothing else — and the mock STS is a service every other job in the run shares. A CA left in that truststore makes the *next* run's first case pass for the wrong reason, which is a test that has quietly stopped asserting rather than one that fails. It is emptied in the `finally`, beside `driver.quit()`, so a failed assertion cannot skip the cleanup; and it is emptied at the START of the section too, since the previous run may have died in a way that skipped it anyway.

**A test that only passes against a freshly started service is one nobody can re-run.** `tests/webauthn_oidc_mfa.js` enrols a key against the STS, which remembers it per username for the life of its process — while a virtual authenticator lives only as long as the browser session. A second run was therefore told to assert with a key that browser had never held. CI starts the service fresh and would never have shown it. Unique-per-run usernames fix it, and the fix is *demonstrated* by running the test twice in a row rather than assumed.

**And the username a test signs in as is minted per run, by `tests/random_username.js`, with a prefix that names the test.** That is the general form of the paragraph above, and the reason is the same one seen from the mock's side: the mock STS keeps a users page, an authentication log and a statistics pane keyed by the name presented, and its KDC keeps a principal table that `findOrCreateUser()` adds an account to on first sight and nothing ever prunes. While every test signed in as `alice`, all of that was one person — two jobs in a run could not be told apart in it, and a row left behind by a job that died said nothing about which job. `usernameFor("kerberos-as")` returns `kerberos-as-<stamp>`; the stamp is per PROCESS, so one file's names visibly belong together, and it is logged once with the `RANDOM_USERNAME_STAMP` that reproduces it. Keep the environment override in front of the call (`process.env.KRB5_PRINCIPAL || usernameFor(…)`) — pinning the name is how a failed run gets re-driven by hand against what it left behind.

**Two things it must not be used for, and the second one has a trap.** A **fixture** account is not a username in this sense: `alice` in the mock KDC's principal table is RID 1104, a member of Domain Admins, with the full name `Alice Example`, and `krb5_tgs_ap.js` asserts every one of those against the PAC it gets back — an account created on demand carries Domain Users and nothing else, so generating a name there would not randomise that test, it would delete it. There is no admin API for the principal table, so a randomised Domain Admin cannot be asked for either. Neither is `alice` as ENCODED TEST DATA — a cname inside a message handed to the codec, a salt in a decoder fixture, a `given_name` claim — where nothing stores it, nothing can collide with it, and some neighbouring assertions are about byte offsets a name of a different length would move. **The trap** is the guard in front of a Kerberos job: `kerberos_as_page.js` checked "is this principal in `/krb5/principals`?", which was right for a configured name and silently wrong for a generated one, since a name created on first sight is not in that table until the test authenticates — so the check would have skipped the job, with a plausible reason, on a perfectly good stack. `requireKnownOrCreatable(body, name)` asks the question that is actually being asked, off `accountPolicy.anyUsernameAuthenticates` and `accountPolicy.neverCreated`, both of which that endpoint publishes.

**`log` is not in scope everywhere in this directory, and a log line where it is not is a `ReferenceError` that takes the whole test with it.** Two shapes, both of which turned a green suite into 23 failures on 2026-08-14. **`tests/edge_landing_contract.js`** is the exception to the convention every other file here follows: its module logger is `fallbackLog`, and `log` is the *parameter* of `assertEdgeLandingContract(log)` — on purpose, so the contract check reports into the log of whichever test called it. So nothing outside that one function has a `log` to write to, and `locate()` must use `fallbackLog`. Because `wsfed_sso.js` and `saml_encrypted_sso.js` call that check as their **first** step, one bad line there fails all 21 WS-Federation cases and the SAML EncryptedAssertion case at once, with `log is not defined` and `Current URL: data:,` — a message naming neither the helper nor the logger, on tests whose own files were never touched. Separately, **anything handed to `driver.executeScript` / `executeAsyncScript` runs in the browser**, where there is no bunyan: a log line inside one of those functions (or in a function `.toString()`d into a script) is `javascript error: log is not defined`, which reads as a page fault rather than a test-side mistake. Log what the script *returns*. Note that `node <test>.js` is no defence for the first shape: `edge_landing_contract.js` exports a function and has no main block, so running it directly exits 0 having executed nothing — it must be exercised through a caller, or by requiring it and calling `assertEdgeLandingContract(log)`.

**Adding the logger to a module under `client/src` breaks whoever borrows it, and that is a `module_paths.js` job.** Those 21 + 1 failures happened a *second* time the same day, from the other end: `client/src/edge_landing.js` acquired a `require("bunyan")` — correctly, it is a client module like any other — and `edge_landing_contract.js` was loading it with a bare `require()`. Node resolves a module's own requires from **where that module lives**, so bunyan was looked for under `client/node_modules`, which a checkout that installed only the tests' dependencies does not have; the message was `Cannot find module 'bunyan'` naming `edge_landing.js`, again before the browser was pointed anywhere. That check now goes through `paths.requireSharedModule()` like every other borrowed module here. So: **no test may bare-`require()` a file out of `client/src`, `api/` or `sts/`** — a module that has no dependencies today acquires one the next time somebody applies the logging convention to it.

**The tests image carries a PARTIAL `client/public` and `client/src`, and "the directory is there" is not "this is a checkout".** Most files reach the image flat beside the tests, but the two Kerberos pane tests resolve their files as `../client/public` and `../client/src`, so `tests/Dockerfile` mirrors a handful of pages, partials and bundles into `/usr/src/client/`. That mirror is a hand-maintained list and it breaks two ways at once, both of which cost the containerized run of 2026-08-17 while the identical host run was green. **A test that names its files fails**, and says so clearly: `krb5_ticket_history.js` and `krb5_operation_history.js` both list `spnego.html` / `spnego.js`, which no COPY line carried, because SPNEGO is the only page of the six whose name does not begin with `kerberos`. **A test that DISCOVERS its files does not fail at all** — `krb5_field_naming.js` finds the pages by the stylesheet they load, found five instead of six, and every assertion below simply had one page less to make; its floor is now the full six and its message names the COPY lines. And **a test that reads the whole directory is worse still**: `static_site_exclusions.js` skips its two directory-wide checks in the image on the grounds that `client/public` is not there, which the mirror silently made false — so it swept five Kerberos pages and reported a clean site, and its existence check failed the image naming two files that are in the repository. It now identifies the checkout by `client/public/index.html`, which the image copies flat and never into the mirror. So: adding a page to a workflow whose tests read source means adding it to that mirror, and a check that reads a directory must ask for a file only a checkout has.

**And the `client/src` half of that mirror did the same thing to two more tests, in the run that followed.** `xml_parse_inert.js` and `jwk_pem_encoding.js` both sweep the whole of `client/src` — every `DOMParser` call names a literal XML MIME type; nothing requires a package that reaches `elliptic`; no BigInt literal anywhere — and both skipped in the image on `fs.existsSync(client/src)`, which stopped being false the moment eleven Kerberos bundles were mirrored there for the pane tests. Neither then reported a silent pass, which is the one mercy here, but neither failed for its own reason either: the MIME sweep found **zero** `parseFromString` calls among eleven Kerberos modules and said "has client/src moved?", and the `elliptic` sweep judged those eleven and then died on `ENOENT: /usr/src/client/package.json`, naming a manifest for what is really a layout. Both now ask `checkoutSrcDir()` / `isCheckout()` for **`client/package.json`**, which is the right discriminator precisely because it sits *outside* `client/src`: no mirror of that directory can ever come to contain it, whereas any file inside it is one COPY line away from being mirrored. Pick a marker the mirror cannot reach, not merely one it does not hold today.

**The runner hands every job `--url`, so a new test that does not DECLARE that option fails before its first line runs.** `run-report.js` spawns each script as `node <script>.js --url <BASE_URL>`, and commander `exit(1)`s on an option it has not been told about — so a node-only test that has no use for a base url (it reads source, or serves its own sockets) still has to accept one. The report then carries a job that failed in 0.07s with `error: unknown option '--url'` and not one line of the test's own output, which reads as a broken runner rather than as a missing option; `page_load_retry.js` shipped that way on 2026-08-20. Take the option and say it is ignored, as `browser_tests_headless.js` and `page_load_retry.js` both now do. It happened a second time on 2026-08-22 — `scim_engine.js` and `scim_protocol.js`, two jobs and 0.06s each — so it is now a check rather than only this paragraph: `everyJobDeclaresTheUrlOption()` in `tests/jwk_pem_encoding.js` reads every `script:` run-report schedules and fails if one uses commander without declaring `--url`. A job that parses no arguments at all is still fine (`crypto_engines.js`), because node ignores the pair when nothing reads it.

**Every script `run-report.js` schedules has to be COPYed into the tests image, and forgetting is silent on every host run.** `tests/Dockerfile` copies test files individually, so a new test passes locally and fails in the image with `MODULE_NOT_FOUND` in a tenth of a second — a failure that names a file rather than a build. `testsImageHasNoCollidingFilenames()` in `tests/jwk_pem_encoding.js` reads the Dockerfile against the runner's job list and fails on the gap; it caught `api_ldap.js` and `ldap_page.js` on the day they were written, before either had ever been run in a container.

**And `tests/Dockerfile` is now built in THREE STAGES, because one COPY per test ran out of layers.** Docker's layer store refuses a chain deeper than **125** — `maxDepth` in moby's layer package — and every `RUN`, `COPY` and `ADD` adds one. This file is almost entirely `COPY`, one line per test script, borrowed module and vendored directory with the comment saying why, so it grows with every protocol this suite learns; on 2026-08-25 it reached 126 and the build died at `Step 132/136 : RUN ls` with **`max depth exceeded`**, a message that names no instruction, no file and no limit, printed after that step's own output had scrolled past — so it reads as the `ls` failing. The COPYs now live in two staging stages (`files1`, `files2`) that the final image takes in with two `COPY --from=… /usr/src /usr/src` lines; each stage starts its own chain and has the full 125 to itself, and the final image is back to a dozen-odd layers. **Three things to keep right when adding a COPY**: put it in a staging stage and never in the final one; keep it in its original position, because this directory is flat and the LAST COPY still wins a basename collision (preserved only because `files1` is copied in before `files2`, so moving a line *backwards* across the boundary silently reverses it); and write into `/usr/src`, since that one directory is all the two `COPY --from` lines carry — a destination outside it is staged and never reaches the image, with no error anywhere. `everyDockerfileStaysUnderTheLayerLimit()` in `tests/jwk_pem_encoding.js` counts every stage of every Dockerfile in the tree and fails at a budget of **100**, well before the build breaks, naming the file and the stage; `client/Dockerfile` is the next closest at 71 and has the same shape, one COPY per bundle.

**The corollary, now that there is a management API: a test that CHANGES the mock must change it back.** Since 2026-08-19 every one of those admin pages has an operation at `/admin-api`, so pinning a setting is a JSON POST rather than a form — which makes it easy enough that a test will now reach for it, and that is precisely when the other half matters. Nothing in the mock resets between jobs, so a custom claim left in `/admin-api/claims` changes what every later job's ID Tokens contain, a narrowed credential claim set changes what every later credential carries *and* what the issuer metadata advertises, and a `revoke-all` invalidates tokens a job that ran before yours is still holding. Read the setting first, put it back at the end, and put back the tokens too — `revoke-all` has no opposite, so the restore is one `restore` per `jti` that was **not** already revoked when you started, which is why the revoked set has to be read before rather than reconstructed after. The mock's own `admin_api.js` does all of that and is the file to copy the pattern from — it left this suite on 2026-08-28 and is readable here as `sts/tests/vendored/admin_api.js`, in the checkout the submodule points at. The one exception is the mock's CONFIGURATION, added 2026-08-19: every setting it has is at `/admin-api/config`, and `POST /admin-api/config/reset-all` puts *all* of them back in one call, so a job that pins an issuer or a clock skew has an opposite and should use it. Note which settings will not move — the bound ports, the TLS certificate's names, the Kerberos realm, SIDs and passwords, and the directory's base DN are all consumed at startup and are refused with the reason, so a test that needs one of those still has to set the environment variable before the service starts, exactly as `tests/krb5_spnego_http.js` does.

**The mock's `/admin` console is BEHIND A SIGN-ON now, and `/admin-api` deliberately is not.** Since the submodule bump of 2026-08-24 the mock STS ships `admin.authRequired` **on**: every `/admin` page and every `/admin` form needs a browser session from `/authn/login` plus a console role, and a caller that asks for `?format=json` — or posts JSON — is refused **401 `login_required`** rather than redirected, because a redirect to an HTML sign-in screen is not an answer a program can read. Two tests here were driving the console directly and both died in under a second, naming a credential rather than a gate: `sd_jwt_vc_presentation.js`, whose whole file failed on its *setup* POST to `/admin/vc-verifier-config` before a browser started, and the mock's `admin_api.js`, on the console read its API-versus-console comparison is made of. **The rule for a test is: configure through `/admin-api`, which is not gated and is the surface that exists for a program** — the action moves from the body to the path (`POST /admin-api/verifier-request/select`) and the same handler answers the same object. Sign in only when the CONSOLE is the thing under test, the way that file now does: GET a console page without `?format=json` and without following the redirect, take the `authn` id out of the `Location`, POST it to `/authn/login` with any username and password (this service checks neither), and send the `sts_mock_session` cookie back. The role comes from `admin.openWhenEmpty`, which is on: while neither role group has a member, whoever signs in holds both. Watch for the quieter half of this — a `fetch` that FOLLOWS the redirect gets the sign-in screen's headers and body, so its Content-Security-Policy check was reading the login page's policy while claiming to read the console's, and it passed because the two happen to be identical.

**Putting a setting BACK is `reset`, not `set` with the old value.** The mock records where every value came from — `appconfig` for one the process started with, `override` for one changed at runtime — and a `set` always produces the second, even when the value is byte-identical to what was there. So `spiffe_protocol.js`, which read four settings and wrote them back, left four rows reading `source: override` on a live container for ever, and the mock's `admin_api.js` check "no runtime override should be in force before this check runs" then fails on the **next** run against that same container, naming `spiffe.adminIds, spiffe.svidTtl, spiffe.autoCreateEntries, spiffe.attestWorkloads` and no test at all. `POST /admin-api/config/reset` with the key is the operation that undoes an override rather than covering it; use it unless the setting was ALREADY an override when your test arrived, in which case its value is what it goes back to. `reset-all` is the same argument for a job that pinned several.

**A `require` added inside the `sts/` submodule breaks this image and nothing else.** `tests/Dockerfile` copies the mock STS's modules **individually** — the set is the transitive closure of what `krb5_kdc.js`, `krb5_service.js` and `spnego.js` require, because there is no `.dockerignore` here and a whole-directory `COPY sts/` would drag the submodule's `node_modules` in with it. So the closure has to be **recomputed** whenever the submodule grows a dependency, and on 2026-08-17 it was not: the mock's admin console acquired `admin_stats.js`, `app.js` began requiring it, and all four in-process mock-KDC jobs — `krb5_as_exchange`, `krb5_tgs_ap`, `krb5_spnego_http`, `krb5_delegation_interop` — died at load with `Cannot find module './admin_stats'` while every host run stayed green, because a host run has the whole submodule. Those four tests catch the load error and say which COPY set is short, which is the only reason it reads as plumbing rather than as a broken KDC. Recompute it by walking `require('./…')` from those three files (`grep -oE "require\(['\"]\./[^'\"]+['\"]\)"` over each, then over whatever that turns up) rather than by adding the one file the error named — the error names the first missing module, not the last.

**A test that asserts a property by reading source must read a STATEMENT, not a line.** Four tests here prove something about the code by regex over `client/src` or `api/server.js` rather than by driving it — `xml_parse_inert.js` (every `DOMParser` call names a literal XML MIME type), `api_connect_timeout.js` (`outboundHttpAgent()` returns the cached agent, and every axios call site is bounded), `api_ssrf_guard.js` and `jwk_pem_encoding.js` (no bundle requires `jwk-to-pem`/`jsonwebtoken`/bare `crypto`; no BigInt literal anywhere in `client/src`; and `coverage_beacon.js`, which the coverage build appends to bundles raw, takes no `require` and touches no `process`). Those are cheap and genuinely load-bearing, and they have one failure mode of their own: a pattern anchored to a single line stops matching as soon as somebody wraps the call. The repo-wide 80-column sweep did exactly that — nine `parseFromString` calls wrapped at once, and the MIME check reported every one of them as a parse with no literal type; the caching check broke on nothing more than the `log.debug("Entering …")` the logging convention puts between the brace and the return. Both now join a line to its continuations before matching (`codeLines()` in `xml_parse_inert.js`) or allow anything but a brace in between. The give-away for this class is a failure that names a security property in a file nobody touched, so when one of these fires, **check the formatting of the reported line before believing the property broke** — and when writing a new one, assume the file will be reformatted, because it will be.

**A long in-page loop must be SLICED, and the script timeout is not `waitTime`.** `driver.executeScript` is bounded by the WebDriver **script timeout** — 30s by default, set separately from every `driver.wait` in the suite — and a synchronous script holds the renderer for as long as it runs, so one long call is a cliff rather than a slow pass. When it goes over, the run dies with `script timeout (Session info: chrome=121.0.6167.85)` and nothing else: no page, no function, no line, and the last thing printed is whatever step finished before it. `tests/saml_tools.js` drives the 2^10 power set of the SAML assertion's optional elements in-page precisely because a round trip per state would take minutes, and it failed exactly this way on a GitHub Actions runner on 2026-08-14. Two things stacked up: a `log.debug` pair added to the page's one-line accessors had made each rebuild emit ~1000 log records, taking the single sweep call from 1.9s to 34s on the dev host (see the hot-path note in the repo-root `CLAUDE.md`), and the runner is about **twice** as slow again on identical code — its text-field sweep took 35s where the same commit took 18s locally, so 34s became the 71s at which the run died. Note what that means for the arithmetic: a call that takes a comfortable-looking 15s on your machine has no margin at all in CI. Both halves are fixed: the page no longer logs its getters, and the sweep now runs 128 states per call and accumulates in node, so no single call is more than an eighth of the work. Write a loop that way from the start, set the timeout explicitly (`driver.manage().setTimeouts({ script: … })`) rather than inheriting the default, and remember that a 10x-slower CI host turns any margin you measured locally into a coin flip.

**A pane no test opens is a pane that is broken.** The Analyzer's "What the relying party asked for" pane threw `ReferenceError` from the moment the shared panes were extracted, and nothing noticed, because that pane fills only for an extension capture and nothing exercised one until the capture inbox existed. When a page grows a surface that only one input path reaches, that path needs a test on the same day.

**Before waiting on content, make sure the BROWSER GOT THE PAGE (`tests/page_load.js`).** The rule below is about a field the page has not filled in yet; this one is about there being no page at all, and it comes first because a page load over a network is not something `driver.get()` reports on. Chromedriver reports some failures by THROWING (`net::ERR_CONNECTION_REFUSED`, `net::ERR_NAME_NOT_RESOLVED` — a connection that was never established) and others not at all: when the connection IS established and then dropped — `ERR_EMPTY_RESPONSE`, `ERR_CONNECTION_RESET`, `ERR_HTTP2_PROTOCOL_ERROR`, the shapes a CDN edge produces once in a few hundred requests — `get()` resolves normally, `getCurrentUrl()` returns the URL that was **asked for**, and the tab holds Chromium's error page. Nothing the caller can see says the load failed, so the test waits out its whole budget for a field that was never there and fails naming one of *our* ids for somebody else's socket: `Waiting for element to be located ... Wait timed out after 10080ms`, on a page that was never ours. That is `WS-Trust 1.2 — Issue` on 2026-08-15 (test.idptools.com) and `WS-Trust 1.4 — Validate` on 2026-08-20 (idptools.com) — in both, the neighbouring cases loaded the same page seconds either side and passed, which is what a dropped connection looks like and is not what a broken page looks like. `loadPage(driver, url, readyId, { timeout })` retries **only** the network-error page (a page that is ours with the field missing is a product failure and is raised on the first attempt, because retrying it trebles the time every genuine breakage takes to report), and it says the error CODE — it reads `.error-code` out of the DOM, where the old diagnostic dumped the first 6000 characters of the page source and the first 6000 characters of Chromium's error page are Chromium's stylesheet. Two failed runs are on record whose logs contain several KB of `--google-gray-700` and not one word about what went wrong. **Use it for any navigation to a target this suite does not start itself**; `tests/page_load_retry.js` holds it to all of that against sockets of its own.

**And before pressing anything, wait for the page's BUNDLE to have run (`waitForPageBundle`, `waitForBundle`).** This is a third question, distinct from "did the browser get the page" above and from "has the page filled this field in" below, and it is the one that took out ten jobs at once on 2026-08-20 — every VC issuance, VC presentation and DID Tools job that drives a page, while the node-only jobs against the same services all passed. Nearly every control in this application is wired with an INLINE handler naming a browserify `--standalone` global: `onclick="didtools.resolveDid(); return false;"`, and the same shape across the VC pages. The markup carrying that handler is in the HTML from the moment the page parses, so `until.elementLocated` succeeds long before the bundle has executed — and a click in that gap does not queue, retry or fail. It raises `ReferenceError: didtools is not defined` **inside the page**, and out here it looks like a control that was pressed and did nothing, for ever. The gap is not small: these bundles are one to three megabytes of unminified JavaScript with an inline source map, and a suite run has Postgres, two Keycloaks, two mock STS instances, walt.id and Chrome on the same machine, so `elementLocated` plus `sleep(500)` is a bet that loses *reliably* rather than occasionally — two consecutive runs failed identically. **Not one of the ten failures named a page that was not ready**: they said "the credential issuer metadata was not retrieved (last status: (empty))", "resolving the generated did:jwk produced no verdict (last status: \" \")", "a ticked box that silently does nothing", "presenting should reach step 3" — each a statement about the product, on code that was working. `waitForPageBundle(driver)` reads the page's own `<script src="/js/X.js">` tags and waits for each one's export, trying the file's name and that name with the underscores removed (the two forms `client/Dockerfile` uses: `saml_request` keeps them, `vc_issuance_1` becomes `vcissuance1`), so a test that opens six pages carries no table of six global names and nothing goes stale when a page is renamed. Call it after every navigation to a page this test is going to press a control on; `waitForBundle(driver, name)` is the same wait when you want to name the global yourself.

**A step TRANSITION is not a field read, and `waitTime` is 2000ms.** The same runs failed two presentation jobs on the budget rather than on the wait: `tests/env/*.js` sets `waitTime: 2000`, which is right for a page filling a field it already holds the data for, and those tests were also spending it on "click Present, derive a bbs-2023 proof in the browser, POST it to the verifier, load the next page of the workflow and let its bundle run". `ldp_vc_presentation.js` and `jwt_vc_json_presentation.js` now derive a `stepWait = waitTime * 4` for anything that crosses a page or does crypto, and keep `waitTime` for reads. The house multipliers are `waitTime * 3` / `* 4` / `* 6`; pick one deliberately rather than inheriting the field budget by default.

**Waiting on content, not on elements (`tests/wait_for.js`).** Every field these browser tests read is static markup, so `until.elementLocated` succeeds during parsing and says nothing about whether the page has filled the field in. Following it with a fixed `driver.sleep(N)` is a bet on the page finishing in N ms, and those bets lose periodically on a loaded machine — it cost two SD-JWT VC issuance runs (2026-07-31), both `SyntaxError: Unexpected end of JSON input` at the same line. Use `waitForFilled` / `waitForValue` / `waitForJson` / `waitForStatus` from that module instead: they poll for the content, so they are *faster* normally and do not fail when the page is slow. Three details in there are load-bearing:

* An unfilled two-line `<textarea>` has a `.value` of `"\n            "` — **whitespace, which is truthy**. So `if (!value)` waves it through and `JSON.parse` of it throws "Unexpected end of JSON input", naming JSON for a timing problem. Test by parsing or trimming, never by truthiness; `forMessage()` renders it as `(blank: N chars of whitespace)` so a failure message cannot be mistaken for the bug below.
* `driver.wait(fn, timeout, message)` takes a **plain string, evaluated at call time**, so interpolating the polled value into it always reports the pre-poll value. The old local `waitForStatus` did exactly that, which is why failed runs logged the useless `(last status: )`. The last value must be attached in a `catch`.
* The reason `#jwt_payload` is slow enough to lose the race is worth knowing: `token_detail.js` fills it only after fetching `/claimdescription`, DOMParsing the IANA registry, **and then looping over every claim in that registry re-decoding the token and rebuilding both tables on each pass** — hundreds of identical rebuilds where one would do.

**A CSS `transition` makes a computed style a MOMENT rather than a state, and reading it too early asserts the value the element is coming *from*.** A style read in the same `executeScript` that changed the class returns the start value, not the end one: the transition is still pending and has not moved yet. It cost a run on 2026-08-24. The SCIM page's configuration pane fades a scroll cue in over 120ms; `scim_page.js` scrolled to the end of the table and read the top fade in the same script, and the assertion failed with `'0' !== '1'` about a cue that was on screen a tenth of a second later — naming the cue, which was working, rather than the read. **Wait for the transition, not for a sleep**: `getAnimations()` on an element holds a CSS transition while it is *pending* as well as while it runs and drops it when it finishes, so polling until that list is empty settles immediately when nothing moved and exactly once when something did. `scrollCuesAt()` in `tests/scim_page.js` is the pattern, and it is mutation-tested — deleting the stylesheet rule that raises the fade still fails the check, at once rather than after the wait. The failure mode to recognise is a geometry or computed-style assertion that names the property it read and passes when the section is run on its own.

**A page whose markup a browser has to GUESS AT behaves differently deployed than it does here, and no browser test can see it.** HTML has no syntax errors: a malformed tag is recovered from by a specified algorithm, and two implementations of that algorithm may legally disagree. `encryption_tools.html` carried `title="The encrypted value. "As PBES2 JWE" writes …"` — one attribute that ends at its second quote, followed by junk. Chrome's recovery put the end of the start tag in the right place and the page worked on every containerized run for a week. **html-minifier-terser, which only the static build runs, recovered differently**: it dropped the `</label>` and `</textarea>` around that field, so `<textarea id="enc_pbe_ciphertext">`'s raw-text content swallowed the next field whole and `enc_pbe_tag` **did not exist on the deployed site**. AES-GCM had no tag to verify, Decrypt refused every ciphertext, and the encryption job spent 150 seconds waiting for a box that was never going to fill — reporting the box. `client/build.js` had `--continue-on-parse-error` on the minifier with a comment saying some pages had "minor markup quirks" and the deploy build should not fail over them; that flag is what shipped this. **It is gone, the three quirks in the tree are fixed, and `tests/page_markup_well_formed.js` is the check that runs without a deploy** — two patterns over `client/public`, both mutation-tested, both reporting the file and the line. Three rules follow. A markup quirk is never minor, because the thing that reads it in production is not the thing that reads it here. **A build must not be told to continue past input it could not parse** — "skip and pass through" was not what the flag did. And a test whose only symptom is an empty output box should say what the page's own STATUS LINE said: `waitForOutput()` in `tests/encryption_tools.js` appends it to every timeout, and the sentence that identified this fault had been sitting one field above the box for the whole 150 seconds.
