# tests/ — the Selenium suite

Scope: everything under `tests/`, plus the launchers (`docker-run-tests.sh`, `local-run-tests.sh`, `remote-run-tests.sh`, `run-coverage.sh`) and the provisioning in `common/common.sh`. The commands themselves are in the repo-root `CLAUDE.md`; the services on the other side of each protocol are described in `api/CLAUDE.md`, `client/CLAUDE.md`, `waltid/CLAUDE.md`, `keycloak-wsfed/CLAUDE.md` and `docs/mock-sts.md`.

Tests use Selenium WebDriver with Chrome. A Keycloak test IdP is spun up automatically.

**What each individual test covers is in `docs/test-suite-map.md`** — 24 files' worth of notes, including which services each needs and what gates or skips it. Read it before changing a test you did not write, or before adding one that overlaps. What follows here is the part that applies to **every** test in the suite, and each item below has already cost a run.

## What the launchers must get right

**Tests must not assume the client's baked defaults exist.** `client/src/env/local.js` and `docker-tests.js` set `rfc8414MetadataUrlDefault` / `oid4vciIssuerUrlDefault` to this suite's STS, so the workflow pages open ready to use; `prod.js` and `test-idptools-com.js` set them to **`""`**, because a public site has no business defaulting to somebody's localhost. A test that asserts such a default therefore fails against the deployed sites for a reason that has nothing to do with the protocol. Assert the *shape* of a default when one is present, note its absence otherwise, and supply the URL from the test's own environment — which is what these tests do anyway a few lines later.

`./remote-run-tests.sh [base-url]` runs the same suite against a site that is **already deployed** — `https://test.idptools.com`, `https://idptools.com`, or a local dev server — while starting everything on the *other* side of each protocol locally, in an isolated compose project (`idptools-kctest`, `keycloak-tests.yml`): Keycloak 26.x on 8080, the mock STS on 8081 (WS-Trust plus the OID4VCI issuer and OID4VP verifier), **Keycloak 8.0.1 + wsfed on 8082**, and **walt.id's issuer on 7005 and verifier on 7003** behind their CORS proxies. Selenium drives a LOCAL browser, which is what makes that work against an https site: Chrome treats `http://localhost` as potentially trustworthy, so the page may talk to those without a mixed-content block.

Two things that launcher must get right, and both were missing until 2026-07-30 (the SD-JWT VC and WS-Federation jobs were silently skipping or failing): the walt.id **keys and rendered configuration** have to exist before compose starts, since both services mount a directory that is generated per run; and **`OID4VCI_WALLET_URL` must be the target base URL**, because the mock issuer's Credential Offer pages and the mock verifier's request pages hand the End-User back to the *wallet*, which here is the deployed site — its default of `localhost:3000` sends them nowhere. It reaches the container through `docker_compose()`, which forwards a fixed list of variables explicitly **because `sudo` resets the environment**: for a long time only `CONFIG_FILE` was passed, so every other `${...}` in a compose file (including `GIT_COMMIT` and `BUILD_NUMBER`) silently substituted to empty.

## Coverage, provisioning and the environment hazards

`./run-coverage.sh` runs that same containerized stack with Istanbul/c8 instrumentation (`docker-compose-run-tests.yml` + `docker-compose-coverage.yml`, the override touching only `api` and `client`). It therefore needs **everything the plain launcher does before compose starts**, and for a while had none of it: the walt.id key generation and `renderWaltidConfig` (both walt.id services mount `waltid/generated-*-config`, which is not in the repository — without the render compose creates those paths as empty directories, the services exit, and `--abort-on-container-exit` takes the whole run down), the pre-run teardown of stale containers from either stack, the WS-Federation side-car started and checked on its own, and a `waitForWaltid` through the proxies' published ports so a service that dies during startup prints its own log instead of stalling the healthcheck the `tests` service depends on. It tears the stack down on any exit, including the early ones those checks can take.

**The SAML SP key pair is never committed.** `generateSpKeyPair()` in `common/common.sh` generates a fresh self-signed RSA pair per run and exports `SAML_SP_PRIVATE_KEY` / `SAML_SP_CERT` (read by the tests through `common/sp_keypair.js`) and `SAML_SP_SIGNING_CERT` (registered on the Keycloak SAML client). It lives only in the run's environment — the containerized suite generates its own inside the tests container. Do not reintroduce a key pair under `tests/fixtures/` (gitignored, along with `sp-key.pem` / `sp-cert.pem`).

**Web Crypto needs a secure context, and the containerized suite is not one.** `window.crypto.subtle` exists only on HTTPS or a localhost origin. Locally the debugger is at `http://localhost:3000` (trustworthy, so Web Crypto works); in the containerized stack it is at `http://client:3000` — plain HTTP on a DNS name — where `crypto.subtle` is **undefined**. Most of the app depends on it (`jwt_tools.js`, `jose_jwe.js`, `vci_wallet.js`, `sd_jwt_vc.js`, `sd_jwt_vp.js`, `metadata_client.js`'s signature verification, `token_detail.js`, `digital_signature.js`, `encoding_tools.js`), so in that stack those pages silently have no crypto. The failure never says so: it appears as a `signed_metadata` signature that "does not verify with any key" (each `importKey` throws and is skipped) and as timeouts waiting for holder key pairs, proofs of possession and Key Binding JWTs that are never produced — which is how it cost a full debugging round. `tests/browser_flags.js` handles this and one other environment hazard, and the four SD-JWT VC tests call it; **any new browser test that signs, verifies, encrypts or hashes — or whose page must fetch one of this suite's local services — must call it too**:

- `--unsafely-treat-insecure-origin-as-secure` (plus the `--user-data-dir` Chrome requires alongside it), applied only to an origin that is not already a secure context, i.e. the containerized `http://client:3000`.
- `--allow-running-insecure-content` and `--disable-features=BlockInsecurePrivateNetworkRequests,PrivateNetworkAccessSendPreflights,LocalNetworkAccessChecks`, applied always. These matter against a **deployed https target**: this suite's services all live on loopback, and a fetch from a public origin to a private address is a Private Network Access request that Chrome blocks or preflights. The symptom is a status pane that never fills and a timeout naming metadata, a verdict or a credential — nothing about the network. Every other browser test in the suite had carried these flags for years; the four SD-JWT VC ones did not, which is why all four failed against `https://test.idptools.com` while passing locally.

**Clicks and reads taken just after a navigation must tolerate a stale element.** `debugger2.html` rebuilds its panes on load and after every token call, so a `WebElement` found a moment earlier can be detached before it is used — and the window is easy to miss on a *read*, because `findElements()` and `getAttribute()` are two round trips with a re-render able to land between them. `tests/oidc_userinfo.js` flaked two runs in three on exactly that, immediately after *Return to debugger*; it now re-finds inside a retry loop for both (`clickStable()` and a stale-tolerant `valueOf()`). Only staleness is retried — a genuinely missing element still returns null or fails, so the tolerance cannot hide a real regression.

**`--headless=new`, never bare `--headless`, in any browser test that uses crypto.** The tests image pins **Chrome 121**, where plain `--headless` selects the OLD headless implementation — and in that one `--unsafely-treat-insecure-origin-as-secure` has no effect. So on the containerized suite's `http://client:3000` origin `window.crypto.subtle` stays undefined however carefully `browser_flags.js` was called, and the symptom is a timeout waiting for a key pair that names neither crypto nor headless mode. It cost a containerized run of 13 jobs on 2026-08-05: the three new OIDC tests used bare `--headless` while the eighteen older crypto tests already used `=new`, and the give-away was that `dpop_workflow.js` — which generates a DPoP key on the same origin in the same run — passed. **It cannot be caught locally**: from Chrome 132 the old mode is gone and `--headless` IS the new one, so a modern browser passes either way.

**A section that clears `localStorage` must restore it.** `tests/sd_jwt_vc_issuance.js` runs one browser session through the whole workflow and then over a dozen further sections, several of which need an EMPTY page to measure or to check a pane's initial state — and the sections after them run on the state the workflow left behind. `preservingLocalStorage()` returns a restore function for exactly this; `metadataSignatureValidation()` and `presentationHandoff()` do the same by hand. Clearing without restoring does not fail where the mistake is: it fails hundreds of lines later in `presentationHandoff()` with "no credential in storage", which reads as a broken issuance. That assertion now names the likely cause and lists the keys it did find.

**A host run needs the STS's OWN `node_modules`, and `tests/module_paths.js` cannot supply them.** Four tests load `sts/bbs2023.js` from the submodule in place — `bbs2023_cryptosuite.js`, `ldp_vc_issuance.js`, `ldp_vc_refresh.js`, `vc_did.js`, each comparing the issuer's cryptosuite with the wallet's — and that module reaches `@digitalbazaar/bbs-signatures` through a dynamic **`import()`**. ESM resolution walks the directory tree upward from the importing *file* and **does not consult `NODE_PATH`**, which is the whole mechanism `module_paths.js` uses to make a borrowed module's CommonJS `require`s resolve against `tests/node_modules`. So those four fail at load with `ERR_MODULE_NOT_FOUND` unless `sts/node_modules` exists; `prepTestEnv()` in both host launchers therefore runs **`npm ci --prefix sts`** — `ci` rather than `install` because mock-sts commits its lock and `npm install` rewrites it (its lock still carries the pre-rename package name), which would leave the submodule showing a modified file after every run. The containerized suite never sees this: there `bbs2023.js` is copied flat beside the tests, next to `tests/node_modules`.

**`tests/package.json` pins `@noble/curves` and `@noble/hashes` at `1.4.0`, and the pin is load-bearing.** `client/src/bbs.js` is written against the 1.x layout (`require("@noble/curves/bls12-381")`, `@noble/hashes/sha256`), matching `client/package.json`'s own `1.4.0` pin — but 2.x renamed every subpath (`./bls12-381.js`, `./sha2.js`) and removed the old ones from `exports`, so the failure is `Package subpath './bls12-381' is not defined by "exports"` at require time, which reads as a broken module rather than a version mismatch. `@digitalbazaar/bbs-signatures@3.1.0` — the independent implementation `bbs_crypto.js` and `bbs2023_cryptosuite.js` check ours against — depends on `^2.2.0`, so before the pin it took the top-level slot and both tests died at load. Declaring 1.4.0 directly gives the client's module the hoisted copy and leaves bbs-signatures a **nested** 2.2.0, so each gets the major it was written for; that arrangement is what `tests/package-lock.json` now records, and it is why the pin cannot simply be relaxed to match the newer dependency.

**No test may `require("chromedriver")`.** It is not a declared dependency of `tests/package.json` — Selenium finds the driver itself — so a `require` for it makes that one test the only file in the suite that cannot *start*, with `MODULE_NOT_FOUND` in 0.1s, on any checkout installed from the manifests. It is an easy line to leave behind after developing a browser test as a standalone script, which is exactly how `dpop_workflow.js` acquired one.

**`populateMetadata()` now waits for the endpoints to arrive AND is willing to click Populate again, and every test in the suite was racing it before.** Two separate things are being waited on and conflating them is what made it flaky. *Retrieve* fetches the discovery document asynchronously and the Populate button is rendered only when it arrives, so waiting for that button does gate on the fetch — but the click itself can still land without effect: the button is re-rendered as the table is built, so a click can reach the copy being replaced, and the handler leaves every field untouched when it runs against an empty document (jQuery's `.val(undefined)` is a no-op, so the seeded placeholders simply remain). One click plus a bare wait therefore fails about once per cold run — it took out the **OAuth2 Client Credentials** job on 2026-08-05, a test that touches no authorization endpoint at all. The helper now re-finds the button and clicks again until the endpoints fill or the deadline passes, and mutation-testing it is easy: inject a capturing listener that swallows the first click on `.btn_oidc_populate_meta_data` and the single-click version fails while this one recovers. The helper in `common/tests.js` clicked *Populate* and returned; the discovery document is fetched asynchronously, so the caller could read `#authorization_endpoint` while it still held the placeholder `initValuesToLocalStorage()` seeds — `https://localhost/oauth2/authorization`. The authorization request then went to a host nothing is listening on, and the failure named the OP ("the OP did not show its login screen", at `https://localhost`) rather than the race. It surfaced about one run in a dozen. The wait is for the field to be filled **and no longer the placeholder**, rather than for an expected URL, so the one condition covers Keycloak's realms, the mock STS and a deployed OP alike; ten consecutive runs of the case that failed now pass.

**Waiting on content, not on elements (`tests/wait_for.js`).** Every field these browser tests read is static markup, so `until.elementLocated` succeeds during parsing and says nothing about whether the page has filled the field in. Following it with a fixed `driver.sleep(N)` is a bet on the page finishing in N ms, and those bets lose periodically on a loaded machine — it cost two SD-JWT VC issuance runs (2026-07-31), both `SyntaxError: Unexpected end of JSON input` at the same line. Use `waitForFilled` / `waitForValue` / `waitForJson` / `waitForStatus` from that module instead: they poll for the content, so they are *faster* normally and do not fail when the page is slow. Three details in there are load-bearing:

* An unfilled two-line `<textarea>` has a `.value` of `"\n            "` — **whitespace, which is truthy**. So `if (!value)` waves it through and `JSON.parse` of it throws "Unexpected end of JSON input", naming JSON for a timing problem. Test by parsing or trimming, never by truthiness; `forMessage()` renders it as `(blank: N chars of whitespace)` so a failure message cannot be mistaken for the bug below.
* `driver.wait(fn, timeout, message)` takes a **plain string, evaluated at call time**, so interpolating the polled value into it always reports the pre-poll value. The old local `waitForStatus` did exactly that, which is why failed runs logged the useless `(last status: )`. The last value must be attached in a `catch`.
* The reason `#jwt_payload` is slow enough to lose the race is worth knowing: `token_detail.js` fills it only after fetching `/claimdescription`, DOMParsing the IANA registry, **and then looping over every claim in that registry re-decoding the token and rebuilding both tables on each pass** — hundreds of identical rebuilds where one would do.
