# infra/ — static hosting, and the POSTs that have nowhere to land

Scope: `infra/terraform/`, `infra/terraform-test/`, `infra/terraform-krb5/`, `infra/edge/`, and the deployed sites (`idptools.com`, `test.idptools.com`). The client-side halves of the hand-off (`client/src/edge_landing.js`, `saml_response.js`, `wsfed_response.js`) are described in `client/CLAUDE.md`; the tests that exercise them in `tests/CLAUDE.md`.

**There are THREE root modules here and the third one is not like the other two.** `terraform/` (prod) and `terraform-test/` are the long-lived static sites. `terraform-krb5/` is an **ephemeral Windows domain controller** that exists only while `tests/krb5_real_dc.js` runs against it — see `infra/terraform-krb5/README.md`. Two consequences worth knowing before touching any of them. First, **each stack is a separate root module with a separate S3 state key** (`idptools.com/prod.tfstate`, `idptools.com/test.tfstate`, `krb5-interop/dc.tfstate`), and that is the entire reason a `destroy` of the KDC is safe to run routinely: Terraform destroys only what is in the state it is pointed at, so it cannot reach a bucket, a distribution or a DNS record belonging to a site. The KDC module reinforces that by owning its own VPC rather than borrowing the default one, taking no `terraform_remote_state` and referencing no ARN from another stack — the only thing the three share is the state *bucket*, which Terraform never destroys. Second, **the KDC stack is deliberately not free tier** and nothing starts it automatically: `run-report.js` skips the real-DC job unless `KRB5_DC_HOST` is already set, and `./infra/krb5-test.sh` is the only thing that brings the stack up, which it does around one test run with the teardown on an `EXIT` trap so a failed test still removes the instance.


The hosted sites (`idptools.com`, `test.idptools.com`) are S3 + CloudFront with **no backend**, and every protocol has to get its *response* back to a page with no server to receive it. OAuth2/OIDC manage alone — they come back on a redirect into `dist/callback/index.html`. Two protocols end with the IdP **POSTing** its result, which S3 answers 403/405, so both are answered at the edge by a **Lambda@Edge** on viewer-request (`infra/edge/`, deployed by `lambda_edge.tf` in both Terraform stacks, one zip and two handlers sharing `edge_common.js`):

| Path | Handler | Without it |
|---|---|---|
| `/wsfed` | `wsfed_landing.js` | the WS-Federation round trip **cannot complete at all** — the Passive Requestor Profile defines one way to return the token and no redirect binding to fall back to |
| `/samlacs`, `/samlslo` | `saml_landing.js` | SAML falls back to asking the IdP for the **HTTP-Redirect** binding into the static `saml_response.html`, which works but is out of profile — and the **EncryptedAssertion** job cannot run |

That SAML fallback is what `responseProtocolBinding()` in `saml_request.js` selects when no landing is available, and it is deliberately **kept** (real deployments use the Redirect binding, and it is the only thing that works with nothing able to receive a POST). But it is not the default where a POST can land, because `saml-profiles-2.0-os` §4.1.2 step 5 says the Response goes over HTTP POST or HTTP Artifact and *"the HTTP Redirect binding MUST NOT be used, as the response will typically exceed the URL length permitted by most user agents"*. **That stated reason is measurable and bites on encryption**: ciphertext does not compress, so a Keycloak response DEFLATEs to ~42% plain but only ~71% encrypted, taking the redirect URL from ~3.0 KB to ~7.0 KB against CloudFront's 8,192-byte cap — with each extra attribute or role mapper adding another 350–450 bytes. Note also that **decryption was never the obstacle**: `decryptAssertion()` in `saml_response.js` is node-forge in the page, no `fetch` and no Web Crypto. What the encrypted job needs is somewhere for the POST to land, because Keycloak's encrypted client is provisioned `saml.force.post.binding: "true"` (the plain one is `"false"`), so it POSTs whatever the AuthnRequest asks for. `HTTP-Artifact` remains impossible statically under any arrangement — it needs a server-side SOAP `ArtifactResolve` back-channel, and `saml_landing.js` refuses a `SAMLart` saying exactly that.

Five things about the landings are load-bearing:

* It **cannot be a CloudFront Function** like the sibling `callback_rewrite`. Functions are never given the request body, so the `wresult` would be gone before any code saw it. Only Lambda@Edge with **`include_body = true`** receives it — and `/wsfed` is therefore its own `ordered_cache_behavior` (POST allowed, caching off), because one behavior may carry a CloudFront Function *or* a Lambda@Edge on a given event type, never both.
* It has nowhere to stash the token, so it hands it to the browser: a same-origin page that writes the `wresult` into **sessionStorage** and `location.replace()`s to `wsfed_response.html?posted=1`, which reads it **once and deletes it** (a leftover would make the next visit render a stale sign-in as if it had just happened). The token never goes in the URL. Those key names are a contract **duplicated** in `client/src/wsfed_msg.js` (`EDGE_LANDING`) — Terraform and the site build ship the two halves separately and they cannot import each other — so `edgeLandingContract()` in `tests/wsfed_sso.js` reads both files and fails on drift. The generated page escapes `<`/`>` when embedding the token in its `<script>`: a `</script>` inside the token (CDATA can carry one) would otherwise close the element and inject the rest as live markup, which a mutation test demonstrates.
* Sign-out (WS-Fed) and the redirect-bound response (SAML) behave byte-identically to the api's routes, precisely so nothing downstream has to know which landing answered. The SAML landing does **not decode** the `SAMLResponse` — it passes the base64 through exactly as it arrived, because `decodeSamlParam()` on the response page already distinguishes raw base64 from DEFLATE+base64 and is the decoder the `?SAMLResponse=` path has always used.
* CloudFront caps a viewer-request Lambda at **40 KB** of request body (truncating beyond, flagged as `inputTruncated`) and 40 KB of generated response. A truncated token is refused with a 413 rather than rendered as though whole, and the no-JavaScript fallback copy is dropped before the hand-off itself is.
* A WS-Fed **`wa=wsignin1.0` with no token is not a sign-out** and answers 400 naming the cause: an `http` wreply is 301'd to https and the browser re-sends as a GET with no body, so "Signed out" after a successful login would be a long hunt.

The site build and the infrastructure **ship independently**, so a target can be current and still have no landing. `wsfedEdgeLanding: true` and `samlEdgeLanding: true` in the static env configs are the page's statement that each is deployed (with them false, `wreply` falls back to the response page with a paste-it-in notice, and the SAML ACS falls back to the Redirect binding), and `remote-run-tests.sh`'s `probeEdgeLandings()` probes both with a real POST — recognising a landing by the `<meta name="wsfed-landing">` its pages carry — **before `configureKeycloak` runs**, because what it finds is what gets registered as the client's ACS. A missing landing **skips the job with instructions** rather than failing.
