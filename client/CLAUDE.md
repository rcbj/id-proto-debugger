# client/ — the Express frontend (port 3000) and everything in the browser

Scope: `client/src/`, `client/public/`, the bundles, the pages and their layout. Cross-cutting matters — versioning and the `{{VERSION}}` stamp, `CONFIG_FILE`, the key-material opt-out rule, how the suite is run — stay in the repo-root `CLAUDE.md`. The tests that drive these pages are in `tests/CLAUDE.md`, the edge landings they hand off to in `infra/CLAUDE.md`, and the mock issuer/verifier they talk to in `docs/mock-sts.md`.

**`/client/`** — Express frontend (port 3000). Serves static HTML/JS pages and handles the OAuth2 redirect callback at `/callback`, forwarding query params to `oauth2_oidc_2.html`.

This file holds what applies across the whole frontend: the shared modules, the landing page, and the build. Each workflow's own hard-won detail is one file away, and **each of these is worth opening before you edit the pages it names** — every one records a defect that looked like something else:

## The landing page

`client/public/index.html` is the protocol chooser — one card per protocol, styled by `css/landing.css`. **Every card has to be visible without scrolling**, which is the one thing this page must get right: it exists to be a choice, and a choice you have to scroll to find is one you do not know you have. That constraint fixes every number in that file. **Sixteen cards** now sit in a filled **8 + 8** grid, ending ~597px down against a 625px headless viewport and the 640px budget `landingFitsOnOneScreen()` enforces. The thirteenth (LDAP) was the expensive one that forced seven columns; the **fourteenth (SCIM) was free**, because seven across turns 7+6 into a filled 7+7 — the same two rows and therefore the same height. **The fifteenth (SPIFFE) was predicted to be expensive and was not**, and the reason is worth keeping. 7+7+1 does put a third row below the fold — but the fix was not eight columns of narrower cards, it was the **230px this grid had been leaving on the table**. `max-width` was 940px, which is bootstrap 2's `.container` width; bootstrap-responsive.css widens that container to **1170px** at a viewport of 1200px or more, and the test viewport is 1366 wide. So `max-width: 1070px` (`8*125 + 7*10`) fits eight columns of the SAME 125px the seven had — the same wrapping, the same two rows and the same height, measured at 597px either way. Below a 1200px viewport the container is 940px again and auto-fit falls back to seven columns, which is the ordinary responsive degradation this grid has always had. **The sixteenth (Shared Signals) was free and the note above was WRONG about it**, which is worth keeping rather than deleting: the prediction that it would be expensive was made when the container was 940px, and the fifteenth card widened it to 1070px. Eight columns then hold sixteen cards as a filled **8+8** — the same two rows and therefore the same height as 8+7, measured at 597px either way. **The SEVENTEENTH is the next expensive one**: at 1070px, nine columns need `min <= 110`.

**The column count has had to grow four times, always for the same reason**: two columns put the last of six cards below the fold, three would have done it to the seventh, five to the ninth, six to the eleventh. The minimum width is arithmetic rather than taste, and it is the WIDEST value that works — *n* columns fit when `n*min + (n-1)*gap <= 940`, so six need `min <= 148.3` at a 10px gap. **Anything larger fails silently**: the grid simply stays at the previous count and the only symptom is the height. The eleventh card also cost an icon (40px down to 34px), a line-height and some padding — an icon costs its height once per ROW, so trimming it buys back twice what it gives up, which is why it is reached for before anybody's product copy is shortened to fit a layout. Descriptions are still kept short and roughly **equal in length**, because a grid row is as tall as its tallest card. Measure with the test at each step rather than estimating, and remember the containerized run and a host run differ by a few pixels: fonts-liberation's metrics are not a host's Arial's.

**Three cards point into the OAuth2 / OIDC pages**, because two of those protocols are panes rather than pages: Dynamic Client Registration links to `/oauth2_oidc_1.html#dcr_fieldset` (the fragment opens the page at its pane), and Token Exchange links to plain `/oauth2_oidc_1.html` — its pane is on `oauth2_oidc_2.html`, since an exchange needs a subject token first, so there is nothing on `oauth2_oidc_1.html` to scroll to. Two cards therefore share one href, which is why `tests/navigation.js` locates those cards **by title** (`cardByTitle()`) rather than by href; the CSS href locator matches both.

**PKI is the one card whose page half-works without the api, and it ships anyway.** The certificate authority itself is Web Crypto and pkijs in the browser; only the TLS test at the foot of `pki.html` needs `POST /tls/connect`, and the page says so itself with the `#pki_backend_notice` banner. So it is an ordinary card with no `data-not-on-static` marker — the test below fails a card that carries the marker without its page being in `EXCLUDED_PAGES`, and greying a workflow that mostly works is the wrong trade. That is what separates it from the three cards that follow.

**What is greyed instead is the one PANE, and it is greyed the way the cards are: switched off, not merely marked.** `disableTlsPane()` in `pki.js` runs from `onload()` when `appconfig.backendAvailable === false`, adds `pki-pane-disabled` to `#pane_tls` (the rules are at the foot of `css/pki.css`), sets `disabled` on **every** control in `#pane_tls_body`, and shows `#pki_tls_unavailable`. Both halves are needed for the reason a dead card is an `<a>` with no `href` rather than one that merely looks grey: a pane that only *looks* dead still submits on a Return keypress in a text field, and `runTlsTest()`'s own refusal is then the first thing that says anything. The legend is deliberately untouched, so the pane still collapses and expands. Two notes on the CSS: it greys with **colours rather than `opacity`**, because `opacity` makes a stacking context and the notice — the one line in there that has to be read — could then not be brought back to full contrast by any rule of its own; and `show()` in `pki.js` had to start toggling the `saml-hidden` class as well as the inline `display`, because `#pki_backend_notice` is hidden by that class in the markup, so for as long as the banner existed the static build asked for it and the class kept it off the page. `tests/pki_page.js` asserts all three properties separately, and reads `getComputedStyle` rather than the inline style — the check that read the inline style is exactly what agreed with the caller instead of with the user. See `docs/pki.md`.

**Two cards are dead on the static deployments and live everywhere else.** Kerberos needs the api's port-88 relay, so `client/static_site.js` drops all six of its pages from `dist/` — SPNEGO included, because the ticket it carries still comes from a KDC — and `client/build.js` rewrites both cards: `href` stripped, `landing-card-disabled` added, `aria-disabled="true"`. It stays an `<a>` — with no `href` it is neither focusable nor clickable, and every selector that reads this page, here and in `tests/navigation.js`, is written against `a.landing-card`; a `<span>` would drop it out of the geometry and accent-colour checks, which is exactly when a card silently stops fitting. The card is keyed off a `data-not-on-static` attribute in the markup and carries a **second** description (`landing-card-unavailable`, `display:none` everywhere else) saying why. **SCIM is the second card whose page works without the api, and like PKI it ships as an ordinary link.** RFC 7644 is plain HTTPS with a JSON body, so `scim.html` calls a SCIM server directly from the browser; what a static build loses is the api call path, and with it the ability to reach a server that sends no CORS headers or one with a self-signed certificate. The page says that itself in the `callPath` row of its Configuration Parameters pane (`refreshCallPathControls()` disables that select and prints the reason) rather than the card being greyed — same trade PKI makes, and the reason it carries no `data-not-on-static` marker and is not in `client/static_site.js`. **Four cards are dead on the static deployments and live everywhere else.** SPIFFE is the newest and gives up the most to be one — three of its readers need no network at all — and it goes anyway, because a page whose two biggest panes are permanently dead is worse than a card that says why; see `docs/spiffe.md`. **And one thing on that page is the opposite: present on the static deployments and nowhere else.** Each greyed card says why it is dead and none of them says what to do about it, so a note under the card grid names the remedy — deploy the containerized build, api and client together, from `https://github.com/rcbj/id-proto-debugger`. It is keyed off a `data-static-only` attribute the way the cards are keyed off `data-not-on-static`: `showStaticOnlyNotes()` in `client/static_site.js` adds `landing-static-note-shown` to it and `client/build.js` throws when the marker matches nothing, since a note that stays `display:none` is invisible on precisely the one deployment it was written for. It sits BELOW the grid, so it is outside the 640px budget `landingFitsOnOneScreen()` enforces — that check measures cards, and the requirement it encodes is that no *choice* falls below the fold. `tests/static_site_exclusions.js` holds the markup, the link, both CSS halves and the rewrite.

**The header's brand logo goes to this page, from everywhere.** It used to be workflow-aware — a script in `partials/header.html` rewrote its `href` off `window.location.pathname`, so the logo meant "the home of the workflow you are in" and each family got its own target. With ten workflows that made the one control every page shares mean ten different things, and it left no single click back to the chooser from a workflow's first page (where the logo pointed at the page you were already on). `tests/navigation.js` clicks **every** card and checks the page it lands on — its footer build number and its stylesheets. Adding a protocol therefore means three things here, and `landingFitsOnOneScreen()` in `tests/navigation.js` fails if any is missed: the cards must still fit (checked against the viewport *and* against a 640px budget, because headless Chrome has no toolbar and so its viewport is more generous than a real browser's), the new card needs its own `:nth-child(N) .landing-icon` accent rule or its icon silently falls back to the text colour, and no card may end up nested inside another — an unclosed `</a>` is invisible in a screenshot, since the browser recovers from it.

## The OAuth2 / OIDC pages were renamed

**`debugger.html` and `debugger2.html` are now `oauth2_oidc_1.html` and `oauth2_oidc_2.html`.** They were the only pages still carrying the name the whole project had when OAuth2 and OIDC were all it did; every workflow added since is `<protocol>_<step>`, and the two originals now read the same way. The rename is total and nothing answers on the old URLs: the pages, their bundles (`client/src/oauth2_oidc_1.js` / `_2.js`), `debugger2.css` (now `oauth2_oidc_2.css`), the `BUNDLES` entries in `client/build.js`, both sets of `browserify` lines in `client/Dockerfile` — the plain build's and the coverage build's `for entry in "name:standalone"` list, which is a *second* place and is only exercised by `./run-coverage.sh` — the `/callback` target in `client/server.js` and in `build.js`'s static callback shim, the landing cards, and the tests.

**The browser globals went with them**, which is the part that reaches every inline handler: `--standalone debug` is now `--standalone oauth2_oidc_1` and `debugger2` is `oauth2_oidc_2`, so the ~85 `onclick`/`onchange` attributes on the two pages call `oauth2_oidc_1.foo()` / `oauth2_oidc_2.foo()`, as do the `driver.executeScript` probes in `tests/oauth2_metadata_rfc8414.js`. That also fixed something that had never worked: three links at the top of `debugger.html` called `debugger.clickLink()`, and `debugger` is a **reserved word**, so those handlers were a `SyntaxError` in every browser since the page was written. The old global was `debug`, so the name was wrong twice over.

**`css/debugger.css` keeps its name on purpose.** Despite the name it is not this workflow's stylesheet — it is the shared `.dbg-*` pane chrome (the pane borders, the collapse legends, the expand-all toggle) that **21 pages** link, Kerberos and the VC workflows included. Renaming it to `oauth2_oidc_1.css` would have said something false about it; renaming it to what it actually is would have touched every one of those pages for no behavioural gain, so it was left alone and this paragraph is the answer to "why is that one still called that".

**The Configuration Parameters pane sizes its fields to its column, and the class that does it is `.dbg-config-table`.** Bootstrap gives every text input, select and textarea a fixed `width: 206px` (`input, textarea, .uneditable-input`), which outranks the `size="60"` several of those fields carry and takes no notice of the box it is in. That is harmless on `oauth2_oidc_1.html`, where the pane is one of two flex columns and about 854px wide at 1366, and wrong on `oauth2_oidc_2.html`, where the same table sits in one of THREE columns at about 419px: every field's right edge landed on the pane's border and the four boolean `select`s 25px past it, growing to 136px as the window narrowed, because the pane shrinks and a fixed field does not. So the form table carries `.dbg-config-table` and `debugger.css` gives its fields `width: 100%` with `box-sizing: border-box`, leaving checkboxes, radios and buttons intrinsic — those are as wide as they look, not as wide as their content. Auto layout is kept rather than the `table-layout: fixed` the metadata table beside it needs (that one renders a document we do not control), because here the labels are known and the label column should still take what the longest of them needs; the `width: 45%` on the first column is a preference a browser honours when the labels allow. `tests/oauth2_config_pane_layout.js` holds both pages to it at seven viewport widths, and asserts the field-to-cell width as well as the geometry — an 854px pane hides a 220px field perfectly well, so on page 1 the geometry alone can never see this coming back.

**The token exchange pane has two tabs, and the second one shows an exchange the page mostly cannot see.** *Parameters* is the form that has always been there; *HTTP* is the Token Request and its response as they actually went — method, URL, headers and body each way, and the elapsed time. Four things about it are load-bearing. **The default tab is never changed by code**: a successful call collapses this whole pane (`$("#token_fieldset").hide()`), so switching tabs from a response handler would rearrange a pane nobody is looking at and hand the next reader who expands it something other than the form they went there for — the tab's own LABEL carries the status instead (`HTTP · 200`), which is what a reader sees the moment they open it. **The bytes come from two different places**: a browser-direct call is recorded here from the jqXHR, where the browser withholds the headers it adds and CORS withholds most of the ones that come back — and the pane says so rather than presenting a partial list as a whole one — while the **proxied** call, which is this pane's default, is made by the api and can only be reported by the api, which returns it under `http_exchange` when the request asks with `http_trace: true` (see `api/CLAUDE.md`). When no trace comes back the pane falls back to the browser's own call *to the api* and names that too; a fallback that looked like the real thing would be a debugger showing the wrong URL with a straight face. **Nothing about it is drawn as markup** — `renderTokenHttpExchange()` builds text nodes, because a response body is somebody else's bytes and concatenating those into `.html()` is the `js/xss-through-dom` defect this same pane already carries a long comment about. And the **live** pane holds the exchange verbatim and writes nothing down — what is kept is a redacted copy, on the generation it produced; see the Token History paragraph below. The error pane is handed a copy with the trace taken back out (`tokenErrorWithoutTrace()`), or its five-row textarea would open on sixteen kilobytes of transport. `tests/token_http_exchange.js` holds all of it, geometry included.

**The same exchange is on the Token Endpoint Results pane too, and that is deliberate rather than a duplicate.** The exchange is *composed* on the request form, which is why the form has a tab for it — but a successful call collapses that form, so the pane a reader is actually looking at afterwards is the results one, and "what did the wire look like" is a question asked about a result. It carries a **Tokens** tab (the default: whoever just called the token endpoint came for the token) and an **HTTP** tab showing the identical view, with the identical label. What makes it one feature rather than two is that there is one view and one renderer: `renderHttpExchange()` stores the view on its CHANNEL and draws it into every host that channel has, and `tests/token_http_exchange.js` asserts the two panels' text is character-for-character the same so that a second implementation cannot quietly grow here. Two things are worth knowing before touching it. **That pane is not in the page** — `oauth2_oidc_2.js` builds it as a STRING in four branches and drops it into `#token_endpoint_result`, one of which emits a bare `<fieldset>` with no `.dbg-pane` around it — so the tab is not markup but `attachHttpTabToTokenResults()`, which wraps whatever was just built (the tokens become the first panel) and is idempotent because the pane is rebuilt after every call. Its buttons are wired with `addEventListener` rather than an inline `onclick`: the strip is created BY the bundle, so the handler is in scope by definition. And **the empty state differs from the form's on purpose**: on the form, no exchange means none has been sent yet; on the results pane it usually means the tokens on screen came back from `localStorage` on the return from `token_detail.html` (`?redirectFromTokenDetail=true`, the only caller of `recreateTokenDisplay()`), where the pane cannot know WHICH stored exchange those tokens belong to — the exchange is kept per generation, not in the current-token slots those fields come from — so it points at Token History instead. Saying "nothing has been sent yet" over a pane full of tokens would be a lie, and an empty panel would read as a broken tab; both states are asserted.

**The refresh pane has the same two tabs, and it is a second CHANNEL rather than a second copy of the first.** *Obtain New Access Token Using Refresh Token* and *Token Endpoint Results for Refresh Token Call* carry a `Parameters`/`Tokens` + `HTTP` strip apiece, drawn by the same `drawHttpExchange()` off a channel of their own — `HTTP_CHANNELS` in `oauth2_oidc_2.js` is the whole of the difference between them: a name, the hosts that draw it, and the last view drawn. Adding the pair took one entry in that table, `noteHttpRequestSent("refresh", …)` in `refreshButtonClick()`, `showHttpExchange("refresh", …)` in both of its ajax handlers, and `attachHttpTabToRefreshResults()` after the results pane is rebuilt. The proxied refresh now asks for `http_trace: true` like the token call does — the same `POST /token` on the api, so nothing changed there. `tests/token_http_exchange.js` drives Client Credentials and can therefore only reach this channel's EMPTY state, which is what it asserts; `tests/oidc_authorization_code.js` makes a real Refresh Request and asserts the exchange, both panes, and the redacted copy.

**The exchange is now KEPT with the token set it produced, and what is kept is redacted.** Every generation in `token_history` carries an `http_exchange` — the view `redactExchangeForStorage()` made, of exactly the shape `drawHttpExchange()` draws, so the **Currently Viewing** pane can hand it straight back to the same renderer under a third `Tokens`/`HTTP` strip. That is a reversal: this page kept no exchange at all until this build, and the reason it did not has not gone away, which is what the redaction is for. Method, URL, status, timing, response body and every other header and parameter are stored **verbatim** — they are what the exchange is FOR; the values of `authorization`, `proxy-authorization`, `cookie` and `dpop`, and of the `client_secret`, `password`, `client_assertion` and `assertion` parameters in either body shape, read `(redacted — not stored)`. Four things to know before touching it. Redaction is by NAME and deliberately blunt — a named header or parameter loses its **whole** value, because guessing which part of a credential is secret is how a redactor leaves half of one behind. Be exact about what it buys: this page already stores `token_client_secret` and `refresh_client_secret` as ordinary form state, so the redaction is not what keeps the client secret out of the browser — it keeps a second copy out of a record that grows one entry per call, outlives the form's state, and carries the api's HTTP **Basic** header, which is a credential this page never composed and had never persisted. Bodies are capped at `HTTP_STORED_BODY_LIMIT` and `writeTokenHistory()` drops the OLDEST kept exchanges one at a time when a write is refused, because `TOKEN_HISTORY_LIMIT` is 1000 generations and a browser has about five megabytes — the tokens are never dropped, the exchange is the extra. And an entry may legitimately have none: a set from the Authorization Endpoint (which this page reaches by navigating the browser, not by making a request it can trace) or one saved by an older build, and the pane says which rather than drawing an empty panel.

**Panes on `oauth2_oidc_2.html` COLLAPSE; they do not disappear.** Three of its rows put panes side by side in a flex row, and a `display: none` on a flex child does not leave a gap — the row re-divides its width among what is left, so the panes beside it move and change size and the page a reader meets after a token call is laid out differently from the one they were looking at a moment before. `collapsePane()` / `expandPane()` keep the container and its legend (which is what makes the state recoverable — a hidden pane offers nothing to click) and hide only the fieldset inside. They are for **panes**: the row- and field-level `.hide()` calls elsewhere in that file — `#authzCodeRow`, the PKCE rows, the device-grant rows — are untouched and must stay that way, since a row that does not apply to the selected grant is not something a reader goes looking for. One consequence needs care: a collapsed pane and a pane whose fieldset has simply never been opened are identical in the DOM, and the load path is entitled to open the second. `collapsePane()` therefore MARKS the container (`data-pane-collapsed`), and the guard that opens `#token_fieldset` on the authorization-code return reads that mark — it used to read `$('#step3').is(':visible')`, which was free while the pane was hidden and would now undo every deliberate collapse.

The browserify build runs inside Docker. There is no local build script — to rebuild bundles you must use Docker.

**One file in `client/src` is not a module and must not be treated as one: `coverage_beacon.js`.** It ships browser coverage back to the client server, and the coverage build gets it there by *appending* it to each finished bundle — `cat src/coverage_beacon.js >> public/js/${src_name}.js`, in the `COVERAGE` block of `client/Dockerfile`. So it is the only file here that browserify and envify never see: in the browser it is raw script text where **`require` and `process` do not exist**, and its `log` is a console-backed shim written *inside* its IIFE (at the top it would be new globals in the page's own scope). A `require("bunyan")` added to it by the 2026-08-14 style sweep therefore threw before `setInterval()` ever ran, which collected **zero** frontend coverage and failed the 12 tests that assert a clean browser console — none of which named the beacon. Only `./run-coverage.sh` appends it, so no ordinary run can reproduce that; `appendedBeaconNeedsNoModuleSystem()` in `tests/jwk_pem_encoding.js` reads the file instead. Anything it needs from configuration has to be a literal in it.

**A new page has to be registered in THREE places**, and they are not near each other: the `BUNDLES` array in `client/build.js` (which the static deployments use), a `RUN browserify` line in `client/Dockerfile` (which the container image uses), and the `for entry in "src:standalone"` loop in that same Dockerfile's `COVERAGE` block (which only `./run-coverage.sh` executes). Miss the second and the deployed static site is perfectly fine while the containerized page's `<script>` 404s — so the failure appears only in the suite, and only as a page that does nothing.

**Miss the third and NOTHING fails.** The page builds, ships, works and passes every test it has; it simply reports no coverage, and the only symptom is a number in a report nobody diffs. Until 2026-08-22 seven bundles were missing from it — all six Kerberos pages and `pki` — and the Dockerfile had carried a comment *saying* six of them were, for months, because a comment is not a check. `coverageListCoversEveryBundle()` in `tests/jwk_pem_encoding.js` now compares all three lists on every ordinary run (not just under `./run-coverage.sh` — that is the point, since the plain launchers never execute that block) and fails naming the bundle and the list. It also catches a `--standalone` name that disagrees between the two builds: that global is what every inline `onclick` calls, so a mismatch makes every click on the page a `ReferenceError` under coverage and nowhere else.

**A page that cannot work without the api needs a third:** `client/static_site.js`, whose `EXCLUDED_PAGES` / `EXCLUDED_ASSETS` the static build reads to leave that page, its bundle and its own stylesheet out of `dist/`, and whose `CARD_MARKER` it uses to grey the landing card. Kerberos is the only member today, and all five of its pages are in it. The Dockerfile entry stays: the exclusion is static-only, and `tests/static_site_exclusions.js` fails if the container build loses one. The entries stay in `BUNDLES` too, filtered rather than deleted, so a static-only omission does not read as a page nobody ever registered. Note what the module does *not* do — it fails loudly rather than quietly: `fs.rmSync` on an absent path succeeds, so a rename would turn the whole exclusion into a no-op, and the build throws instead. Same for a card whose marker stopped matching, and for any surviving page that links to a dropped one.

### Keeping `elliptic` out of the bundles

`elliptic` carries GHSA-848j-6mx2-7j84 — ECDSA signing computes `k`'s byte length wrongly when `k` has leading zeros, truncating it, which produces a faulty signature and can expose the private key to anyone holding both the faulty and a correct signature for the same input. **There is no patched version and there is not going to be one**: the advisory's range is `<=6.6.1` and 6.6.1 is the latest release, so `npm audit fix` cannot resolve it and an override has nothing to point at. The only remedy is to stop requiring it.

It was reaching **five** bundles — `oauth2_oidc_1.js`, `oauth2_oidc_2.js`, `jwks.js`, `token_detail.js`, `userinfo.js` — never because a page wanted ECDSA, but because browserify substitutes a bare `require('crypto')` with the whole **crypto-browserify** shim, and that shim contains browserify-sign and create-ecdh, and those contain `elliptic`. Four requires were pulling it, and three of the four were **dead code**:

| Require | Where | Replaced by |
|---|---|---|
| `jsonwebtoken` | `jwks.js`, `userinfo.js` — imported, never called | deleted |
| `jsonwebtoken` | `token_detail.js`, for one `jwt.decode(t, {complete:true})` | a local `decodeJWT()`, since decoding a JWT is base64url and no cryptography. Signature *verification* on that page was already Web Crypto's |
| `@fidm/x509` (plus `pem-file`, `@peculiar/asn1-pkcs8`) | `jwks.js` — the only references were two commented-out lines | deleted |
| `jwk-to-pem` | `jwks.js`, genuinely used | `./jwk_pem` |
| `require('crypto')` | `oauth2_oidc_1.js`, for the PKCE `code_challenge` SHA-256 | **`create-hash`** — the very module crypto-browserify uses for `createHash`, so it is the same implementation and the same digest without the ECDSA half. Web Crypto is *not* the answer here: `crypto.subtle.digest` is async while `setPKCEValues()` calls this synchronously, and `crypto.subtle` does not exist at all on the containerized suite's `http://client:3000` origin |

Three rules follow, and `tests/jwk_pem_encoding.js` enforces all three:

* **No file in `client/src` may require `jwk-to-pem`, `jsonwebtoken`, `@fidm/x509`, or a bare `crypto`.** Any one of them silently re-adds `elliptic` to whatever bundle it lands in. This is the only check that would catch a *new* page doing it. (Comments discussing these requires are fine — that is where the reasoning lives — so only real code lines count.)
* Those packages are **removed from `client/package.json`**, so a future `npm install` cannot quietly restore the option.
* `browserify` and the minifiers are **devDependencies**, not dependencies. They are build tools that ship to nobody, and moving them is what makes `npm audit --omit=dev` report **0 vulnerabilities** — the full `npm audit` still shows the four `elliptic` lows, correctly, because the *build tool* still contains it. Both images install with plain `npm ci`, which includes devDependencies, so the build is unaffected. Note `client/Dockerfile` uses `npm ci`, so **`client/package-lock.json` must stay in sync with `package.json`** or the image build fails outright — unlike `api/`, which uses `npm install` and whose lock is knowingly stale.

What remains is `browserify`'s own copy, on disk in the built image. It is not reachable from any page, and removing it needs the runtime image to prune devDependencies (a multi-stage build, or `npm prune --omit=dev` after the bundling steps plus dropping the global `npm install -g browserify`) — not done.

### No BigInt literals in `client/src`

`0n`, `8n`, `0xffn` — write `BigInt(0)` instead, and hoist it: `var _B0 = BigInt(0), _B8 = BigInt(8), _B255 = BigInt(255);`. Both `digital_signature.js` and `bbs.js` do, and both learned it the same way.

The reason is the toolchain, not the language. **browserify runs the `envify` transform over every file in a bundle that references `process.env`, and `envify` parses with an `esprima` build old enough to predate BigInt literals** — it rejects one outright as `Line NNN: Unexpected token ILLEGAL`. `insert-module-globals` lexes the same files for the same reason.

What makes this expensive is *when* it fires. A literal is completely harmless until the file it sits in acquires a `process.env` reference — and then the build fails with a **syntax error against a file the change never touched**, reported in the bundle of whichever page happens to require it, however many requires away that is. `bbs.js` carried three of them for months while nothing in it mentioned `process`; adding a `log.debug` logger (whose level comes from `CONFIG_FILE`) took out `browserify src/vc_presentation_2.js` at `Error: Line 104: Unexpected token ILLEGAL`, with nothing in the message naming `bbs.js`, BigInt, or the logger.

So the rule is "none in `client/src`", not "none in a file that mentions `process.env`": the trigger is not a property of the file, so a rule conditioned on it is one that passes until the day it matters. `bigIntLiteralsStayOutOfTheBundles()` in `tests/jwk_pem_encoding.js` enforces it, beside the `elliptic` check and for the same reason — it is the only thing that catches it without a full image build, and it is mutation-tested against putting `0xffn` back.

**If you hit `Unexpected token ILLEGAL` from a browserify step, do not start with the file the step names.** Run `esprima` over every file in that bundle's require graph; the offender is usually a module the entry point reaches indirectly.
