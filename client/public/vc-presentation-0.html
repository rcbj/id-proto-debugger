VC Presentation — How is the credential being asked for?

A credential is only useful when it is shown to someone. This workflow is the presentation half of SD-JWT VC: a verifier asks for particular claims, and the wallet answers with those claims and no others — over OpenID for Verifiable Presentations (OID4VP), using the presentation format RFC 9901 defines. It presents whatever credential the issuance workflow left in this browser.

Which side of the presentation is the debugger?

 
Configuration Parameters

What this wallet needs to know about the verifier. Unlike an issuer, an OID4VP verifier publishes no discovery document — there is no well-known endpoint to retrieve and nothing to populate these from, so they are set by hand. Restore Defaults fills in this suite’s own mock verifier.

The page on the verifier's own website where a person starts a verification — a relying party's "prove your age" page, say. Every flow below sends you there, and you choose on that page how the request is made. OpenID4VP does not say what such a page is called, so this is a whole URL rather than a path under the verifier. Against a verifier with no such page, paste a request into step 1 instead.
The verifier's own origin, which the JWKS URL below defaults under.
Where this wallet looks for the verifier's keys when a request is signed. For a pre-registered client this is the "out of band" knowledge OID4VP assumes the wallet already has. Leave it empty and a signed request is reported as unverifiable rather than trusted.
The root certificate this wallet trusts for a Verifier named by an x509_hash or x509_san_dns Client Identifier (HAIP 1.0 uses x509_hash). The request carries the Verifier's chain in x5c, normally without its root; the chain is finished here. Leave it empty and the chain is still checked link by link, and its top is reported as UNTRUSTED rather than trusted.
A wallet in a browser page can only use a Verifier that sends CORS headers, and most do not: a wallet is normally a native app, which has no CORS. Ticked, every call to the Verifier (the Request Object, its POST under request_uri_method=post, the Verifier's JWKS, and the answer posted to response_uri) is made by this debugger's api instead (POST /oid4vp/call), which no browser policy applies to. Unticked, the page calls the Verifier itself. Answers through the browser (fragment, query, form_post) always go through the browser.

How does the request reach the wallet?

 

Every protocol and every flow ends the same way for a presentation: your wallet builds it in the format of the credential it holds — an SD-JWT+KB for dc+sd-jwt, a Verifiable Presentation JWT for jwt_vc_json, a bbs-2023 derived proof for ldp_vc, a device-signed DeviceResponse for an ISO mdoc (mso_mdoc) — bound to this request and this verifier by the holder key. Under SIOPv2 a self-issued ID Token goes with it, signed by that same key. What differs is how the request reaches the wallet, how much the wallet can prove about who sent it, and whether the answer travels encrypted.
