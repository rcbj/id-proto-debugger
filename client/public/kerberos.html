What these choices actually decide

The KDC host is resolved by the api, which is where the relay runs — on the containerized stack that makes it the compose service name sts; localhost there is the api container, which listens on nothing.

The KDC picks the first encryption type the account supports, so the order is the negotiation. 18 and 17 are AES-SHA1 (what Active Directory uses), 20 and 19 are RFC 8009's AES-SHA2, and 23 is arcfour-hmac-md5 — legacy, disabled by the Windows Server 2025 security baseline, and still the reason a lot of Kerberos breaks in 2026. Offering only 23 to a current domain controller earns KDC_ERR_ETYPE_NOSUPP.

canonicalize lets the KDC correct the name, which is what AD uses for UPN logon. request a PAC sends PA-PAC-REQUEST; unticking it sends an explicit include-pac=FALSE and the ticket comes back with no PAC at all, which is how a Windows service behaves when it has no group memberships to read. forwardable is what makes a ticket delegable — an account flagged NOT_DELEGATED is refused it whatever is asked for.

Step 1 — no pre-authentication

Expected to be refused: the refusal carries PA-ETYPE-INFO2, which is where the salt comes from.

Why the salt has to be asked for

The salt is not guessable — Active Directory uses the realm followed by the sAMAccountName for a user, but a host-shaped string for a computer account — so this step is how a client learns what to hash the password with. An account that answers with a ticket instead has pre-authentication disabled, which is worth knowing about for its own reasons.

Step 2 — PA-ENC-TIMESTAMP

Turned into a key here; never sent to the api.

Why a wrong salt looks exactly like a wrong password

The timestamp is encrypted under the long-term key at key usage 1. Any other usage number produces a perfectly well-formed message that the KDC reports as a wrong password — which is also what a wrong salt looks like, and why the salt is shown above rather than hidden.

The ticket

A ticket's session key is a credential: whatever holds it can use the ticket. So the cache lives in sessionStorage and goes when this tab closes. Tick the box to keep it in localStorage instead — unticking it purges what was already stored, on the spot. The password is never persisted either way.

What this page cannot tell you. That a ticket was issued says nothing about whether a service will accept it: that depends on the service's own key version, its clock, and — on Windows — on the PAC inside the ticket, which is where the group memberships live. Turn this TGT into a service ticket, then present it, to find out.
