Kerberos — the AS exchange: get a TGT from a KDC

Ask a real Key Distribution Center for a ticket-granting ticket and watch every field of both messages. Works against a Windows domain controller, an MIT or Heimdal KDC, or this project's mock KDC. The Kerberos Decoder is next door for bytes you already have. With a ticket in hand: buy a service ticket, present one to a service, or delegate.

Everything protocol-shaped happens in this browser. The password is turned into a key here, the messages are built here, and the api is a guarded byte relay that carries them to port 88 — because Kerberos is not an HTTP protocol and a browser cannot open a TCP socket. That relay is why this page needs a back end at all, and why it is the one workflow here that cannot run on the deployed static site.

The KDC and the principal

The KDC picks the first of these that the account supports, so the order is the negotiation. 18 and 17 are AES-SHA1 (what Active Directory uses), 20 and 19 are RFC 8009's AES-SHA2, and 23 is arcfour-hmac-md5 — legacy, disabled by the Windows Server 2025 security baseline, and still the reason a lot of Kerberos breaks in 2026. Offering only 23 to a current domain controller earns KDC_ERR_ETYPE_NOSUPP.

Step 1 — ask with no pre-authentication

A first request carrying no pre-authentication is expected to be refused, and the refusal is the useful part: KDC_ERR_PREAUTH_REQUIRED carries PA-ETYPE-INFO2, which is where the salt comes from. The salt is not guessable — Active Directory uses the realm followed by the sAMAccountName for a user, but a host-shaped string for a computer account — so this step is how a client learns what to hash the password with. An account that answers with a ticket instead has pre-authentication disabled, which is worth knowing about for its own reasons.

Step 2 — ask again with PA-ENC-TIMESTAMP

The timestamp is encrypted under the long-term key at key usage 1. Any other usage number produces a perfectly well-formed message that the KDC reports as a wrong password — which is also what a wrong salt looks like, and why the salt is shown above rather than hidden.

The ticket

A ticket's session key is a credential: whatever holds it can use the ticket. So the cache lives in sessionStorage and goes when this tab closes. Tick the box to keep it in localStorage instead — unticking it purges what was already stored, on the spot. The password is never persisted either way.

What this page cannot tell you. That a ticket was issued says nothing about whether a service will accept it: that depends on the service's own key version, its clock, and — on Windows — on the PAC inside the ticket, which is where the group memberships live. Presenting the ticket is the AP exchange and is not built yet; nor is the TGS exchange that turns this TGT into a service ticket. Both are the next phase, and this paragraph says so rather than leaving a reader to conclude the ticket is unusable for some subtler reason.
