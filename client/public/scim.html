SCIM 2.0 Provisioning Debugger

SCIM (RFC 7642, 7643, 7644) is how an identity provider puts somebody into a directory and takes them out again. It is the one protocol in this debugger whose whole purpose is to write, which is why this page has two halves: one endpoint at a time for the ordinary debugging, and scenarios — named plans of many operations, each step carrying its own expectation — for the thing a single call cannot show you, which is what happens when a hundred of them run in order.

These endpoints create and delete accounts. Point this at a test directory. The scenarios below really do provision and deprovision the users they describe, and there is no undo.

Connection

The service root is the base URL every path is composed against — the host plus the SCIM base path, which is /scim/v2 on essentially every implementation. Do not include a resource path: this page builds /Users, /Groups and the rest onto it.

Which way the call goes. Unlike the LDAP and Kerberos workflows, the browser path here is real: SCIM is ordinary HTTPS with a JSON body. The api path exists for the three things a browser cannot do — reach a server that sends no CORS headers (which is essentially every real SCIM endpoint), reach one with a self-signed certificate, and report the exchange in full, since a browser withholds the headers it adds and CORS hides most of those that come back.

Authentication

RFC 7644 section 2 defines no SCIM credential of its own. It names six ways of doing it and makes exactly two normative statements: a server SHALL say which it accepts in a WWW-Authenticate header, and it MUST be able to map an authenticated client to an access control policy. All six are here, plus anonymous. Only the two OAuth ones carry scopes, which is the only way an operation can be refused with a 403 rather than a 401.

Specification:

Off by default, and clearing it removes whatever was already stored. A password on this page is never stored under any setting.

Digest is two requests: the first is answered 401 with a nonce, the second carries a hash computed over it. Both are shown in the Exchange pane, because that handshake is what this scheme is and a library normally hides it.

All three RFC 7616 algorithms are implemented here — SHA-256, SHA-512-256 and MD5, each with its -sess variant — and the strongest the server offers is the one answered. None of them is Web Crypto, which has neither MD5 nor SHA-512/256; a client that did SHA-256 only would report every MD5-only server as bad credentials.

The nonce count increases per request, which is what makes each credential single-use. A client that sends nc=00000001 every time authenticates once and is then refused as a replay — and refused without stale=true, so it reads as expired credentials rather than as a counter.

A DPoP proof is a JWT signed over this method and URL and carrying a hash of the access token, so a captured one is not replayable against another endpoint. A key is generated for this page session and never stored.

  Attribute generator
  
Generated users carry every optional attribute
  RFC 7643 section 4.1 defines — all six sub-attributes of
  name, the five multi-valued types with their
  type/primary/display, both addresses
  with formatted, and the whole section 4.3 enterprise extension.
  That is the point: a provisioning client tested only against
  userName and emails has tested nothing about the
  fields it will meet in the field. What a server stores is usually
  narrower, and the difference between “accepted and stored” and
  “accepted and dropped” is what reading the resource back
  shows.

  
The seed makes it reproducible. The same
  seed always produces the same users, so a failure on the seventh generated
  user can be run again exactly rather than described.

  

    

      
      
    

    

      
      
    

    

      
      
    

    

      
      
    

  

  
  

    
    
    
    
  

  







  Scenarios
  
A scenario is a plan, and every step in
  it carries its own expectation. So a green run does not mean “the server
  answered something” — it means every step did what the plan said
  it would, including the steps that expect a refusal. That is what
  makes the negative scenarios work: a 409 on a duplicate userName is a pass and
  a 201 is a failure.

  Operations History
  
Every request this page sent. Failure
  means the server answered and the answer was no — which is very often
  the correct outcome, and is what the negative scenarios expect. A row that
  stays Sent means nothing came back at all, which on this
  workflow is usually CORS refusing a browser-direct call before it was made.
  Those two look identical in a status line and need completely different
  fixes.
