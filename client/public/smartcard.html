Decode a YubiKey's Yubico OTP, OATH, PIV, OpenPGP card and YubiHSM Auth traffic. FIDO2 and FIDO U2F stay on the WebAuthn page. USB and NFC are the same bytes. A pasted trace needs no reader. A PIN, an OTP key, an OATH seed and an API key are not saved unless the box next to that field is checked, and a PIN is never saved.

This is the static deployment. Decoding and the OATH calculator work here. Verifying an OTP with YubiCloud, and talking to a reader, need the API. A container does not see a key on the host unless the operator passes the device through.

Configuration

Yubico OTP

Touch the key and it types the token. The public identity is the first twelve characters of a current 44-character OTP. The AES key decrypts the rest. The CRC is how a wrong key is recognised.

YubiCloud validation

The API key stays in this browser. The page signs the request and the API posts it. A BAD_OTP answer is still an answer.

Program a slot
How programming works

Writes a configuration to OTP slot 1 (a short touch) or 2 (a long touch) through the API, after you confirm it. Slot 1 normally holds the key's factory Yubico OTP credential, which YubiCloud knows: overwriting it cannot be undone. Generate fills the secrets from this browser's random source and leaves them on screen, because the key never gives a secret back. The access code is only needed for a slot that has one. Static passwords are not offered: their scan codes depend on the keyboard layout.

through the API; which slots are programmed

OATH

The calculator needs no key. Six digits is what an authenticator shows. The applet trace is YKOATH: PUT builds an APDU and does not send it.

Add an account to the key
How adding works

Paste the otpauth:// link a site's setup QR code holds, or fill in the fields with the base32 secret the site shows. The account is written to the key's OATH applet through the API, after you confirm it; an account with the same name is replaced. The key never gives a secret back. A TOTP period other than 30 seconds is kept in the name (60/Issuer:account), as Yubico Authenticator writes it.

through the API; read-only

PIV

NIST SP 800-73. A certificate sits in tag 70 inside tag 53. GENERAL AUTHENTICATE is decoded and not performed. Paste the response, including the status word, or the command.

Change the key
How PIV writing works

Keys, certificates and the management key itself are changed under the card management key: the page authenticates with it (mutual 3DES or AES, the algorithm read from the key's metadata), sends the change, and closes the connection, which resets the card. The key never leaves this browser. The PIN and PUK are changed with their current values, and a wrong one costs a try (three by default) — the page never retries. Generate shows the public key; most software also wants a certificate for it, which Import stores. Nothing typed here is stored.

through the API; read-only

OpenPGP card

Application related data and the public key. There is no OpenPGP message here. A signature or a decipher is decoded and not performed.

Change the card
How OpenPGP writing works

Every change is checked against the Admin PIN first, in the same sequence; three wrong tries block it, and the page never retries. Generate sets the key's algorithm, generates it on the card, and writes its OpenPGP fingerprint and creation time so GnuPG recognises it — the key that was in that slot is destroyed. A FIXED touch policy cannot be turned off without resetting the OpenPGP applet. Nothing typed here is stored.

through the API; read-only

YubiHSM Auth

This is the applet that authenticates to a YubiHSM 2. CALCULATE's 48 bytes are the session keys a host would hand to that HSM. This page does not open a session. The management key and the credential password are not saved.

Add or delete a credential
How writing works

Each write carries the applet's management key. A wrong one costs one of its retries, so the page never fills it in: the factory default (16 zero bytes) is a button you press. A credential is AES-128 — derived from a password the way yubihsm-auth and ykman derive it (PBKDF2-SHA256, salt "Yubico", 10000 rounds), or from the two keys themselves — or EC P-256 from a private key. Its credential password (up to 16 bytes) is what a session asks for. Nothing typed here is stored.

through the API; read-only

Reader

The reader is the machine the API runs on. localhost on this pane is that machine. A container does not see a USB key unless the operator passes the device through. PC/SC is optional: if the library is not installed, listing readers says so and the API stays up.

The reader relay is off on this API. Set smartcardReaderEnabled: true in its env file to list readers and transmit. It is off by default because any APDU reaches the card, including a wrong-PIN VERIFY that blocks the PIN.

Challenge-response to an OTP slot. Over WebHID the page polls the key the way yubikit does and waits up to 15 seconds for a touch. Through the API — any browser, Firefox included — the api asks the key over HID itself (it must run natively: node api/native.js --smartcard), because a YubiKey on USB answers challenge-response only on HID; for a key on an NFC reader it falls back to SELECT and CALCULATE over CCID. The keyboard OTP field on the first pane works in every browser.
