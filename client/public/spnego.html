SPNEGO — Kerberos over HTTP

The protocol that puts a Kerberos ticket in an HTTP header, and the reason a corporate intranet site signs you in without asking for anything. Four layers, of which HTTP shows you one: RFC 4559 carries RFC 4178 (SPNEGO, the negotiation) which carries RFC 4121 (the GSS-API Kerberos mechanism) which carries the AP-REQ the AP exchange page builds.

The first 401 carries no token, and that is the whole problem. A server answers WWW-Authenticate: Negotiate and nothing else: it does not say which realm, which KDC, or which service principal name. The client derives the SPN from the URL's host name and finds the KDC from its own configuration — so when SPNEGO fails, it usually fails over a DNS name or an SPN registration that leaves no evidence on the wire at all. This page shows you both halves of both round trips, and names the SPN it derived, so that the guess is visible rather than implicit.

What these choices actually decide

The mechanism list is ordered, and the order is not cosmetic: RFC 4178 section 5 lets the mechListMIC exchange be skipped only when the acceptor selects the mechanism the initiator listed first. Select anything else and the MIC becomes mandatory — because an attacker who struck the preferred mechanism out of the list on the wire would otherwise be indistinguishable from an acceptor that does not support it.

The MIC is signed with the subkey from this client's own Authenticator, because at the moment the NegTokenInit is built that is the only context key in existence. The server's own MIC comes back signed with the acceptor's subkey, which RFC 4121 makes the context key once it has been offered. Two MICs, two keys, and the asymmetry is forced by when each one is computed rather than chosen.

This page never sends a password anywhere and never asks for one: it spends a ticket that the AS and TGS pages obtained.

The ticket this needs, and where to get one

SPNEGO obtains nothing. It spends a service ticket for the SPN above, which is what the AS exchange and then the TGS exchange produce — so those pages are where you go, and each of them will offer you a link back here once you have what this page needs. Nothing about the Kerberos half changes because HTTP is carrying it.

Round trip 1 — the unauthenticated request

The challenge is the bare word Negotiate with nothing after it (RFC 4559 section 4). A token there is not a harmless extra: a client that reads it as the acceptor's first negotiation token has nothing to answer with.

The ticket that was sent

The ticket travels inside the AP-REQ, and it is encrypted under the service's long-term key — not under anything this browser holds. So the fields below are the ones a client can see, and everything that matters to the service (the client's name, the ticket flags, the session key and the PAC) is opaque here until you supply that key. On a real deployment you would take it from the service account's keytab; the decoder page reads a keytab directly.

Why your browser will not do this for you. Chrome and Firefox perform Negotiate only for hosts on an explicit allow-list (AuthServerAllowlist, network.negotiate-auth.trusted-uris), and send a Kerberos ticket to nobody else — which is a defence rather than an inconvenience, since a ticket handed to the wrong host is a credential handed to the wrong host. That is also why this page performs the handshake by hand: it is the only way to see what a browser would have sent.

What SPNEGO does not carry. No realm, no KDC, no SPN, and — on a rejection — no reason. negState has four values and none of them is an error message, so the only diagnosis available is the mechanism's own error token: a KRB-ERROR inside responseToken. When one arrives this page decodes it, because a reject with nothing inside it cannot be told from a wrong password.
