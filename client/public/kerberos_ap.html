Kerberos — the AP exchange: present the ticket

The end of the protocol, and the only page that answers the question the rest were preparation for: will the service accept it? A KDC issuing a ticket says only that the KDC was willing. Buy a service ticket first if you have none, or see delegation for the ways a ticket can be obtained on somebody else's behalf.

A service is not sent a bare AP-REQ. It is sent an RFC 2743 InitialContextToken — 0x60, the Kerberos mechanism OID, the token id 01 00, then the AP-REQ — and inside that AP-REQ's Authenticator sits a checksum of type 0x8003, which is not a checksum at all. It carries the channel bindings and the GSS flags, and every integer in it is little-endian in a protocol where everything else is big-endian. It is the most commonly botched field in Kerberos, so this page decodes it field by field rather than showing you a hex blob.

The ticket to present

A TGT will not do: it is a ticket to krbtgt, and a service refuses it with KRB_AP_ERR_NOT_US. That refusal is worth seeing once, and the decoder page will show you the ticket's sname if you want to know why.

Where the service is

Prefilled from the SPN's host component, which is a guess: an SPN's host part and the address a service actually answers on are not required to agree, and on a load-balanced service they routinely do not.

There is no default: a Kerberos service can be on any port. That is also why the api disables this relay endpoint unless krb5ServicePorts is set — sending caller-supplied bytes to an arbitrary port is a broader capability than reaching a KDC on port 88, so it is switched on deliberately. What bounds it instead is the payload check: only a GSS-wrapped AP-REQ, or a bare one, gets through.

The security context

Mutual authentication is an echo: the AP-REP returns the Authenticator's ctime and cusec encrypted under the ticket's session key. Only something holding the service's long-term key could have decrypted the ticket to learn that session key, so a correct echo is the service's identity. This page checks the echo — a client that asks for mutual authentication and does not verify it has only asked.

Note that KerberosTime carries no fractional seconds, so the echoed ctime is second-precision and the sub-second part travels in cusec. Comparing a millisecond-precision timestamp here accuses a perfectly correct service of not being itself.

Per-message tokens

Once the acceptor has offered a subkey, these must be keyed from it rather than from the ticket's session key — and the key usage depends on who is speaking: an initiator signs with 25 and seals with 24, an acceptor with 23 and 22. The wrong pair produces a token the far end cannot verify, and the error names the checksum rather than the direction.

The PAC, and what a Windows service actually reads. A ticket proves who the client is and says nothing about its group memberships — a Windows service authorizes on the PAC inside the ticket instead, which carries the account's SID, its groups and its UserAccountControl flags. Supply the service key below and the pane will decode it: the group SIDs with their well-known names, and each of the four signatures checked separately. Those four are not interchangeable. The server signature is made with this service's own key, which is what lets a service verify the PAC by itself; the other three are made with the krbtgt key, so only a KDC can confirm them — and altering the PAC's contents breaks the server signature while leaving the KDC signature verifying, because that one covers only the server signature's bytes. That is the gap the extended KDC signature (CVE-2022-37967) was added to close, and it is why a signature that cannot be checked here is reported as not checked rather than as a failure: on a service ticket you do not hold the krbtgt key at all.

What is still missing. Constrained delegation — S4U2Self, S4U2Proxy and resource-based constrained delegation — and cross-realm referrals. A ticket this build produces carries a PAC a Windows service can read, but nothing here yet asks a KDC to obtain one on behalf of somebody else.
