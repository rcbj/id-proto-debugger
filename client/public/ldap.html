LDAP Protocol Debugger

LDAP v3 (RFC 4511) is BER over a TCP socket, so a browser cannot speak it: there is no fetch, no XHR and no WebSocket that produces an LDAPMessage. Every operation on this page is therefore performed by the debugger’s api, which opens the socket, and the Exchange pane at the foot shows both halves of what was asked of it. The URL below is resolved by the api and not by this browser — localhost there means the machine the api runs on.

Connection & Bind

The bind is an LDAP operation in its own right (RFC 4511 section 4.2), and it is the only one whose failure is about credentials — result code 49, invalidCredentials. It has a button of its own here rather than being a side effect of the first search, so that “my credentials are wrong” and “my filter is wrong” never look alike. Every other pane binds with these same fields before it does anything.

The password is not saved in localStorage — every other field on this page is. Against this project’s mock directory, any password is accepted except the literal string invalid, which is refused with a 49 so that a negative test has something to fail on.

Search

The four buttons below fill these fields and then run, rather than running a hidden query — the filter is the thing worth reading. The last one is the one nobody guesses: there is no attribute on a user that lists their groups (memberOf is a Microsoft extension, and OpenLDAP has it only behind an overlay), so “which groups is this user in” is answered from the other end, by searching the groups for a member value that is the user’s DN.

Groups

There is no “add user to group” operation in LDAP. A groupOfNames keeps its membership in a multi-valued member attribute whose values are DNs, so adding a member is a modify carrying one add change and removing one is a modify carrying one delete change with the value. The two buttons below do exactly that, against the group, using the uid from the Users pane as the member; the Exchange pane shows the change list they built.

DN:

Delete a user and then read this group again: its member still names the DN that is gone. That is correct — referential integrity is a directory feature, not a protocol rule. OpenLDAP needs an overlay for it and Active Directory does it in the DSA; nothing in RFC 4511 requires it, and a debugger that tidied the dangling value away would be hiding the thing worth seeing.

Entry — the operations themselves

The same five write operations against any DN at all, in the protocol’s own vocabulary. This is what the two panes above are shorthand for.

Modify

The changes are applied in order and the whole operation is atomic: either every change or none of them. A delete naming an attribute that is not there is 16, noSuchAttribute, and deleting the last value of an attribute deletes the attribute — an LDAP attribute always has at least one value.
