VC Presentation — Step 1 of 3: The Verifier’s Request

A verifier has asked for a presentation. Before any part of the credential is disclosed the wallet has to establish three things: who is asking (the Client Identifier, and what its prefix lets the wallet prove about them), what they are asking for (the DCQL query, next to the credential this wallet actually holds), and how the answer travels back. Nothing is disclosed on this page.

What the protocol Demands of This Request

The protocol chosen on step 0 decides what this wallet refuses. Every rule is listed whether or not it passed. A REFUSED row is why Continue is off; a WARNING row is shown and answered anyway. Under HAIP 1.0 the rules about the transport refuse, because the profile exists so that wallets do not negotiate them.

What Is Being Asked For

The DCQL query, decoded, against the credential this wallet holds: a claim in green is one the credential can disclose, a claim in red is one it cannot — and a vct in red means the verifier is asking for a different kind of credential altogether.

Which query the request carries: DCQL (OpenID4VP 1.0 section 6), or a DIF Presentation Exchange 2.1.1 presentation_definition, which the OpenID4VP drafts used and 1.0 removed. A DCQL claim with values is matched by exact type and value (section 6.4.1); a mismatching claim is treated as absent.
 
What the Verifier asks to be PROVEN about a claim rather than shown, such as age >= 18. A Presentation Exchange predicate is standard (DIF PE 2.1.1); a DCQL one is this debugger's extension, honoured only when the credential query marks it critical. AnonCreds proves a range in zero knowledge; an mdoc answers an age bound with the issuer's age_over_NN; every other format cannot, and a required predicate is then REFUSED rather than answered with the value. Receive a Request (cross-device)

In the cross-device flow the verifier's screen shows a QR code and the wallet is on another device, so nothing navigates here. Paste what the code encodes — an openid4vp:// URI, an https:// link carrying the same parameters, or just the query string — and the wallet will read it, fetching the Request Object if it is passed by reference.
