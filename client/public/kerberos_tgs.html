Kerberos — the TGS exchange: spend a TGT on a service ticket

A TGT is not a ticket to anything useful. It is a ticket to krbtgt, and its purpose is to buy others without the password being used again. This page does that: name a service and the KDC issues a ticket to it. Get a TGT first if you have none; present the result when you have one; or spend the TGT on somebody else's behalf — S4U2Self, S4U2Proxy, forwarding and renewal.

This page never asks for your password, and that is the point of the exchange rather than a convenience. A TGS-REQ is signed with the session key inside the TGT, so the password is used once, at logon, and never again for the life of the ticket. The shape is worth knowing too: the TGT travels as pre-authentication — a PA-TGS-REQ whose value is an entire AP-REQ, whose Authenticator carries a checksum over the encoded request body. The panes below show that nesting.

The service to get a ticket for, as the KDC knows it. It must match a registered servicePrincipalName EXACTLY — a near miss is KDC_ERR_S_PRINCIPAL_UNKNOWN, which reads as a missing service rather than a typo.

The commonest failure here is KDC_ERR_S_PRINCIPAL_UNKNOWN, and it almost never means the host does not exist: it means the SPN is not registered, or is registered on a different account. setspn -Q <spn> is the check on Windows. Note the name-type as well — a two-part SPN is NT-SRV-HST, and AD is inconsistent about enforcing that, which is worse than being strict.

The Kerberos realm, conventionally the DNS domain upper-cased. It is case-sensitive on the wire and a realm that differs only in case is a different realm.
Where the KDC is. Resolved and reached by the api's relay, not by the browser — Kerberos is DER over a socket and a page cannot open one.
88 by convention, on both TCP and UDP. The api will only reach ports on its krb5AllowedPorts list, so a non-standard port has to be added there too.
UDP first is the traditional client behaviour, falling back to TCP when the reply will not fit. A reply carrying a PAC usually will not, so most real exchanges end up on TCP.
The encryption types offered, IN PREFERENCE ORDER — the order is the negotiation. The KDC picks the first it supports, so putting 23 (RC4) first tests the weak path by accident.

The KDC picks the first of these the service account supports — not the first the user supports. A ticket the client can read and the service cannot is KDC_ERR_ETYPE_NOSUPP from the service's point of view.

Send a subkey in the authenticator. It changes which key usage number opens the reply — 9 with a subkey, 8 without — and a client that always tries one fails half the time.

A subkey changes which key the reply is encrypted under: key usage 9 with one, key usage 8 without. The KDC chooses based on what was sent, so a client that always tries one of the two fails half the time — and the failure is an integrity error that names neither. This page reports which usage opened the reply.

Service tickets held

What a service ticket does not tell you. That the KDC issued one says only that the KDC was willing. Whether the service accepts it depends on its own key version, its clock, and — on Windows — on the PAC inside the ticket, which is where the group memberships live and which this build does not yet produce. Presenting the ticket is the only way to find out, and that is the next page.
