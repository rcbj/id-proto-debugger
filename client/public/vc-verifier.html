VC Presentation — the debugger as the Verifier

Here the debugger is the Verifier of OpenID for Verifiable Presentations 1.0: it asks a wallet for claims and checks what comes back. You compose a DCQL query, the page signs the Authorization Request with a certificate issued under the Verifier's own root, and you hand the request to a wallet. The wallet posts its answer to a response_uri this debugger's api hosts on the page's behalf, because a page cannot receive a POST. Every check on the answer is reported on its own line. The other side, the debugger as the Wallet, is the presentation workflow.

 

1. What to ask for

One credential query. The DCQL below is generated from these fields and stays editable, so a second query or credential_sets can be written by hand.

Segments separated by dots; a number is an array index and * is every element. For an mdoc, the first segment is the namespace. A line may start with a claim id and a colon (a: address.country), and end with the values it must have (= DE | AT; a whole number is an integer, true and false are booleans).
One set per line, the claim ids above separated by commas, most preferred first (DCQL claim_sets, OpenID4VP 1.0 section 6.1). Every claim then needs an id.
intent_to_retain on every claim of an mso_mdoc query (Appendix B.2.4, ISO/IEC 18013-5's IntentToRetain).
  Each anchor's SubjectKeyIdentifier, base64url, which is the AuthorityKeyIdentifier of every certificate it issues (OpenID4VP 1.0 section 6.1.1.1; HAIP 1.0 section 5). The wallet SHOULD return a credential that matches; one that does not is reported on its own row, and its issuer's trust is still decided by the anchors.
One per line, name op integer with op one of >= > <= <: prove it, do not show it. OpenID4VP 1.0's DCQL has no predicates, so in DCQL they go in this debugger's extension (x_debugger_predicates, marked critical); in Presentation Exchange they are its standard Predicate Feature. Only AnonCreds proves a range in zero knowledge; an mdoc answers an age bound with age_over_NN; any other format fails the predicate. A predicate's claim must not also be in Claims. Predicate query page.
Presentation Exchange is sent as presentation_definition and answered with a presentation_submission, as the drafts defined; this Verifier checks such an answer in AnonCreds only, and reports any other format's as incomplete.
An AnonCreds proof is checked against the issuer's schema and credential definition (and, for a revocable credential, its registry definition, status list and tails), which a Verifier with no ledger is given out of band: an AnonCreds bundle. Without it an AnonCreds answer is incomplete. Not stored.
 
2. How to ask
HAIP is a profile of OpenID4VP, not another protocol. Under it this Verifier does not send a request HAIP forbids it to (anything but x509_hash, a request by value, an unencrypted response, a format other than dc+sd-jwt or mso_mdoc), and names the rule. An answer that breaks one of HAIP's rules is reported on its own "HAIP 1.0" rows, and every other check still runs; the HAIP line says whether the answer conforms.  
The key of the leaf certificate an x509_hash or x509_san_dns request is signed with. The root stays P-256. HAIP 1.0 section 7 makes ES256 the one every wallet must verify.
Sent INSTEAD of dcql_query (section 5.1: one or the other, never both). A scope is an alias for a DCQL query the wallet already knows (section 5.5); this page checks the answer against the query above, so make it the one the scope stands for.
A JSON array of transaction objects, each { type, credential_ids, ... } (section 8.4), sent base64url-encoded. For an SD-JWT VC the answer is checked by Appendix B.3.3.1: the KB-JWT's transaction_data_hashes must hold the hash of each string as sent (sha-256, or one of the object's transaction_data_hashes_alg). A query a transaction is bound to must require holder binding (B.3.3).
A JSON array of attestations about this Verifier, each { format, data, credential_ids? } (section 5.1). Carried as given; the wallet decides whether to use them.
The certificate is a leaf made for this request, under the Verifier's root CA (below), which is kept across runs. The leaf's subjectAltName is the api's host name and its Authority Information Access points at the root, which the api serves. A signed Digital Credentials API request is the exception: its leaf names this page's host (see the note under the response mode).
Only for the pre-registered prefix. The request is signed with the Verifier's request key (below); the JWKS the wallet must have registered for it is shown there and in pane 3.
 

One payload, one signature per Client Identifier, in a JWS JSON Serialization (Appendix A.3.2.2). client_id and verifier_info go in each signature's protected header only. The first signer is the prefix chosen above.
Under request_uri_method=post the wallet may send a wallet_nonce; this page signs a fresh Request Object holding it while the wallet waits (the api holds its request open). If it cannot in time, the wallet is answered HTTP 503 (section 5.10.2), never an object without its nonce.
The roots (an IACA for mdoc) an issuer's x5c must chain to. With none, an x5c-signed credential's issuer trust is reported as not performed, and the verdict is incomplete rather than a pass: a certificate is not trusted just because it is in x5c (SD-JWT VC section 2.5).
Where a wallet reaches this debugger's api. The request_uri, the response_uri and the root's caIssuers URL are built from it. Empty: the api's oid4vpVerifierPublicBaseUrl, or else the address this page reached the api at, which a phone scanning the QR code usually cannot reach (localhost, api). An https URL. It only shapes the URLs handed to the wallet; the api still serves on its own host, so the address must lead back to it. When the host is an IP address the leaf names it in an iPAddress subjectAltName, and x509_san_dns cannot be used: an address is not a DNS name.
On by default wherever there is an api. From the page, each of these is a cross-origin GET the browser lets it read only when the server sends CORS headers, and SD-JWT VC issuer metadata and did:web hosts usually send none (Token Status List section 8.1 makes it only a SHOULD). Through the api it is fetched server-side under the api's address policy. Either way a fetch that fails is reported as a check not performed, naming the URL. A static site has no api, so the box is off there.
One per line: an iss, then the certificate it is bound to, by the SHA-256 of the signing certificate, a certificate of its chain or the anchor it chains to (sha256:<hex>), or by the signing certificate's common name (cn:<name>). SD-JWT VC section 2.5 lets a Verifier configure such a mapping; without one, an iss that no subjectAltName names is reported as not authenticated by the certificate, and never fails the signature.
Returned as redirect_uri in the answer to the wallet’s POST (section 8.2), with a fresh random response_code added for each answer, as section 8.2 requires. Empty: none — which a same-device flow should not be (HAIP 1.0 section 5.1: Verifiers MUST include one).
These are what a wallet is given to trust this Verifier, so they stay the same from one request to the next; only each request's leaf certificate is new, issued under the same root. They are private keys. Unticked, nothing is stored and whatever was is removed at once; the identity then lasts this page load, and Download carries it.
