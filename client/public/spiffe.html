SPIFFE Protocol Debugger

What SPIFFE’s three server surfaces are

SPIFFE’s server side is three surfaces and they have almost nothing in common. The bundle endpoint is plain HTTPS — one GET returning a JWK Set, and the whole of the federation protocol’s server half. The Workload API is gRPC, and it is what a workload talks to in order to be given an identity. The SPIRE Server API is gRPC over mutual TLS — forty-two methods across six services — and it is what an operator and an agent talk to. All forty-nine methods are on this page.

Why both gRPC surfaces go through the api, and whose localhost these addresses mean

A browser cannot speak gRPC at all, and that is not a limitation of this page: gRPC is HTTP/2 with a binary framing and its status in the trailers, so fetch can neither send trailers nor read a grpc-status — and it cannot present a client certificate, which the SPIRE Server API requires. Both gRPC surfaces are therefore performed by the debugger’s api, and the Exchange pane at the foot shows both halves of what was asked of it. The addresses below are resolved by the api and not by this browser — localhost there means the machine the api runs on, and a unix:// path is a path on that machine.

Why the two gRPC surfaces authenticate in opposite ways

The two gRPC surfaces are authenticated in opposite ways, and reading that as an inconsistency is the mistake to avoid. The Workload Endpoint specification says that endpoint MUST NOT require its clients to authenticate — a workload has no secret and no root of trust until that call gives it one. A SPIRE server, by contrast, binds a port whose callers present an X509-SVID over mutual TLS and authorizes every method against what the caller is. So: fetch an SVID from the Workload API with nothing at all, then present it to the SPIRE Server API and find out who that makes you.

Configuration Parameters
What is in this pane, and what deliberately is not

Every editable setting on this page, in one place and under the name of the pane it acts on. What stayed in the panes below is what is the operation — the method pickers, the two request editors and the two offline inputs — so nothing here is a second spelling of a field that also exists somewhere else: each of these boxes is the one element with its id, and an edit here is an edit to the value the call is made with. The Trust Bundle group is the exception and is here whole, buttons and document and all: everything it needs is in this pane already, and what it produces — the trust anchor the SPIRE Server API group presents — is a setting two groups below it rather than a call to somewhere else.

Trust Domain

Why a trust domain is lower-case, and what a URL parser hides

A trust domain is the unit of trust in SPIFFE and the authority part of every identifier in it. It is lower-case: spiffe://Example.org/x is not a valid SPIFFE ID and is not another spelling of spiffe://example.org/x either — they are different identifiers, and a URL parser hides that by lower-casing the host for you.

Trust Bundle

What a trust bundle is, and the one defect that verifies nothing silently

A SPIFFE trust bundle is a JWK Set with two extra members, spiffe_sequence and spiffe_refresh_hint. Every JWK in it must carry use, and a consumer MUST IGNORE one whose use is missing or unrecognised — which is why a bundle full of keys with no use is not slightly imperfect but verifies nothing, silently: the failure shows up as an SVID that will not validate and never as anything naming the bundle. The two registered values are x509-svid and jwt-svid.

What this switch reaches, and what it cannot

The bundle endpoint is the one SPIFFE surface that is plain HTTPS, so it is the one with a TLS certificate to check at all. Its URL is above, with the other three addresses. Clearing this reaches a bundle endpoint carrying a self-signed certificate, which a development trust domain usually does.

Workload API

What workload.spiffe.io: true is for, and what it is not

That header is the one check a conforming Workload API makes, and it is not a security control — anybody can send a header. It exists so that a caller cannot reach the endpoint by accident. Held Identity

What clearing that box does, and when

Clearing that box removes what is already stored, on the spot — an opt-out that left yesterday’s private key in storage would not be one. With it clear the identity lives only until you reload this page. Every other field here is remembered either way.

SPIRE Server API

Why ordinary hostname verification cannot apply to a SPIRE server

A SPIRE server’s certificate carries no DNS name, so ordinary hostname verification cannot pass — it fails with ERR_TLS_CERT_ALTNAME_INVALID, which reads as a certificate problem rather than as a check that was never applicable. The api therefore replaces that check with a SPIFFE one on the URI subjectAltName. The chain is still verified in every mode above, including the last: that mode turns off the identity check and nothing else.

Workload API
Why this surface authenticates nobody, and what a second message shows

This surface never authenticates anybody and must not: a workload has no credential until this call gives it one. FetchX509SVID hands back an SVID with its private key, which is what makes the SPIRE Server API pane reachable as somebody. Four of the seven methods are streams that a real client holds open for the life of its process — ask for two messages on FetchX509SVID and the second one is a rotation.

Held Identity
What is held here, and the two ways to come by it

An X509-SVID and the private key that goes with it. There are exactly two ways to come by one here: FetchX509SVID above, which needs no credential at all, and AttestAgent below, which makes you an agent. An SVID without its key proves nothing, which is why both are kept together and why the pane says when only one of them is here.

SPIRE Server API
How SPIRE authorizes a caller, and why the port asks rather than requires

Forty-two methods across six services. Its TCP port is mutual TLS: the caller presents an X509-SVID and every method is authorized against SPIRE’s own table, which classifies a caller as local (it arrived on the private Unix socket), agent, admin, downstream, or nothing at all. The port asks for a client certificate and does not require one, because AttestAgent has to be reachable by somebody who has no SVID yet.

Why UNAUTHENTICATED and PERMISSION_DENIED are different instructions

A refusal here is the interesting answer, not the disappointing one. UNAUTHENTICATED means “authenticate” and PERMISSION_DENIED means “you may not” — two different instructions, which SPIRE distinguishes and this page keeps apart. Debug.GetInfo is local-only in SPIRE’s own table, so an administrator’s SVID over TCP is refused it; that reads like an omission and is not.

Certification Request
Why there is a certification request builder on this page

Five of the forty-nine methods take a PKCS#10 certification request — AttestAgent, RenewAgent, MintX509SVID, BatchNewX509SVID and NewDownstreamX509CA — because in SPIFFE the requester keeps its own private key and the authority never sees it. The signature on the request is the proof of possession, and it is what lets an authority certify a key it has never met. The private key generated here stays in this page, so an SVID issued against this request is paired with it automatically.

Why MintX509SVID is the one method that reads the SPIFFE ID asked for

A CSR’s extensions are a request and an authority may ignore every one. MintX509SVID is the exception and the reason the SPIFFE ID field in the Configuration Parameters pane exists: it is the one method with no registration entry to take an identity from, so the URI subjectAltName in the request is the only statement of what is wanted.

SVID Inspector
What makes a certificate an SVID, and where the identity is not

Reads an X509-SVID (PEM or base64 DER) or a JWT-SVID, here, with no network. The one thing that makes a certificate an SVID is its URI subjectAltName: the identity lives there and nowhere else, and it has exactly one. The subject DN carries no meaning at all in SPIFFE, so a reader who looks there for the identity is looking at the one field that never has it.

Why reading a JWT-SVID is not verifying one

Reading a JWT-SVID is not verifying one. Nothing here checks a signature; ValidateJWTSVID on the Workload API is what does that, and it is the one method in the family that behaves like a production implementation.

SPIFFE ID
The four ways the grammar is stricter than a URL parser

The grammar is stricter than a URL parser, in four ways that each produce an identifier looking perfectly fine in a log. A trust domain name is lower-case. The path is not a URL path: no percent-encoding, no empty segment, no . and no ... There is no port, no userinfo, no query and no fragment — each of those is a way of writing an identifier that a naive startsWith() treats as belonging to a trust domain it does not, which is an authorization bug in anything that federates. And /spire is reserved for the implementation itself.

Operations History
Why a row that stays Sent is not a Failure

Every call this page has asked for, newest first. A row that stays Sent means the api never answered at all — which is a different thing from Failure, which here usually means the round trip worked and SPIFFE said no.
